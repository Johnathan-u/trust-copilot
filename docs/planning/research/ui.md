## Highest-impact findings

- `/vendor-response` is unfinished: Start/Continue shows “Questionnaire Interface Coming Soon” (`apps/web/app/vendor-response/page.tsx:107-125`). Completing vendor collection requires an actual answer/save/resume/submit journey and sender review.
- `/dashboard/requests` only calls `/api/vendor-requests` (`page.tsx:79-96`); incoming public Trust requests, attachments, notes, replies, assignment/status and suggested reply APIs exist but have no screen (`apps/api/app/api/routes/trust_requests.py:253,286,321,383,398,672,693,731,786`). Public request confirmation therefore lacks a visible operator inbox.
- `/dashboard/review` is a 29-line instruction/link page, not a review queue. Detailed review has unacknowledged saves (`review/[id]/page.tsx:113-183`), “Saved” inferred from a ref rather than successful persistence (`:771`), no edit/review permission checks in its controls (only `can_export` at `:33`), and very wide tables with all questions rendered (`:702-827`).
- Shared shell reserves a sidebar of at least160px even at the smallest viewport (`components/layout/DashboardShell.tsx:77`). This leaves an unusably narrow main area on phones; horizontal overflow masks layout failures.
- Shared `Input` renders a sibling label without `htmlFor` or generated input ID and lacks error associations (`components/ui/Input.tsx:13-24`). Shared `Modal` has Escape/backdrop closing but no focus trap, return-focus, accessible title association or accessible close label (`Modal.tsx:13-49`). `Toast` lacks live-region semantics and always shows a success tick (`Toast.tsx:20-35`).
- Loading failures frequently become empty/healthy screens: document and questionnaire registries, exports, requests, members, notifications, trust articles and integrations. Notifications can label failed retrieval “No active alerts. Your compliance coverage looks healthy” (`notifications/page.tsx:104-119,209-213`).
- Workspace switch changes only workspace and reconstructed role-derived permission booleans (`contexts/AuthContext.tsx:59-79`). It does not refresh subscription or MFA policy/custom-role grants. Several pages do not key their data fetches to workspace: dashboard, coverage, AI insights, audit, alerts, integrations, proof chain. Prevent stale data or action targets during switching.
- Trust admin exposes `published` in its type but not a publish/unpublish control (`dashboard/trust-center/page.tsx:15,124-172,300-379`); overview assumes three `demo-*` slugs (`:50-55,275-288`). Public article cards are click-only divs with hover expansion of up to50,000 characters and an ad-hoc modal (`trust/[slug]/page.tsx:286-324`).
- Settings hardcodes `$25/month` even for annual subscriptions (`settings/page.tsx:49-77`); checkout sends503 billing failures to the dashboard (`checkout/page.tsx:164-168`). Show accurate purchase/pending/failure state.
- Security activity expects `items` (`security/page.tsx:125-131`), while Activity consumes `events` (`audit/page.tsx:290-299`). Audit category filtering only filters the returned page and replaces the total with that page's filtered length (`audit/page.tsx:294-299`).
- Product analytics APIs exist, but no production callers were found outside their ingestion endpoint; no browser GA4/GTM/gtag instrumentation exists. Detailed distinction below.

## Reusable UI acceptance contract

Each screen-specific ticket below consumes the following shared acceptance contract. This is a concrete checklist to attach to each ticket, not a substitute for its unique functional criteria:

1. Verify its permitted roles and denied roles with direct route navigation, not only hidden navigation. Mutating actions respect current server permissions and changed membership. Display readonly context and reason for disabled actions where useful.
2. Verify initial loading, successful nonempty, genuine empty, filtered-empty, unauthorized, session-expired, not-found, network failure, server failure, rate-limit and recovery states wherever applicable. No failed request is represented as success, zero, healthy, or empty data.
3. After a mutation, present pending state, prevent duplicate submissions, check HTTP result, retain user input on failure, present retry, and reload the persisted result. Announce outcome to assistive technology. Destructive actions explain exact effect and dependencies.
4. Visually inspect at320px,375px,768px,1024px and1440px, and200% zoom. No clipped content or page-level horizontal scroll; tables may have a labelled scroll region and usable compact detail view. Long filenames, long unbroken text, large totals and translated-length labels do not overlap. Touch targets meet the chosen accessible size contract.
5. Keyboard-only completion; visible focus; correct tab order; labels, descriptions, errors, heading hierarchy and landmarks; screen-reader names for icon controls; non-color status meaning. Modal focus remains contained and returns to the trigger; charts have an equivalent data table or text summary.
6. Every interactive element has an accessible name and correct semantic element; no nested anchor/button controls. No secrets, user-entered document/question/answer/article text, emails, tokens or full URLs are emitted into telemetry.
7. Capture approved screenshots for mobile/tablet/desktop and the highest-risk states in the acceptance evidence; run meaningful role/API contract/browser tests for the functional slice. Test fixture includes actual empty data and failures, not only seeded happy paths. Accessibility findings and residual visual deviations are resolved or explicitly bounded.
