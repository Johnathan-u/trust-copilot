# TC-06-BUG-001 Cross-workspace foreign keys on evidence, exports, and gaps

Status: reported. No backfill and no data repair in TC-25-011.

This is a tenant-isolation defect in the schema. A workspace-scoped row can store the primary key of a document, questionnaire, question, or answer that belongs to another workspace. The foreign key checks that the target id exists. It does not check that the target's workspace is the same as the row's workspace.

`demo_proof_summaries` is not part of this defect. Its `workspace_id` and `created_by_user_id` foreign keys reject unknown ids. That is covered by `test_foreign_keys_reject_unknown_workspace_and_user`.

TC-25-011 leaves these rows in place and leaves them out of proof counts. It does not null them and it does not rewrite them.

## How a cross-workspace reference is possible

`questions` and `answers` have no `workspace_id`. A question belongs to a questionnaire, and an answer belongs to a question. Workspace is known only by joining to `questionnaires.workspace_id`.

| Table | Column | Constraint | Why another workspace can be referenced |
| --- | --- | --- | --- |
| `evidence_items` | `document_id` | `evidence_items_document_id_fkey` references `documents(id)` on delete set null | `documents.workspace_id` is a separate column. Nothing requires it to equal `evidence_items.workspace_id`. |
| `export_records` | `questionnaire_id` | `export_records_questionnaire_id_fkey` references `questionnaires(id)` on delete set null | `questionnaires.workspace_id` is not part of the foreign key. |
| `evidence_gaps` | `questionnaire_id` | `evidence_gaps_questionnaire_id_fkey` references `questionnaires(id)` on delete set null | Same gap as exports: the questionnaire id is not tied to `evidence_gaps.workspace_id`. |
| `evidence_gaps` | `question_id` | `evidence_gaps_question_id_fkey` references `questions(id)` on delete set null | The question's questionnaire can belong to a different workspace. The foreign key does not join that far. |
| `evidence_gaps` | `answer_id` | `evidence_gaps_answer_id_fkey` references `answers(id)` on delete set null | The answer's question's questionnaire can belong to a different workspace. The foreign key does not join that far. |

Deleting the parent sets the child column to null. That does not stop the insert of another workspace's id.

## What exposed it

`apps/api/tests/release/test_domain_demo_proof.py::test_foreign_reference_partial_failure_excludes_other_workspace`

That test commits rows on PostgreSQL (`trustcopilot_test`) and then deletes the workspaces in cleanup. Workspace delete cascades, so the rows are gone after the test. The assertions that show the references were stored and then excluded:

- `evidence_items_stored` is 1. `exclusions.foreign_reference` on that metric is 2. One excluded evidence row points at a document in another workspace. The other points at a soft-deleted document in the same workspace. The same-workspace soft delete is not this defect.
- `exports_stored` and `exports_completed` are 1. One export row points at a questionnaire in another workspace and is reported as `foreign_reference_rejected`.
- `evidence_gaps_stored` is 0. The one gap row points at a question whose questionnaire is in another workspace.

The test does not set `evidence_gaps.questionnaire_id` or `evidence_gaps.answer_id`, so it inserts no cross-workspace values in those two columns.

### Rolled-back schema probe on `trustcopilot_test`

On 2026-10-27 a single transaction inserted one cross-workspace row for each of the five columns, ran the operator queries, and then rolled back. Inside the transaction each query returned 1. After `ROLLBACK` the standing census was 0 again. That shows the database accepts the reference. It does not leave a row behind, and it is not a production count.

## Read-only queries for production counts

Operators can run these against production. They return counts only. Do not add columns that hold ids, names, filenames, or other values to the select list.

```sql
SELECT COUNT(*) AS row_count
FROM evidence_items e
JOIN documents d ON d.id = e.document_id
WHERE d.workspace_id <> e.workspace_id;

SELECT COUNT(*) AS row_count
FROM export_records x
JOIN questionnaires q ON q.id = x.questionnaire_id
WHERE q.workspace_id <> x.workspace_id;

SELECT COUNT(*) AS row_count
FROM evidence_gaps g
JOIN questionnaires q ON q.id = g.questionnaire_id
WHERE q.workspace_id <> g.workspace_id;

SELECT COUNT(*) AS row_count
FROM evidence_gaps g
JOIN questions qs ON qs.id = g.question_id
JOIN questionnaires q ON q.id = qs.questionnaire_id
WHERE q.workspace_id <> g.workspace_id;

SELECT COUNT(*) AS row_count
FROM evidence_gaps g
JOIN answers a ON a.id = g.answer_id
JOIN questions qs ON qs.id = a.question_id
JOIN questionnaires q ON q.id = qs.questionnaire_id
WHERE q.workspace_id <> g.workspace_id;
```
