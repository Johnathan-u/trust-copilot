# TC-04-002 · Make verify, invite and reset tokens single-use and bounded

## Review follow-up on PR #280

This section does not accept the ticket and does not change the batch-4 verdict below to MEETS. The implementer does not mark TC-04-002 DONE.

Comments 6967410479 and 6974047713 on PR #280, and issue #85 comment 6974255416, asked for two changes. Both are in this branch, after merging master `af478a601a5df6ac49410711c77a14b014c70bf4`.

1. Timing oracle. `POST /api/auth/forgot-password` and `POST /api/auth/resend-verification` return before the provider is called, on a background session. A known address is not held open for the provider round-trip. `test_slow_reset_provider_does_not_delay_a_known_address` and `test_slow_verification_provider_does_not_delay_a_known_address` sleep 0.5s inside the provider. Against the synchronous send at `1229fb37`, those known-address calls took 0.510s and 0.511s. The unknown-address resend took 0.006s. On this tree both sides of each pair return in under 0.35s, and the reset token is stored only after the background send is accepted.
2. Verification and invite scope. A false or raised verification resend keeps the previous code and link and writes `auth.verification_send_failed`. A failed invite send leaves that invite's code redeemable (`test_failed_invite_send_leaves_the_code_usable`); invite creation still commits the row first, which `test_create_invite_succeeds_when_email_send_returns_false` requires. A second redeem of the same verification link or invite returns 400. Two in-flight redeems of one verification link, and of one invite, produce one 200 and one 400. Against `1229fb37` the resend cases failed, both verification redeems returned 200, and the invite pair returned 200 and 500 with `arrived=0`.

The mail-drain fixture used so tests can read a background send does not request `monkeypatch`. Push run 44274753210 failed at teardown because the previous fixture did. `tests/release/test_enqueue_consistency.py` then passed 45.

## Gaps
1. Treat a failed verification or reset send as recoverable. `_issue_verification` (`auth.py:307-310`) and the reset background thread (`auth.py:491-500`) ignore a false provider result after the new token is already the only live one. Keep the previous unused verification row until the send returns true, or return a retryable failure that does not say whether the address exists.
