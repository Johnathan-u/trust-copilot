## Assumptions

1. Create still defaults `published` to 1, including when the field is omitted. That default writes version 1. Gap 1 left the default in place, and the dashboard create does not send `published`. A draft is `published` other than 1.
2. A PATCH of title, content, slug, category, or `is_policy` without `published` changes the draft only. Readers keep the approved version. `published: 1` approves the draft. The dashboard sends `published: 1` when it saves an article that is already published, so that save updates what customers see and revokes the previous acknowledgment.
3. Unpublish keeps the version row and revokes acknowledgments. Publishing the same text again reuses that version. The old acknowledgment stays revoked, so the reader acknowledges again.
4. A repeat acknowledgment of the current version returns the original timestamp. A new version requires a new row.
5. `Idempotency-Key` uses the existing scoped claim (`app/core/idempotency.py` `scoped_key`, `claim`, `set` with `commit=False`). The same key and body replay the stored response. The same key and a different body are 422 and do not insert. No key still returns 400 for a duplicate slug. An in-progress key is 409.
6. A public read is an anonymous request, a list with `published_only`, or a get that names `workspace_id` (the trust centre does). A signed-in get without `workspace_id` returns the draft so the editor can save it.
7. A published row that has no version yet, because it was inserted outside this path, is still returned as its live columns. The migration backfills workspace-scoped published rows to version 1. A null workspace still has no version and is not returned. That is gap 1.
8. `GET /api/trust-articles/{id}` with no session and no `workspace_id` still returns a published article from any workspace. That was left as the existing public-by-id contract in the gap 1 note. This change does not alter it.
