### Missed in the first pass

At `69a5230`, `switch_workspace` (`apps/api/app/api/routes/auth.py:2254-2314`; the review cited `:2255-2314`) checked membership and suspension, then issued `member.role`. It never read the target workspace's `mfa_required`. Login applied that policy only to the lowest-id membership (`auth.py:946-950` is `order_by(WorkspaceMember.workspace_id).first()`; the review cited `:946-949`. `:1016-1020` is `policy_enrol` for that member). On `2aea83a` the same login query is `:1007-1011` and `policy_enrol` is `:1069-1073`, because helpers were inserted above it. Login still uses that lowest-id membership. `switchWorkspace` at `69a5230` (`apps/web/contexts/AuthContext.tsx:147-162`) copied the previous state and left `mfa_required_for_workspace` on the workspace the user had just left. A user with no factor could sign in to a workspace that did not require MFA, switch into one that did, and receive that workspace's role. The first pass missed this finding.

**TC-05-001c** closed it. That is PR #309, merged as `2aea83a64b1a936afc90da9e9793d0fcbb8c7de8`, and it is the P0 security child for this hole. On that head, `workspace_requires_unmet_mfa` yields the five-minute enrol-only cookie (`auth.py:2345-2385`). An enabled factor whose stored session is not `mfa_satisfied` gets `_mfa_challenge_response` and no cookie (`:2386-2391`). The client copies `mfa_required_for_workspace` from the switch body (`AuthContext.tsx:187-189`) and refreshes it from `/api/auth/me` (`:195-201`). The decision record is `docs/release/verification/TC-05-001c.md`. This report does not propose a duplicate child.
