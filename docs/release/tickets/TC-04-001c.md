# TC-04-001c: verification abuse, rollout sessions and verification web flow

Follow-up of TC-04-001. It collects the verification, rollout and web items that the independent reviews of #193 (heads `68ed30d`, `75cb6d7` and `138e047`) left as non-blocking. Provider and protocol hardening is in TC-04-001b.
Epic E04. 5 points, P1. Depends on TC-04-001. Branch: `tc/TC-04-001c-verification-rollout`.

## Acceptance criteria

1. Timing:
   - Duplicate registration takes the same time as a new registration.
   - Resend takes the same time whether or not an unverified account exists.
   - Neither reveals whether an address is registered.
2. Resend and lockout abuse:
   - A third party can't use up a victim's resends, or lock the victim's address or user id out of verification.
   - Neither limit weakens brute-force protection.
3. Sessions and links at rollout:
   - Sessions held by unverified accounts at deploy are ended.
   - Provider sign-in through an existing link refuses an unverified account, or verifies it only from a validated provider email.
   - A seed run that marks an existing row verified also resets its password.
4. Microsoft personal accounts:
   - An existing personal-account link, stored under the Graph `id`, either keeps working or gets a clear path back, not a bare 400.
   - The TC-04-001 release doc says the re-keyed link "stays on the same account" only for work accounts.
5. Web and docs:
   - `/verify-email` doesn't show "Missing verification link." above the code form when there is no token.
   - The TC-04-001 release doc says the e2e spec mocks the API, and lists OIDC `preferred_username` as outside TC-04-001.
   - The real mailed-link flow is exercised end to end at least once: a real mail sink, the page, then the API.
6. Each item has release tests that fail without the fix.

## Evidence and sign-off

CI on both events, plus an independent review. Under OD-14 no separate owner sign-off is needed.
