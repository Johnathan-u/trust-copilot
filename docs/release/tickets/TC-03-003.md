# TC-03-003 — Separate readiness, liveness and worker health

**Epic:** E03 Deployment and migrations · **Baseline:** `c20f949161ac12a619b396d30904448ffd74d532` (master `f72def3` merged in) · **Branch:** `tc/platform/TC-03-003`
**Evidence:** [`artifacts/acceptance/TC-03-003/`](../../../artifacts/acceptance/TC-03-003/README.md)
**Verification:** `cd apps/api && python -m pytest tests/release/test_health_probes.py -q` → 24 passed.

## Problem at baseline
* `/healthz` and `/readyz` were not cleanly separated: readiness checks had no time bound (a hanging DB/S3 call could hang the probe), and failure responses echoed raw exception text.
* `/workerz` reported only the DB heartbeat row without a staleness verdict; on heartbeat-store errors it returned `str(e)` (possible DSN/host leakage).
* The worker refreshed its heartbeat only between jobs, so a long-running healthy job looked dead, while a stalled loop could not be detected.
* The API image `HEALTHCHECK` did an HTTP GET; the worker service reuses that image and therefore **inherited an HTTP probe for a server it never runs** (always unhealthy).

## Behaviour after this ticket
| Endpoint | Purpose | Dependencies | Failure |
|---|---|---|---|
| `GET /healthz` | API **liveness** — the process serves requests | **none** (never touches DB/S3) | — (200 whenever the process is up) |
| `GET /readyz` | **readiness** — DB (`SELECT 1`) and object storage reachable | DB, S3/MinIO, each bounded by `READINESS_TIMEOUT_SEC` (default 3) via a thread pool | `503`, `checks: {database, storage}` each `ok`/`unavailable`/`timeout`; errors redacted to exception class; `ALERT_NOT_READY` log |
| `GET /workerz` | **worker health** from the heartbeat row | DB | `200` `status: ok` when age ≤ `WORKER_HEARTBEAT_STALE_SEC` (default 120); `503` `status: stale`, or `unknown` (redacted) if the store is unreachable. Adds `last_seen_age_sec`, `stale_after_sec` (additive fields; existing fields kept) |

**Worker heartbeat** (`app/worker_health.py`, started from `app/worker.py:main`): a daemon `HeartbeatThread` beats every `WORKER_HEARTBEAT_INTERVAL_SEC` (15) — upserts `worker_heartbeat` (`INSERT … ON CONFLICT`) and touches `WORKER_HEARTBEAT_FILE` (`/tmp/trustcopilot-worker.heartbeat`). It keeps beating while a healthy job runs, but **withholds** the beat if the claim loop has not ticked for `WORKER_LOOP_STALL_SEC` (120) or the current job exceeds `WORKER_JOB_MAX_RUNTIME_SEC` (3600). A DB write failure is logged and does not kill the thread (the file beat continues).

**Container probes** (`python -m app.probe [api|worker]`, role from arg or `TC_PROCESS_ROLE`): `api` → loopback `GET /healthz`; `worker` → heartbeat-file freshness, **no HTTP**; unknown role → unhealthy. API `Dockerfile`: `ENV TC_PROCESS_ROLE=api`, `HEALTHCHECK … python -m app.probe` (start-period 60 s). `docker-compose.yml` and `docker-compose.prod.yml` worker services: `healthcheck: python -m app.probe worker`.

Configuration is documented in `.env.example` (all optional, defaults shown above).

## Runbook
* Orchestrator liveness → `/healthz` (restart only if this fails). Load-balancer/rollout readiness → `/readyz`. Worker alerting → `/workerz` (via API) or the worker container's own health status.
* A worker reported `stale` while its container is running means the claim loop stalled or a job exceeded `WORKER_JOB_MAX_RUNTIME_SEC`; inspect worker logs before restarting.

## Decisions / ambiguities (resolved conservatively)
1. `infra/caddy/Caddyfile.production` unchanged — it already proxies `/healthz`, `/readyz`, `/workerz`.
2. `.github/workflows/deploy.yml` and `apps/api/docker-entrypoint.sh` unchanged — no deploy behaviour change was needed; deploy-time readiness gating is left to the deploy tickets.
3. No migration: the existing `worker_heartbeat` table is reused (no persisted-state change, so no rollback evidence is needed).
4. Response changes are additive (`checks`, `status`, `last_seen_age_sec`, `stale_after_sec`); error text is redacted to the exception class name.
5. The heartbeat file lives in `/tmp` inside the worker container (not shared); it is only a local probe signal. `/workerz` remains the cross-process source of truth.
6. `apps/web/Dockerfile` unchanged (web has its own HTTP healthcheck in compose).
