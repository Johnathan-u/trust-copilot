# TC-21-002 Legacy and canonical control contract reconciliation

**Status:** implemented. Framework catalogs stay **BLOCKED** pending **TC-01-007**. This ticket does not add framework control text.

The legacy routes in `apps/api/app/api/routes/controls.py` and the compliance routes in `apps/api/app/api/routes/compliance_controls.py` keep their existing request and response fields. Agreement is an additive `canonical` object, `control-contract/v1`.

## Canonical object

Both list and write responses include:

| Field | Meaning |
| --- | --- |
| `contract_version` | `control-contract/v1` |
| `id` | `framework:control_id` for the shared identity |
| `version` | Always null. Not a licensed catalog version. |
| `content_version` | Always null while TC-01-007 is open. The column is only a slot. |
| `owner_user_id` | Workspace member, or null |
| `owner_team` | Free text, or null |
| `lifecycle` | `not_implemented`, `in_progress`, `implemented`, or `verified` |
| `status_aligned` | False only when both stored lifecycle columns are set and differ |
| `evidence` | `control-evidence/v1` counts and the mirror flag |

Lifecycle is the workspace vocabulary. The legacy `status` column stays `implemented`, `in_review`, or `na`. `verified` is stored as lifecycle `verified` and projected to legacy status `implemented`, because that column has no verified value. The `lifecycle` field is the one status both routes return.

A paired read uses the workspace row's lifecycle when the stored columns differ. GET does not rewrite the drifted column. The next edit writes both columns to the same lifecycle.

## Routes

Legacy, mounted at `/api/controls`:

- `GET /` and `GET ""` require review and do not write
- `POST /`, `PATCH /{id}`, `DELETE /{id}` require admin
- `GET /{id}/evidence` requires review and does not write
- `POST /{id}/evidence` and `DELETE /{id}/evidence/{evidence_id}` require admin

Compliance create, patch, accept-suggested, link, and unlink require admin. Verify and set-evidence-verified require review. `GET` and suggest-evidence require review and suggest-evidence does not persist. These are the permission levels from before this ticket. No acceptance criterion widens them.

A control or evidence target in another workspace is 404. An owner who is not a member of the workspace is 404. Creating an identity that already exists returns 409 `control_identity_conflict` when the lifecycle, owner, or name would change. That request does not update the row. A display-name change does not move the canonical key, so creating the old identity again is that conflict and does not reset the lifecycle. A repeat with the same lifecycle, owner, and name returns the existing row and does not change it, which lets a contract-event retry finish. PATCH and verify are the routes that change lifecycle. Repeating an evidence target reuses the link and finishes the canonical mirror.

Legacy `POST /api/controls/{id}/evidence` mirrors every accepted target onto the paired compliance control, not only documents. A document reuses or creates an `evidence_items` row with source `document`. A trust article or an export record is mirrored as a manual evidence item. The legacy `control_evidence` row stores `evidence_item_id`, and the compliance side stores a `control_evidence_links` row. If that mirror hits a foreign-key failure, the legacy link stays and the response is `control_evidence_partial_failure` (`control-contract-error/v1`, retryable). The retry does not insert a second legacy link.

The reverse direction uses the same `evidence_item_id`. A compliance `POST /{id}/evidence`, accept-suggested, Slack or Gmail suggestion approval, and remediation evidence each write a `control_evidence` row on the paired legacy control when that pair exists. A repeat reuses the row. Compliance `DELETE /{id}/evidence/{link_id}` deletes that legacy row. `GET /api/controls/{id}/evidence` and `GET /api/compliance/controls/{id}/evidence` then list the same evidence items. `canonical.evidence.mirrored` is true when the two counts match and every legacy row has an `evidence_item_id`. The response fields on both evidence routes are unchanged.

## Remediation status

`POST /api/remediation/tickets/{id}/evidence` still attaches the given evidence items and mirrors each one onto the paired legacy control. `bump_control_to` is optional. Null leaves the control status unchanged. Any other value must be a workspace control status other than `verified`: `not_implemented`, `in_progress`, or `implemented`. An unknown value is HTTP 400 `invalid_control_status`. `verified` is HTTP 400 `verified_status_not_allowed`. This route never sets a control to verified and never writes `verified_at`. Omitting `bump_control_to` defaults to `implemented`, and that default does not demote a control that is already verified: its status and verification stamps stay. A bump to `not_implemented` or `in_progress` does leave `verified`, and then both `verified_at` and `verified_by_user_id` are cleared. Evidence links and the legacy mirror are written first, then `sync_workspace_row` copies the lifecycle, and the request commits once. A failure before that commit leaves the ticket, the links, and the control unchanged. A permitted bump makes compliance `status`, `canonical.lifecycle`, and the legacy status projection agree, and `status_aligned` is true. The sync keeps a stored canonical key. A compliance display name is not treated as a new identity, so a legacy framework and control id stay in place. An unknown or `verified` value writes nothing.

A contract-event foreign-key failure after the pair is saved returns `control_contract_partial_failure`. The control stays. The retry writes the event and returns the same row.

Deleting a legacy control also deletes the paired compliance row when that row has no evidence links. Otherwise the compliance row remains the only copy.

## Migration

`tc21002_control_contract` revises `tc06001_same_workspace_refs`. It adds nullable columns and `control_contract_events`. It does not rewrite existing status values and does not insert framework rows. Downgrade drops only those additions.

## UI

`apps/web/lib/controlContract.ts` reads the nested object. It rejects a non-null version. The same reader accepts a legacy payload and a compliance payload.

## Ambiguities

- Canonical lifecycle uses the compliance vocabulary. Legacy `status` is unchanged as a stored projection.
- `version` and `content_version` are forced null in responses. Writes clear the slot. No licensed version is accepted on the request.
- GET reports the workspace lifecycle for a drifted pair and does not repair it.
- Historical rows are not backfilled.
- A compliance control with no framework control uses the label `custom` plus the custom name. No catalog text is copied into a new description.
- `verified` projects to legacy `implemented`. Remediation evidence cannot set `verified`.
- Delete removes the compliance pair only when it has no evidence links.
- Suggest-evidence stays a non-persistent review route.
- `rights_are_cleared()` was removed because nothing called it. The rights gate remains the catalog paths that already return blocked.
