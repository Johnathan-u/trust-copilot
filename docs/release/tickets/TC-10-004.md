# TC-10-004 Cancellation and audited manual retry

**Status:** implemented. No migration. `jobs.status` is an unconstrained string, and `cancelled` was already one of its values. The actor, the prior error, and the prior attempt are stored on `audit_events`, not on new columns.

An admin cancels or retries a job in their own workspace. Anyone else gets 403. A job that is not in that workspace, or a workspace id that is not the caller's, is 404 with `Job not found`.

## Cancel

`POST /api/jobs/{id}/cancel?workspace_id=`

The row is locked. Queued, running, and retrying (`queued` with `next_attempt_at`) become `cancelled`. The lease and `next_attempt_at` are cleared so a claim and lease recovery no longer see the row. `completed_at` is set. An existing `error` and `error_code` are kept. If there was no error code, the row stores `cancelled` and `Cancelled before the job finished.`

One `job.cancelled` audit is written. It includes `actor_user_id`, `prior_status`, `prior_error_code`, `prior_error`, and `prior_attempt`.

A second cancel of a job that is already cancelled returns the same job and does not write another audit. A completed or failed job is 409 `job_not_cancellable` and is not changed. The body is the usual `{"detail", "error"}` envelope. `error.retryable` is false.

A running worker that still holds the job finds, at the heartbeat or at the commit, that the lease is gone. It does not write a result, a completion, a retry, or a failure. Lease recovery locks only `running` rows, so it cannot put a cancelled job back to `queued`. Enqueue of the same idempotency key creates a new job. It does not reopen the cancelled row.

## Manual retry

`POST /api/jobs/{id}/retry?workspace_id=`

Allowed only when the status is `failed` or `cancelled`. Anything else is 409 `job_not_retryable`. The same job row goes back to `queued` with `attempt` 0, so the next claim is attempt 1. The audit `job.manual_retry` keeps `actor_user_id`, `prior_error_code`, `prior_error`, `prior_attempt`, and `prior_status`. While the failed or cancelled row is locked, a retry is refused when any other queued or running job in the same workspace and kind already has that idempotency key. The response is 409 `idempotency_conflict` and the row is unchanged. That covers a running copy, which the queued-only unique index does not.

## Runbook

* **Stop a queued, running, or retrying job.** An admin calls `POST /api/jobs/{id}/cancel?workspace_id=`. The status becomes `cancelled`. A later worker completion does not overwrite it. Repeat the call if you are not sure; a second cancel does not add another audit.
* **The job is already completed or failed.** Cancel returns 409. Leave it, or use manual retry when the status is failed.
* **Run a failed or cancelled job again.** An admin calls `POST /api/jobs/{id}/retry?workspace_id=`. The audit records who did it and which attempt and error they retried. The worker then claims it as a new attempt.
* **403.** The caller is signed in and is not an admin.
* **404 `Job not found`.** The job is not in the caller's workspace.

No new configuration.
