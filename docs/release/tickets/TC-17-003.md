# TC-17-003: Configurable evidence-backed public security claims

**Epic:** E17 Trust center public sharing and NDA · **Status:** implemented, in review · **Branch:** `claude/TC-17-003-security-claims`
**Evidence:** `artifacts/acceptance/TC-17-003/`
**Verification:** `cd apps/api && python -m pytest tests/release/test_domain_security_page.py -q`

## Problem at baseline

`GET /api/security-page` hardcoded every assertion in `security_page_service.py`: three certification statuses, the encryption/backup lines, the security contact address `security@trustcopilot.io`, and the DPA and subprocessor flags. An owner could not approve a claim, attach proof, or change the contact, and nothing tied a claim to evidence.

## Behaviour after this ticket

### AC1: owner-approved configuration and proof references

- New table `security_claims` (migration `tc17003_security_claims`, parent `tc23001_deal_types`): one row per workspace and claim key holding the latest owner decision (`not_claimed` | `claimed`), the public statement or value, an optional proof `evidence_item_id`, and who decided it and when. Constraints: unique `(workspace_id, claim_key)`, status check, `revision >= 1`, and a `claimed` row must carry `decided_at`.
- Claim catalogue (`CATALOGUE` in the service): `soc2_type2`, `gdpr`, `iso27001` (certifications); `encryption_at_rest`, `encryption_in_transit`, `backups` (infrastructure); `dpa`, `subprocessor_list`, `security_contact` (contact). Unknown keys return 404.
- Every claim except `security_contact` needs proof: **current** evidence under the codebase's single rule (`compliance_coverage._evidence_is_current`). That means same workspace, approved, its document (if any) present and not deleted, and no expired metadata. `security_contact` is an owner-approved email address.
- A claim is shown as attested or verified **only at read time, while its proof is still valid**. Otherwise the page shows the same conservative wording as before ("not attested", "Deployment-dependent, not yet verified: …"). The contact email is `null` until the owner approves one. No address or attestation is hardcoded.
- `GET /api/security-page` keeps every previous key (title, subtitle, sections, notice, certifications, infrastructure_highlights, contact). It adds `schema_version: 2`, a `proof` reference on each certification, and a `claims` list with `verified` and `reason` (`verified`, `not_claimed`, `proof_unavailable`, `value_unavailable`).
- Admin API: `GET /api/security-page/claims` and `PUT /api/security-page/claims/{key}` with body `{status, statement?, value?, evidence_item_id?, expected_revision}`. Both need `can_admin` with a current, unsuspended membership (re-read under lock, as in the FAQ routes). The PUT also needs a signed-in person: API keys can't decide claims. Each change writes an `audit_events` row (`security_claim.claimed` / `security_claim.not_claimed`).

### AC2: positive, negative and partial-failure cases on real PostgreSQL

`tests/release/test_domain_security_page.py` runs against the CI PostgreSQL database with synthetic workspaces, users and evidence, and exact cleanup:

- **Positive:** an approved claim with proof is attested and records the decider and audit row. An infrastructure claim replaces the unverified wording. An owner-set security contact is shown.
- **Negative:** evidence that is foreign, unapproved or missing is rejected with one identical message, and nothing is written. A proof-required claim without proof gets 422. An invalid email gets 422. An unknown key gets 404. Editors and reviewers get 403 on list and decide, while the public page still works for them. Unauthenticated requests get 401.
- **Foreign references:** claims never leak to another workspace. A row pointing at another workspace's evidence (inserted directly) is reported as `proof_unavailable`, never attested.
- **Partial failure:** if proof is later un-approved, its document soft-deleted or its evidence expired, the page falls back to "not attested" and keeps the decision. If proof is deleted, the FK sets `evidence_item_id` to NULL and the claim stays unverified. A failure after the claim and audit rows are flushed rolls both back: 409, no revision bump, no audit row.
- **Database guards:** an invalid status, `claimed` without `decided_at`, and a duplicate key are all rejected by PostgreSQL.
- **Permissions:** API keys and suspended admins can't decide claims.
- **Rollback:** a real `alembic downgrade tc23001_deal_types` then `upgrade head`, with data present, archives both claims. It restores the in-scope claim unchanged, and the claim whose proof moved to another workspace comes back with `evidence_item_id` NULL.

### AC3: schema, consumer and persisted outcome agree across restart and retry

- **Retry:** resending the same PUT with the same `expected_revision` returns the stored decision unchanged (no second revision, no second audit row). A different change on a stale revision gets 409. Withdrawing with the current revision bumps the revision and clears the proof.
- **Restart:** the API response equals the page built from a fresh database session. The admin listing shows the persisted revision and proof.
- **UI consumer:** see the web page added under `apps/web/app/dashboard/security-page/`. It reads the same response and shows only verified claims as attested.

## Migration and rollback

Upgrade creates the table, with no backfill: all workspaces start with no claims, which the page shows exactly as before. Downgrade copies every row into `tc17003_security_claim_archive` (no FKs) and drops the table. Re-upgrade restores archived rows whose workspace still exists. Proof and decider references that no longer resolve inside the same workspace come back as NULL. A fully restored archive is dropped, and the round trip is tested with data (see AC2).

## Limits

- No live provider calls and no new dependencies.
- Verification is "approved evidence in this workspace". It doesn't check what the document actually says; that stays the owner's responsibility when approving the claim.
