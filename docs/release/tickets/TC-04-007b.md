## Problem

The default limiter was the per-process memory store. Production without `REDIS_URL` still used it. Login, reset, resend, and invite 429 responses did not send `Retry-After`. Invite creation was not limited. `apps/api/tests/release/test_auth_rate_limits.py` was not in the tree, and `docs/release/tickets/TC-04-007.md` did not exist.

## Behaviour

`REDIS_URL` still selects the existing Redis backend. Its `INCR` and `EXPIRE` calls are unchanged. When `REDIS_URL` is unset, including in production, `app.core.rate_limit` uses the `rate_limit_buckets` table. Each key is one row: `attempt_count` and `window_started`. The window is fixed. It starts on the first attempt and does not slide. A later attempt inside the window increments the count. An attempt at or after `window_sec` starts a new window at 1. The row is committed on its own connection, so a request that later rolls back still counts, and another process reading the same database sees it.

A key longer than 512 characters is stored as `sha256:` plus the hex digest of the key. Auth keys in this tree are shorter than that.

Store errors still fail open, except callers that pass `fail_closed`. `POST /api/workspaces` in production still fails closed with 503 and `Retry-After`. The in-memory class remains in the module and is not selected.

`Retry-After` is a whole number of seconds, at least 1, and at most the window. It is the time left in the window that tripped. These 429 responses send it. The response body text is unchanged.

| Route | Limit | Window | Keys |
|---|---|---|---|
| `POST /api/auth/login` | 10 | 60s | `login:ip`, then `login:email` |
| `POST /api/auth/forgot-password` | 10 | 60s | `reset:ip` |
| `POST /api/auth/reset-password` | 10 | 60s | `reset_password:ip` |
| `POST /api/auth/resend-verification` | 3, then 429 | 900s | `resend-verify:ip` and `resend-verify:email` |
| `POST /api/auth/verify-invite-code` | 10 | 900s | `invite_verify:{ip}:{email}` |
| `POST /api/members/invites` | 10 | 60s | `invite_create:workspace:{id}` and `invite_create:user:{id}` |

Login checks the IP key first. Forgot-password still refuses when `reset:ip` is already at the cap, then records the attempt, then loads the user. A known address and an unknown address still return the same generic 200 body ten times, then the same 429 body. `reset:ip` is still recorded before the lookup. Resend still records both keys before the lookup. The header on that 429 is the longer of the two remaining windows.

Invite creation is limited only after the email, role, membership, duplicate, and grant checks have passed. An invalid email, an existing member, or a duplicate invite does not consume the window. The eleventh new invite in the window is 429 `Too many invites. Try again later.` with `Retry-After`, and no invite row is inserted. Either the user key or the workspace key is enough to refuse.

Other auth 429 responses (verification lockout, change-password, OAuth callbacks, MFA) are unchanged and do not gain `Retry-After` in this child.

## Design

The shared store is PostgreSQL, which every deployment already runs. Redis remains optional and is used only when `REDIS_URL` is set. No new service is required. The deploy contract in `docs/release/config-contract.md` now says an unset `REDIS_URL` uses `rate_limit_buckets`.

The check does not increment. `record_attempt` does. That split is the same as before, so the existing caps stay: ten login or reset attempts are allowed, and the next one is 429; resend allows three and the fourth is 429; invite verification allows ten failures and the eleventh is 429.

## Migration

**Required.** `tc04007b_rate_buckets` revises `tc12004a_answer_revisions`, the single Alembic head on master when this branch was cut. Upgrade creates `rate_limit_buckets` (`bucket_key` primary key, `attempt_count`, `window_started`). Existing deploys start with an empty table, so open in-memory windows do not carry over. The revision id is 21 characters and fits `alembic_version.version_num` (`varchar(32)`). The revision does not import the application package.

Downgrade drops the table. In-flight counts are discarded. A caller that was limited can try again until the new window fills. Re-upgrade does not restore the dropped counts.

## Acceptance criteria

1. **AC1.** With `REDIS_URL` unset, a counter recorded in one process is visible to another process on the same database. Redis is still selected when `REDIS_URL` is set.
2. **AC2.** Login, forgot-password, reset-password, resend-verification, invite verification, and invite creation 429 responses include `Retry-After`. The 429 body text is unchanged.
3. **AC3.** Invite creation is limited to 10 new invites per 60 seconds for the acting user and for the workspace. The eleventh new invite is 429 and inserts no row.
4. **AC4.** `apps/api/tests/release/test_auth_rate_limits.py` fails on the unfixed handler and passes after this change. The backlog command is `python -m pytest tests/release/test_auth_rate_limits.py -q`.
5. **AC5.** TC-04-007a stays in place: eleven forgot-password requests for a known address and eleven for an unknown address, each from an empty `reset:ip` window, are ten generic 200 responses and then one 429, and `reset:ip` is recorded before the user lookup.
6. **AC6.** `docs/release/tickets/TC-04-007.md` records the parent behaviour. This file's Behaviour section is the child record.
