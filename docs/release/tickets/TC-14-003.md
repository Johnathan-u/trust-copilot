# TC-14-003 — Dialog focus and accessible notifications

## Behavior

`Dialog` is the shared modal primitive, used only for real dialogs. Opening it moves focus inside, Tab and Shift+Tab stay inside, Escape closes it, and focus returns to the control that opened it. The rest of the page is `inert` and `aria-hidden` while it is open. The dialog is named by its title (`aria-labelledby`) and, when copy is provided, described by that copy (`aria-describedby`).

Destructive confirms use `role="alertdialog"` and move the first focus to Cancel. `window.confirm` on the dashboard card, alert rule, session, Slack, Gmail and trust-article deletes uses that confirm. Registry delete and bulk delete, and the member danger/warning confirms, use the same role.

Incoming Trust request navigation no longer uses `window.confirm`. A plain click or keyboard activation on a link, while a reply is unsaved, opens an alertdialog named "Leave this page?" and described by "Unsaved reply text will be discarded." Cancel is focused first. Tab from the last control wraps to Close. Escape closes it and returns focus to the link without navigating. "Discard and leave" closes the dialog, then follows the link after the page is no longer `inert`. Choosing another request while a reply is unsaved opens an alertdialog named "Discard unsaved reply text?" "Discard and open" switches the request. The PostgreSQL browser acceptance clicks that button; it does not accept a native confirm. Closing the browser tab still uses the platform `beforeunload` prompt, which cannot be replaced by an in-page dialog. Modifier clicks (Ctrl, Meta, Shift, Alt) are left to the browser.

`placement="drawer-start"` and `placement="drawer-end"` are part of the same primitive. The mobile navigation drawer uses `placement="drawer-start"`.

The notifications panel is a disclosure popover, not a dialog. It does not trap focus and does not mark the page inert. The bell has `aria-expanded` and `aria-controls` pointing at the panel. Escape and a click outside the panel close it and return focus to the bell.

Toasts use one mounted `role="status"` region (`aria-live="polite"`) for success, info and warning, and one mounted `role="alert"` region (`aria-live="assertive"`) for errors. A toast does not create its own live region and does not take focus. The dismiss control is a button. `Toast` owns the dismiss timer. Success, info and warning leave after 4000ms. A toast that renders an action button (Undo, View, Retry, or any control other than dismiss) does not auto-dismiss. The timer is omitted rather than paused on hover or focus, so the action has no time limit (WCAG 2.2.1 Timing Adjustable). Errors stay until dismissed. `prefers-reduced-motion: reduce` drops the toast opacity transition and does not change the timer. `apiErrorAnnouncement()` keeps `formatApiErrorDetail` and maps a failure onto that persistent error announcement.

Errors shown inside a dialog, rather than as a toast, use `role="alert"` and stay until the next attempt clears them. They do not take focus. The vendor-request result dialog mounts its `role="status"` region empty with the dialog, then puts the outcome text into that same region, and exposes the one-time-link warning as the dialog description.

Dashboard status and error text outside dialogs is announced too. Password errors, MFA errors, notification preference and rule errors, document and questionnaire list errors, answer-evidence errors, and proof-chain errors use `role="alert"`. Password success and the workspace security "Saved" message use a `role="status"` region that is already mounted, and they are not cleared by a timer. The answer-evidence and proof-chain errors use the existing danger text token.
