## What 038a and 038b already do

`GET /api/jobs` lists persisted jobs for the session workspace, newest first, with a descending id cursor. Reads use `require_can_review`. Cancel and retry stay on the existing admin routes. The history projection returns lifecycle fields, a safe typed error, charge uncertainty, an outcome of `already_applied`, `reconciled` or `superseded`, and a current document or questionnaire reference. It does not return raw payload, raw result, storage keys or provider text.

`/dashboard/jobs` reads that endpoint for the current workspace, page size 25, and keeps the cursor in the URL. Reload reads the server again. The page shows questionnaire parsing, evidence parsing, document indexing, answer generation and export. Review permission reads; admin permission cancels and retries, after confirmation. Loading, empty, denied, invalid cursor, unknown, not-found detail, failure, partial and success stay distinct. There is no editable draft, so there is no unsaved-change prompt. Direct navigation by someone without `can_review` shows "Job access is restricted" and does not call the jobs API (`apps/web/app/dashboard/jobs/page.tsx` around the `can_review` check).

## AC3 — owner and viewer

Neither role exists in the current principal model. No owner or viewer case was added to `apps/web/e2e/release/screen-jobs.spec.ts` or `apps/api/tests/release/test_job_history.py`. Inventing a permission mapping would decide the coordinator's ruling.

Built-in roles are only `admin`, `editor` and `reviewer`:

- `apps/api/app/core/roles.py:6-12` defines `Role` and `BUILTIN_ROLES` as those three names.
- `apps/api/app/core/roles.py:14-18` is the only built-in permission table. `can_review` (`:36-37`) is true for admin, editor and reviewer. `can_admin` (`:40-41`) is true for admin only. There is no owner or viewer branch.
- `apps/api/app/api/routes/members.py:64-78` accepts a built-in name or an existing custom-role name for this workspace. `:642-644` rejects an API-key role other than `editor`, `reviewer` or `admin`. `:785-788` lists built-ins only from `BUILTIN_PERMISSIONS`.
- `apps/web/app/dashboard/members/page.tsx:76` sets `BUILTIN_ROLES` to `admin`, `editor`, `reviewer`. The member role control (`:549-561`) and the invite control (`:918-928`) offer `allRoleNames` (`:217-218`): the roles API when it has loaded, otherwise that same list.
- `apps/api/app/models/user.py:35` stores `workspace_members.role` as a 32-character string. It is not an owner/viewer enum.
- `GET /api/auth/me` (`apps/api/app/api/routes/auth.py:1858-1867`) returns the membership `role` string and `permissions` from `_permissions` (`:1738-1761`): the four flags for a built-in role, the same four flags from a `CustomRole` row, or all false. The session cookie (`apps/api/app/core/session.py:154-171`) carries that role string. It has no owner or viewer field.
- `apps/web/contexts/AuthContext.tsx:40-65` keeps `workspace.role` and `can_edit`, `can_review`, `can_admin`, `can_export`. Workspace switch (`:157-160`) derives those flags only from `admin`, `editor` and `reviewer`.
- Settings (`apps/web/app/dashboard/settings/page.tsx:232-237`) gates administration with `permissions.can_admin`. It does not read an owner or viewer role.

`docs/planning/PRODUCT_SPEC.md:49` describes owner and viewer as roles to introduce later through a tested migration. That sentence is the planned suite, not a role the running app assigns.

A custom role may be given any non-built-in name, including the strings `owner` or `viewer`, with whatever flags the creator sets (`members.py:807-829`). Those strings are not defined roles, and their flags are not fixed. Mapping either name onto job access would invent the contract. Job reads follow `can_review`. Job cancel and retry follow `can_admin`. Admin, editor and reviewer already have `can_review`. Only admin has `can_admin`. A principal whose custom role has `can_review` false is denied, which the existing `custom-denied` browser case and the PostgreSQL permission matrix already cover.

## AC1 — progress

Answer generation already stores real `generated` and `total` counters on `job.result` (`apps/api/app/services/answer_generation.py:630-635`, written again at `apps/api/app/worker.py:612-620`). `GET /api/jobs` already projects those integers for `generate_answers` only (`apps/api/app/api/routes/jobs.py:172-180`). The consumer accepts them only for that kind (`apps/web/lib/job-history-consumer.ts:149-152`). The page renders "N of M answers generated" or "Progress not reported" (`apps/web/app/dashboard/jobs/page.tsx:73-88`).

No real progress counter is recorded for the other four kinds. Nothing was added to the projection or the consumer, and no progress number was fabricated.

- `parse_questionnaire` (`apps/api/app/worker.py:282-367`) writes a final question `count` into questionnaire `parse_metadata` and the questions effect (`:361-362`), and a reconcile outcome may include that count (`:345`). It does not write `generated`/`total` progress onto the job while it runs. A successful parse leaves `job.result` unset.
- `parse_evidence` is an empty branch (`apps/api/app/worker.py:809-810`). It records nothing.
- `index_document` (`apps/api/app/worker.py:490-550`) writes an outcome, not a progress pair. `index_document` returns an embedded-chunk count and stores `embedded` on the chunks effect (`apps/api/app/services/index_service.py:183-185` and `:217`). The worker does not copy that count onto `job.result`. A completion tally in the effect ledger is not a progress counter.
- `export` (`apps/api/app/worker.py:665-790`) stores `export_record_id` and `storage_key`, or an `already_applied` outcome (`:700-706`). It does not store `generated`/`total`.

`JobKind` (`apps/api/app/models/job.py:10-17`) is those five kinds. There is no sync kind and no sync job contract, so none was added.
