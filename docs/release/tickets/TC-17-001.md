# TC-17-001 — Trust article workspace on create and public read

Status: gap 1 is implemented on this branch and is waiting for independent review. This note does not accept the ticket and does not mark it done. No tracker edit. No migration.

Evidence: [artifacts/acceptance/TC-17-001/README.md](../../../artifacts/acceptance/TC-17-001/README.md). The route and the release test are `d2ca889bc8a1d03e4161011bd115143345babbde`.

Ruling: issue #85, 2026-11-18 15:54Z. Gap 1 from `docs/release/verification/TC-17-001.md`: no null-workspace published article. The other gaps in that report stay open.

## Gap 1

`POST /api/trust-articles/` used to store `body.workspace_id`. That value can be null, and `published` still defaults to 1. `GET /api/trust-articles/{id}` with no session returned the row whenever `published == 1`, including a row whose workspace is null.

### Create

The stored workspace is the session workspace. The body is not the source of the id.

- A body `workspace_id` that is null, omitted, or different from the session workspace is **400** with `workspace_id must match the current workspace`. Nothing is inserted.
- A body `workspace_id` equal to the session workspace is stored as that session id. The response shape is unchanged, and `published` still defaults to 1 when the body omits it.
- A session with no positive workspace id gets the same 400. This route will not insert an unscoped row.

400 is the status this route already uses when it will not accept a body (duplicate slug). 422 stays the schema-validation status. A null `workspace_id` is valid for the optional `int | None` field, so it is not a schema error. A conflicting id used to be 403. It is now 400, because the workspace is taken from the session and a different body value is a bad request.

The dashboard create already sends the current workspace id. The existing `tests/test_trust_articles_api.py` creates do too.

### Update and delete

`PATCH` accepts `workspace_id` only so a change can be rejected. The column is never written.

- A body `workspace_id` that is null or different from the article's workspace is 400 with the same detail. The row stays where it is.
- The same value as the article's workspace is ignored. Title and the other fields still update.
- Update and delete return 403 `Access denied` unless the article's workspace is the session workspace. A null workspace is not the caller's, so an existing null row can no longer be edited or deleted by a workspace admin. Another workspace was already 403.

A null-workspace policy cannot be acknowledged. The check was already `workspace_id != session workspace`, which is true when the article's workspace is null and the session has one. It now also rejects the case where both are null. Unpublish still does not delete acknowledgements. That is gap 2.

### Public read

List was already scoped. A signed-in caller sees the session workspace. An anonymous caller must pass `published_only` and a workspace id, and the query is `workspace_id ==` that id. Null does not match. The filter now also requires `workspace_id IS NOT NULL`.

`GET /api/trust-articles/{id}`:

- A row with a null workspace is 404 for every caller. The body is not returned.
- A signed-in caller still sees only their own workspace. Another workspace is 404.
- An anonymous caller still sees a published article that has a workspace. An unpublished article is 404.
- When that anonymous call names `workspace_id` (the public trust centre does, after `GET /api/workspaces/by-slug/{slug}`), the article must belong to that workspace. A different workspace is 404. The centre page at `apps/web/app/trust/[slug]/page.tsx` already sends this query.

`published` on the create model is still `published: int = 1`. Gap 1 does not change it. Acceptance criterion 1's "deliberate approved versions" is gap 2.

## Existing rows

No migration. A null-workspace row that is already `published = 1` stays in `trust_articles`. The read paths above do not return it, and create will not insert another. Update and delete of that row are 403.

A migration that unpublished or deleted those rows would change stored data. The verification said to prefer code-only exclusion, and to explain a migration rather than write one. Exclusion stops the public read and the new writes. Whether any existing null row should be unpublished or removed needs a separate ruling. `workspace_refs.py` already treats a null workspace as not visible to a signed-in workspace. Tests insert a null row on purpose and then delete it.

## Tests

From `apps/api`:

```sh
python -m pytest tests/release/test_domain_trust_articles.py -q
```

The file covers a null `workspace_id` on create, an omitted one, a body workspace that is not the session's, an anonymous read of a published null-workspace row, a public read that names another workspace, a normal create and read (including `published == 1` when the field is omitted), a patch that tries to move or clear the workspace, and update or delete of an existing null row.

`tests/test_trust_articles_api.py` is unchanged and still passes.

## Rollback

Revert this change. There is no schema change. After revert, create can store a null workspace again, an anonymous read returns that row when `published == 1`, and a workspace admin can edit or delete a null-workspace row.

## Still open

These are not part of this change.

1. **Gap 2.** There is still one `published` integer and one `content` column, no version id. `policy_acknowledgments` is still `(user_id, trust_article_id)`. A later edit leaves the acknowledgement. A repeat acknowledge returns the old timestamp. Unpublish does not revoke it. A second create of the same slug is still 400, not the same row.
2. **Anonymous get by id with no workspace.** `GET /api/trust-articles/{id}` with no session and no `workspace_id` still returns a published article from any workspace. That is the existing public-by-id contract (`tests/test_trust_articles_api.py` and the authority tests). The public list is scoped to a workspace, and a get that names a workspace is now scoped. Requiring a workspace or a trust-centre slug on every anonymous id read would change that contract. It is not required to hide a null workspace.
3. **Evidence labels.** `GET /api/controls/{id}/evidence` loads an attached article by id when it builds the label. Attaching already rejects a null or other-workspace article. A link that was stored earlier could still show that title to the control's workspace. This is not the public read.
4. **`published` default.** Left at 1. A create that does not send `published` still stores 1, including the normal path this change keeps. Turning that into an explicit unpublished draft belongs with gap 2.
