# TC-01-003a: replace PyMuPDF (AGPL) with pypdf (BSD-3-Clause)

Status: implemented on `tc/core/TC-01-003a`, based on `f72def3`. It implements owner decision
OD-2 ("replace with a permissive library", decided 2026-10-27, `docs/acceptance/release-decisions.md`)
and covers the engineering part of TC-01-003-AC2. TC-01-003-AC1 (a legally reviewed path for
**every** incompatible dependency), TC-01-004 (license inventory) and the manual evidence file
`docs/acceptance/license-resolution.md` stay with the Owner/seller and counsel. Per scope-freeze
R4 they are release gates (G0/G5), not engineering blockers. Evidence is in
`artifacts/acceptance/TC-01-003a/`.

## What changed
- `app/services/pdf_text.py` is the single PDF text interface. It is backed by **pypdf**, and
  nothing else imports a PDF library. `extract_page_texts(path)` returns the text of every page in
  page order, with `""` for pages without text; `require_text()` raises when no page has text.
  Explicit errors, all subclasses of `PdfTextError(ValueError)`. Each one's `str()` is a fixed,
  user-readable message with no file path, backend exception text or traceback; the internal cause
  is kept on `.detail` and logged server-side only:
  - `PdfNoTextError`: no text layer, for example an image-only scan. There is no OCR.
    Message: "This PDF has no text layer; OCR isn't supported. Upload a text-based PDF, DOCX or
    XLSX instead."
  - `PdfEncryptedError`: a user password is required. PDFs with only an owner password and an
    empty user password still open, as with PyMuPDF. Message: "PDF is encrypted or corrupt: it is
    password-protected. Upload an unencrypted copy."
  - `PdfUnreadableError`: not a PDF, damaged/truncated, or 0 readable pages. Message: "PDF is
    encrypted or corrupt: the file could not be read. Re-export it and upload it again."
- **pypdf is a hard import** (review follow-up). A missing library fails at import, which fails API
  startup (`app/main.py` imports `app.services.pdf_text` right after the DB bootstrap) and worker
  startup (`app/worker.py` imports the PDF parsers at module level). The per-request
  `PdfSupportUnavailableError` path was removed.
- `evidence_parser.parse_pdf` and `pdf_questionnaire_parser.parse_pdf_questionnaire` use that
  interface. Output shape, page numbers, `source_location` and confidence are unchanged.
- `scripts/generate_mock_docs.py` writes its PDF with the new pure-Python
  `app/services/synthetic_pdf.py` instead of PyMuPDF.
- `apps/api/pyproject.toml`: `pymupdf` was removed and `pypdf>=6.21.2,<7` was added. That file
  is the only dependency manifest, and pypdf has no required dependencies. AES-encrypted PDFs use
  the optional `cryptography` package, which is already a direct dependency.

## Behaviour differences vs PyMuPDF
1. **Table rows: same-line cells are joined with spaces.** pypdf emits text runs that share a
   baseline (table cells on one row) on one line, separated by a single space; PyMuPDF put each
   cell on its own line. Characters and offsets are otherwise identical: the evidence text with
   newlines replaced by spaces is byte-equal. For a table-style questionnaire PDF, the answer
   cells on the question's row now follow the question text, for example
   `do you encrypt backups at rest? yes no` where PyMuPDF gave `do you encrypt backups at rest`.
   Page, section, answer_type, source_location and confidence are unchanged. pdfplumber does the
   same thing. Approved for now by the Coordinator; **follow-up ticket TC-01-003b** (split
   same-line questionnaire table cells so answer-option cells are not appended to the question
   text; 2 pts; owner TC Core; scheduled after TC-11-001) is logged.
2. **PDF with no text layer** (image-only scan, vector-only drawing, whitespace-only text) now
   fails explicitly with `PdfNoTextError`, for both questionnaires and evidence:
   - questionnaire: the parse job is `failed` with the readable message, and the questionnaire is
     marked `status = "failed"` with `parse_metadata = {"count": 0, "error": <message>}`.
     PyMuPDF silently produced status `parsed` with 0 questions;
   - evidence: the index job is `failed` and the document is `failed` with
     `index_error = <message>`. It used to fail with the generic "Parse returned no content;
     document not indexed".
   A text PDF with no question-like lines still parses to 0 questions, as before.
3. **Truncated or damaged PDF that PyMuPDF opened as 0 pages** now raises `PdfUnreadableError`.
   Evidence indexing used to fail with "Parse returned no content", and a questionnaire silently
   parsed 0 questions.
4. **Exception types** for unreadable or password-protected PDFs are now the `PdfTextError`
   subclasses, replacing `pymupdf.FileDataError` and `ValueError("document closed or
   encrypted")`. Their messages are fixed and safe to show; before, the job error carried the
   library's exception text.
5. A missing backend fails at import/startup instead of returning nothing silently per request.

## How failures reach the user (review follow-up)
Both upload endpoints (`POST /api/questionnaires/upload`, `POST /api/documents/upload`) only store
the file and queue a job, so they return 200; PDF parsing never runs on a request thread and
cannot produce a 500. The worker records the failure:
- `GET /api/jobs/{id}`: `status = "failed"`, `error = <readable message>`;
- `GET /api/documents`: the document has `status = "failed"`, `index_error = <readable message>`
  (`index_service` also logs the failure and bumps the failure metric, like the no-content path);
- `GET /api/questionnaires/{id}`: `status = "failed"`, `parse_metadata.error = <readable message>`.
`tests/test_pdf_failure_surfacing.py` covers this end to end for image-only, password-protected,
corrupt and truncated PDFs on both paths (upload API, then the real `_process_one_job`, then the
status APIs), and asserts there is no traceback, path, temp dir or backend exception text.

Unchanged: the supported upload formats and extensions, page-numbering rules, and the
content-stream reading order of multi-column pages.

## Operator note
If a PDF job fails with "This PDF has no text layer; OCR isn't supported", the file is a scan.
Upload a text-bearing PDF, DOCX or XLSX instead. "PDF is encrypted or corrupt" means the file is
password-protected or damaged; the server log (`app.services.pdf_text`) has the internal cause.
