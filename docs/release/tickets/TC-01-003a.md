# TC-01-003a: replace PyMuPDF (AGPL) with pypdf (BSD-3-Clause)

Status: implemented on `tc/core/TC-01-003a`, based on `f72def3`. It implements owner decision
OD-2 ("replace with a permissive library", decided 2026-10-27, `docs/acceptance/release-decisions.md`)
and covers the engineering part of TC-01-003-AC2. TC-01-003-AC1 (a legally reviewed path for
**every** incompatible dependency), TC-01-004 (license inventory) and the manual evidence file
`docs/acceptance/license-resolution.md` stay with the Owner/seller and counsel. Per scope-freeze
R4 they are release gates (G0/G5), not engineering blockers. Evidence is in
`artifacts/acceptance/TC-01-003a/`.

## What changed
- `app/services/pdf_text.py` is the single PDF text interface. It is backed by **pypdf**, and
  nothing else imports a PDF library. `extract_page_texts(path)` returns the text of every page in
  page order, with `""` for pages without text. Explicit errors, all subclasses of `ValueError`:
  - `PdfUnreadableError`: not a PDF, damaged, or 0 readable pages;
  - `PdfEncryptedError`: a user password is required. PDFs with only an owner password and an
    empty user password still open, as with PyMuPDF;
  - `PdfNoTextError`: no text layer, for example an image-only scan. There is no OCR;
  - `PdfSupportUnavailableError` (`RuntimeError`): pypdf is missing. This used to be a silent
    empty result.
- `evidence_parser.parse_pdf` and `pdf_questionnaire_parser.parse_pdf_questionnaire` use that
  interface. Output shape, page numbers, `source_location` and confidence are unchanged.
- `scripts/generate_mock_docs.py` writes its PDF with the new pure-Python
  `app/services/synthetic_pdf.py` instead of PyMuPDF.
- `apps/api/pyproject.toml`: `pymupdf` was removed and `pypdf>=6.21.2,<7` was added. That file
  is the only dependency manifest, and pypdf has no required dependencies. AES-encrypted PDFs use
  the optional `cryptography` package, which is already a direct dependency.

## Behaviour differences vs PyMuPDF
1. **Table rows.** Text runs on the same baseline (table cells) are joined with one space instead
   of each cell going on its own line. Characters and offsets are otherwise identical: the
   evidence text with newlines replaced by spaces is byte-equal. For a table-style questionnaire
   PDF, any answer cells on the question's row now follow the question text, for example
   `do you encrypt backups at rest? yes no` where PyMuPDF gave `do you encrypt backups at rest`.
   Page, section, answer_type and confidence are unchanged. pdfplumber does the same thing.
2. **Questionnaire with no text layer.** The parse now fails explicitly with `PdfNoTextError`
   (the job is `failed` and the error text names OCR). PyMuPDF silently produced status
   `parsed` with 0 questions. A text PDF with no question-like lines still parses to 0
   questions, as before.
3. **Truncated or damaged PDF that PyMuPDF opened as 0 pages.** It now raises
   `PdfUnreadableError`. Evidence indexing used to fail with "Parse returned no content", and a
   questionnaire silently parsed 0 questions.
4. **Exception types** for unreadable or password-protected PDFs are now the `PdfTextError`
   subclasses, replacing `pymupdf.FileDataError` and `ValueError("document closed or
   encrypted")`. Callers already treat any exception as a failed job.
5. A missing backend now raises instead of returning nothing silently.

Unchanged: the supported upload formats and extensions, image-only evidence handling (`[]`,
after which `index_service` marks the document failed with "Parse returned no content"),
page-numbering rules, and the content-stream reading order of multi-column pages.

## Operator note
If a PDF questionnaire job fails with "PDF has no extractable text ... OCR is not supported", the
file is a scan. Upload a text-bearing PDF, DOCX or XLSX instead.
