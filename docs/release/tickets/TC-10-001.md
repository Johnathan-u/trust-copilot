# TC-10-001: Periodic leases and abandoned-job recovery

Status: implemented on `tc/core/TC-10-001`, merged with `master` `bff2c39`.
Evidence: [`artifacts/acceptance/TC-10-001/`](../../../artifacts/acceptance/TC-10-001/README.md) (filled after the local test run).

## What master did

`jobs` had no lease columns. The only heartbeat was the process row in `worker_heartbeat` (migration 026, TC-03-003): `/workerz` reads it, and `HeartbeatThread` refreshes it while a healthy job runs. That says the worker process is alive. It does not say which worker owns which job.

`claim_job` takes the next queued row with `SELECT ... FOR UPDATE SKIP LOCKED`, sets `status = running`, increments `attempt`, and commits. After that commit the row lock is gone. A second worker will not claim a `running` row, and nothing looks for a `running` row whose worker has died. The job stays `running` until a person intervenes. TC-10-002's runbook says this case is TC-10-001.

Retries (TC-10-002) and the side-effect ledger (TC-10-003) already make a second attempt safe. They never ran for a job stuck in `running`.

## Contract

A claimed job carries an owner token and an expiry.

| column | meaning |
|---|---|
| `jobs.lease_owner` | 32-hex token of the worker that holds the lease. NULL if unowned. Same construction as the idempotency owner token (TC-10-003b): `secrets.token_hex(16)`. |
| `jobs.lease_expires_at` | Naive UTC time the lease ends. NULL is not an expiry. |

* **Claim.** The existing `SELECT ... FOR UPDATE SKIP LOCKED` stays the claim. In that same locked update the worker sets `lease_owner` and `lease_expires_at = now + JOB_LEASE_SECONDS`. Two workers cannot both commit that update.
* **Heartbeat.** While the job runs, a daemon thread renews the lease with `UPDATE ... SET lease_expires_at = now() + interval WHERE id = :id AND lease_owner = :owner AND status = 'running' AND lease_expires_at > now() RETURNING id`. The database clock is the only clock. A stale token, or an already-expired lease, changes no row. The heartbeat is at most half the lease, so one missed beat does not drop it (defaults 15s and 60s).
* **Commit fence.** Every commit on the job's session, until the job is no longer running for this owner, locks the row and checks the same condition. If the owner has lost the lease, the commit is rolled back and `LeaseLost` is raised. The worker does not mark the job completed and does not schedule its own retry (the recoverer does that). It audits `job.lease_lost` with an 8-character prefix of the token, not the token.
* **Recovery.** Each claim loop locks one `running` row whose `lease_expires_at <= now()` (`FOR UPDATE SKIP LOCKED`), swaps in a new token, and classifies the failure in that same transaction. A second recoverer cannot write the row until the commit, and the status is no longer `running` by then. Classification is `_handle_job_failure` with `lease_expired`: the existing backoff and attempt cap. The attempt was already incremented at claim time; recovery does not increment it again. The event is audited as `job.abandoned` and as `job.retry_scheduled` or `job.failed`.
* **NULL lease.** A running job with `lease_owner` and `lease_expires_at` NULL is not recovered. Jobs that were already running when this revision is applied stay `running`. An operator fails one by the statements in the runbook below. Automatic grace-period recovery of those leftovers is backlog TC-10-001a (low), not this change.
* **Idempotency.** The HTTP idempotency owner token is unchanged. Job side effects still go through the TC-10-003 ledger, so a recovered attempt that already committed an effect does not apply it again. Enqueue dedupe still returns the queued job for the same key.

`lease_expired` is a retryable `jobs.error_code`. It is not an upstream body: the stored message is the one this worker wrote.

Answer generation commits draft answers as it goes. A lost lease rolls back only the transaction that is still open. Rows already committed stay. A later attempt does not write them again because of the effect ledger and the approved-answer guard (approved answers, and answers edited after the job was requested, are left as they are). The lease is not what undoes those partial writes.

No route docstring, summary, or description was changed.

## Configuration

| variable | default | clamp | notes |
|---|---|---|---|
| `JOB_LEASE_SECONDS` | `60` | `[10, 3600]` | Lease lifetime. An invalid value falls back to 60, then the clamp. |
| `JOB_LEASE_HEARTBEAT_SECONDS` | `15` | `[1, 1200]`, and at most half the lease | If `heartbeat * 2` would exceed the lease, the heartbeat becomes `lease // 2` so one missed beat still fits. |

The worker reads both on each claim and each heartbeat. `Settings.job_lease_seconds` and `Settings.job_lease_heartbeat_seconds` mirror them at process start. They are in `docs/release/config-contract.md`, `.env.example`, and `docker-compose.prod.yml`.

The process heartbeat (`WORKER_HEARTBEAT_INTERVAL_SEC` and `worker_heartbeat`) is a different control. It still answers "is the process alive?".

## Runbook

* **A job stays `running` and `lease_expires_at` is in the future.** The owner is still heartbeating. Nothing to do unless the job exceeds `WORKER_JOB_MAX_RUNTIME_SEC` (that withholds the process heartbeat; it does not by itself clear the job lease).
* **`running` and `lease_expires_at` is in the past.** The next worker loop recovers it. `error_code` becomes `lease_expired`. If attempts remain, `retry_scheduled` is true and `next_attempt_at` is the usual backoff. If the cap is spent, status is `failed` and `retries_exhausted` is true.
* **Repeated `lease_expired`.** The worker is dying or the heartbeat cannot reach the database before the lease ends. Raise `JOB_LEASE_SECONDS`, or fix the database, before raising the attempt cap. The cap is what stops a poison job.
* **`job.lease_lost` in the audit log.** That owner noticed it no longer held the lease and did not commit. The recoverer's `job.abandoned` event is the one that changed the job. The audit stores an 8-character prefix, not a token that can renew the lease.
* **A running job with a NULL lease after deploy.** It was claimed before this revision. Recovery does not take it. If the old worker is still in that process, leave the row alone. If that worker is gone, fail the specific job with the statements below. There is no jobs API that fails a running job, so this SQL is the operator path. It writes the same terminal columns the worker writes on `job.failed`, and it inserts the `job.failed` audit row in the same transaction. It does not send the in-app admin notification, and it does not change a document or questionnaire row.

  List them first. The ids below are synthetic; use the ids this query returns.

  ```sql
  SELECT id, kind, workspace_id, attempt, started_at, updated_at
  FROM jobs
  WHERE status = 'running'
    AND lease_owner IS NULL
    AND lease_expires_at IS NULL
  ORDER BY id;
  ```

  Then fail only the ids you mean to stop. `900001` is a synthetic example, not a live job. `internal_error` is the worker's terminal class, so the row is not retried. `error` is the operator message. `completed_at` is set, `next_attempt_at` is cleared, and the lease columns stay NULL. `result` is left as it is, which is what a terminal failure in the worker does.

  ```sql
  BEGIN;

  UPDATE jobs
  SET status = 'failed',
      error_code = 'internal_error',
      error = 'Operator stopped a running job that has no lease. It was claimed before lease recovery and was not reclaimed.',
      next_attempt_at = NULL,
      lease_owner = NULL,
      lease_expires_at = NULL,
      completed_at = (NOW() AT TIME ZONE 'UTC'),
      updated_at = (NOW() AT TIME ZONE 'UTC')
  WHERE id IN (900001)
    AND status = 'running'
    AND lease_owner IS NULL
    AND lease_expires_at IS NULL;

  INSERT INTO audit_events (
      occurred_at, action, user_id, email, workspace_id, resource_type, resource_id, details
  )
  SELECT
      (NOW() AT TIME ZONE 'UTC'),
      'job.failed',
      NULL,
      NULL,
      j.workspace_id,
      'job',
      j.id::text,
      json_build_object(
          'kind', j.kind,
          'workspace_id', j.workspace_id,
          'error', j.error,
          'error_code', j.error_code,
          'attempt', j.attempt,
          'max_attempts', j.max_attempts,
          'retries_exhausted', false
      )::text
  FROM jobs j
  WHERE j.id IN (900001)
    AND j.status = 'failed'
    AND j.error = 'Operator stopped a running job that has no lease. It was claimed before lease recovery and was not reclaimed.';

  COMMIT;
  ```

  If the `UPDATE` changes no row, the job was not a NULL-lease `running` row. Do not force it. The `INSERT` then also writes nothing, because it requires that same error text.
* **Rollback.** Deploy the previous worker first, then `alembic downgrade bug018c_one_open_gap`. That drops only `lease_owner`, `lease_expires_at`, and `ix_jobs_running_lease_expires_at`. #82's one-open-gap index and #78's status checks stay.
