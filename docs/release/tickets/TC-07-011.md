# TC-07-011 — Redact secrets and sensitive evidence from diagnostics

Status: the behaviour is on master from TC-07-011a (`15c6da10`). The named release test and this note are TC-07-011b. This note does not accept TC-07-011. It does not change the DONE count. No migration.

Parent criteria: canary credentials, cookies, reset links, source text, and filenames stay out of application, provider, and monitoring traces. Request and job correlation stay useful for support.

## Behaviour

`redact` masks a `tc_session` cookie, a bearer or basic credential, a URL password, presigned S3 signing parameters, and a `password=` / `token=` value. `JsonFormatter` applies that to the message and to the exception text, and it masks a secret-named field. It adds `request_id` and `workspace_id` from the request context when those values are set. It leaves `job_id` in place. The redaction patterns do not match `request_id` or `job_id`.

An upload rejection does not write the user-supplied filename. `FileService` reads the name only to choose a suffix. Each `upload_rejected` warning logs `workspace_id`, `size_bytes`, `ext`, and `reason`. `ext` is the lower-case suffix when it is one to eight letters or digits, such as `.pdf`. A missing suffix is `none`. Any other suffix is `other`. A size rejection also logs `max_bytes`. An `upload_raw` extension rejection also logs the fixed allow-list. A trust-request rejection logs that trust request's id as `request_id`. When the request context has an HTTP request id made of letters, digits, `.`, `_`, or `-`, the warning includes it as `http_request_id`. Otherwise that field is `-`. These rejections happen before a job exists, so the warning does not invent a `job_id`. The caller still receives the stored key and the sanitized filename. The HTTP 413 and 400 details do not include the filename.

A classification failure does not log the question or the model text. `parse_classification_response` logs `JSON parse failed` and the UTF-8 byte length. A failed classification call, including a bulk classification failure, logs the exception class name.

Password-reset warnings do not include the reset URL. They log the user id and, when the send raises, the exception class. The mailer still receives the URL. Production email failure does not print the message body. This note does not change email delivery.

Sentry `before_send` runs only when `SENTRY_DSN` is set. It drops request cookies, the Authorization header, and the request body (`data` or `body`). A value whose key is a filename field becomes `[REDACTED]`. A `/reset-password?token=` value in any remaining string is masked, as are `filename=` pairs and the same secret patterns `redact` already masks. Keys named `request_id` and `job_id` are left in place. A short operator message that is not one of those values is left in place.

Pipeline lines from `app.core.pipeline_logging` still carry `job_id` when the caller passes one.

## What support can use

| Need | Where it remains |
|---|---|
| Which HTTP request | `request_id` on the JSON log line, `http_request_id` on an upload rejection when the context id is safe to echo, and `X-Request-ID` on the response |
| Which job | `job_id` on the pipeline line and on any log or Sentry field already named `job_id` |
| Which upload was rejected | `workspace_id`, `size_bytes`, `ext`, `reason`, and `max_bytes` when the file was too large. A trust-request rejection also has that request's id |
| Which classification failed | `JSON parse failed` with `bytes=`, or the exception class name. The question text is not in the log |

## What this note does not claim

A successful upload's audit event still records the stored filename. That is the audit record, not the rejection warning. The non-production Slack stub still logs the first 100 characters of a message. Production refuses that stub and does not log the text.

## Verification

```sh
python -m pytest tests/release/test_log_redaction.py -q
```

The test fails when a canary filename, reset link, cookie, or source sentence is present in the records above, and it requires `request_id` and `job_id`. Evidence is in `artifacts/acceptance/TC-07-011b/`. TC-07-011a remains the behaviour change. This note does not accept the ticket.
