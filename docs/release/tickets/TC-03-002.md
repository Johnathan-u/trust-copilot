# TC-03-002 — Persistent Compose services with least privilege

**Epic:** E03 Deployment and migrations · **Baseline:** `80607881320e1fa2c6416c55730eb98a56449f26` · **Branch:** `tc/platform/TC-03-002`
**Evidence:** [`artifacts/acceptance/TC-03-002/`](../../../artifacts/acceptance/TC-03-002/README.md)
**Verification:** `cd apps/api && python -m pytest tests/release/test_compose_stack.py -q`

## Problem at baseline
* Compose services ran as root, kept a writable root filesystem, and did not drop capabilities.
* Dev Postgres and MinIO published `5432` and `9000`/`9001` on every interface.
* Production Postgres and MinIO sat on the same bridge as the public proxy.
* The published Caddy image has no unprivileged user. The API image had no `USER`.

## Behaviour after this ticket
AC1 and AC2 only. No migration.

| Service | User | Data | Network |
|---|---|---|---|
| caddy | 10001:10001 | named `caddy_data`, `caddy_config` | `trustnet` (public ports). Prod adds `NET_BIND_SERVICE` so it can bind 80/443 after `cap_drop: ALL` |
| web | 1000:1000 | dev named `web_node_modules`, `web_next` | `trustnet` |
| api, worker | 10001:10001 | none of their own | `trustnet` and internal `datanet` |
| postgres | 999:999 | named `postgres_data` | dev `127.0.0.1:5432` only; prod unpublished, `datanet` only |
| minio | 1000:1000 | named `minio_data` | dev `127.0.0.1:9000` and `127.0.0.1:9001` only; prod unpublished, `datanet` only |

Every service sets `read_only`, `cap_drop: [ALL]`, and `no-new-privileges:true`, with `/tmp` on tmpfs. Postgres also tmpfs-mounts `/var/run/postgresql`. Images do not `COPY` an env file and do not set a non-empty `PASSWORD`/`SECRET`/`ACCESS_KEY`. The API entrypoint still runs only `alembic upgrade head`.

## Decisions
1. Postgres stays uid 999, the image's data-directory owner. A fresh named volume inherits that owner, and initdb completes without root. Verified with the committed compose file (`read_only`, `cap_drop: ALL`, `no-new-privileges`).
2. `caddy:2` sets file capability `cap_net_bind_service=ep` on its binary. `cap_drop: ALL` then refuses to exec it (`EPERM`). `infra/caddy/Dockerfile` runs `setcap -r` and adds uid 10001. Production compose adds `NET_BIND_SERVICE` back. `no-new-privileges` still holds: Docker grants that capability at start, the process does not acquire it later. A read-only container with that capability answered on port 80.
3. Dev API port `8000:8000` is unchanged. The acceptance criteria constrain database and object-storage admin ports.
4. No migration. Alembic head stays `tc02001a_parent_ws_move`. Master moved to `b70ba0f` (TC-10-001b) before push; that commit is merged with `--no-ff`. The worker grace-period setting from that commit stays in `docker-compose.prod.yml`.
5. `.github/workflows/deploy.yml` is unchanged.

## Runtime evidence

Previously populated root-owned dependency volumes need separately scoped local
ownership preparation; rebuilding alone does not change their files. Do not
change ownership of the host source or product-data volumes as part of that step.

repair and static checks do not satisfy those runtime gates.

Postgres restart kept the synthetic row `test-example-synthetic`. MinIO was not pulled (`minio/minio:latest` denied), so object-storage restart evidence is pending. Static checks still require the named volume, localhost-only dev ports, and no prod publish.

## Dedicated runtime acceptance (2026-10-30)

`.github/workflows/compose-acceptance.yml` adds one bounded Docker job on relevant
pushes and pull requests, and supports manual dispatch. It runs
`python scripts/release/compose_acceptance.py` with no new Python dependency. The
existing `ci.yml` is unchanged. The runner refuses local and self-hosted execution.

The job derives its service definitions from the committed Compose files. It
preserves images, build targets, users, entrypoints, commands, read-only roots,
capability limits, tmpfs mounts and internal database/storage networking. Fresh
throwaway credentials, unique project/container/volume names and a loopback-only
ephemeral HTTPS port isolate the test. It never writes an existing `.env` file or
changes host-checkout/data-volume ownership.

The dev phase runs the real web image and npm command with a fresh dependency
volume, then restarts against the populated volume. The production phase starts
all six services, verifies runtime hardening and dependency readiness, writes a
synthetic PostgreSQL row and MinIO object, and reads both after full-stack restart
and container recreation. Caddy must serve verified HTTPS with the same internal
CA certificate and persisted autosave configuration after both operations.

The Caddy fixture changes only the production hostname to `localhost` and adds
`tls internal`; committed proxy routes are retained. Public ACME issuance, public
DNS, provider credentials and model calls are outside this test. A generated,
non-provider model-key value satisfies the existing startup configuration contract;
no provider account or paid call is used. Registry denial fails the job without a
fallback image or login.

The uploaded `compose-acceptance-<run>-<attempt>` artifact contains a sanitized
`result.json` with the tested SHA, stage outcomes, inspected image IDs/security
settings and cleanup outcomes, plus bounded failure logs when available. Cleanup
checks the exact unique Compose project label before deleting each test-owned
container, network or volume. No global prune or shared resource deletion is used.

**Status:** harness authored and locally checked; Docker startup/persistence remains
unqualified until this workflow passes on the reviewed head. Existing populated
root-owned dependency volumes are not repaired by the test. If the non-root dev
server cannot write `.next` in its bind-mounted checkout, its real startup failure
remains a failure; the harness does not chmod/chown the checkout to make it pass.
