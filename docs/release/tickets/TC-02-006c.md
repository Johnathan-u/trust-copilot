# TC-02-006c: eslint-disable hygiene in the web app

**Status:** implemented on `tc/web/TC-02-006c`. Do not merge from this ticket.
**Base:** `master` at `04c843b` or newer. This branch does not change product behavior.

## Acceptance criteria

1. Every existing `eslint-disable` comment in `apps/web` is either removed by fixing the underlying code, or narrowed so it names its exact rule and carries a `-- <reason>` justification on the same line. No blanket `eslint-disable` or `eslint-disable-next-line` without rule names remains.
2. Lint fails on any new blanket disable and on any disable without a justification. The flat config enables `@eslint-community/eslint-plugin-eslint-comments` rules `no-unlimited-disable` and `require-description`, and sets `linterOptions.reportUnusedDisableDirectives` to `error`. The existing CI lint step (`npm run lint`, which is `eslint . --max-warnings=0`) enforces that. No gate is loosened.
3. No behavior change. Existing unit tests and release specs pass unchanged.
4. Stay clear of the separate `react-hooks/set-state-in-effect` follow-up. If a disable exists only for that rule, leave it untouched and list it. Avoid editing files that follow-up is likely to touch where possible.

## Definition of done

- The pull request body has a before/after table, one row per disable: file:line, rule, fixed or justified.
- Before and after counts are recorded (below).
- A throwaway local check, not committed, shows that a deliberately added blanket disable fails lint (described below).
- CI is green on the exact head. Any merge with `master` is a pure merge commit. Conflicted files, if a merge is required, are listed in the pull request body.
- This file records the acceptance criteria and the definition of done.
- No ticket ids in user-facing UI strings.
