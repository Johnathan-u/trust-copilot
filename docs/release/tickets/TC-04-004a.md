# TC-04-004a — Strict human session credentials and row ownership

Status: implemented locally; independent review and PostgreSQL/exact-head CI qualification pending. Estimate: 5 points. Claim: [#85 comment 6514312794](https://github.com/Johnathan-u/trust-copilot/issues/85#issuecomment-6514312794). Implementation base: reviewed membership repair `765589e9d3af2992e62f0d1e0cfc03296f444813`.

A signed human cookie previously remained valid without an expiry or session ID. Numeric strings and fractional expiry values were coerced to integers. A present session ID only had to exist, so a synthetic signed cookie naming another user's session was accepted by required authentication and `/auth/me`; logout could delete that other session.

The existing session verifier now requires an object payload, an exact integer expiry strictly later than the current time, and a nonblank string session ID. Required/optional authentication and `/auth/me` share the same database check that the existing session row belongs to the exact integer human user ID. Missing/revoked/foreign rows fail closed. The existing explicit denial for a cookie without a human identity is retained. Valid API keys take their existing separate authentication branch.

Logout still clears an invalid cookie, but it cannot delete a stored session or attribute a logout audit event to that credential. A valid logout deletes only the matching user/session pair. Current active-membership checks, role resolution, account-only onboarding and restricted MFA enrollment remain unchanged. Legacy cookies lacking the required fields must sign in again; all seven existing production issuance sites already supply both fields.

Runtime changes are limited to `core/session.py`, `core/auth_deps.py`, and `routes/auth.py` imports plus `/me` and logout. No schema, key format/purpose, API-key scopes, owner/viewer migration, principal architecture, current-policy enforcement or remember-me redesign is included. Full TC-04-004, TC-05-003 and TC-06-001 remain open.

The new session-validation tests reuse the reviewed real-route HTTP fixture with separate request sessions and exact owned-row cleanup. SQLite and PostgreSQL run the same malformed/expired/revoked/cross-user controls. Restart evidence uses three fresh, exited/reaped Python interpreters mounting real auth dependencies and routes: the first reads the valid session, the second reads it again and logs out, and the third rejects the persisted revoked credential. SQLite uses a private on-disk database copy deleted in `finally`; PostgreSQL uses the existing isolated test database and fixture-owned rows. This is isolated HTTP/router/process persistence coverage, not full production startup qualification.

Valid fixture corrections are confined to the six claimed release files. Trust-request, vendor-request and FAQ actors receive owned session rows and explicit expiry, with cleanup/count invariants extended. MFA/rotation fixtures receive expiry. The intentionally legacy cookie remains invalid; expired fixtures retain negative expiry; the uid-less fixture retains `user_id=None` with otherwise valid metadata so its original identity-denial assertions remain meaningful. No existing assertion is removed or weakened.
