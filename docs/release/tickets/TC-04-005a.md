## Problem

`POST /api/members/{id}/revoke-sessions` (`apps/api/app/api/routes/members.py`) used to delete `UserSession` rows filtered by `user_id` only. An admin of workspace A could sign that user out of every workspace, including ones the admin has no rights in.

## Behaviour

`POST /api/members/{member_id}/revoke-sessions` still requires an admin of the caller's workspace, and the member id must be a membership row in that workspace. A stranger, or the same user's membership row in another workspace, is 404 `Member not found`. No session row is deleted and no cutoff is written.

On success the handler sets `workspace_members.sessions_revoked_at` to the current UTC time on that one membership. It does not delete `user_sessions` rows. The response is still `{"ok": true, "revoked": N}`. `N` is the number of that user's stored sessions whose `created_at` is null or at or before the cutoff. Those sessions lose this workspace. They are not removed.

A request whose cookie names this workspace is rejected with 401 `Session invalidated` when the stored session was created at or before the cutoff. The same session, already pointed at another workspace, keeps working there. Switching onto the revoked workspace is rejected with the same 401 and does not set a new cookie. Switching off the revoked workspace onto a workspace that has no cutoff is allowed, so one browser is not trapped where it can no longer read data.

A session created after the cutoff can use the workspace again, including switching away and back. Membership, role, and suspension are unchanged. Workspace API keys are unchanged.

`POST /api/auth/sessions/revoke-all` is unchanged. The signed-in user still deletes every stored session for that account, in every workspace, and the cookie is cleared. That path does not write `sessions_revoked_at`. There is no separate super-admin global sign-out. Global sign-out stays that self-service action.

The members screen confirm and toast now say this workspace, not every device.

## Design

`user_sessions` does not store a workspace. Columns are the user, the session id, the signing key id, user agent, IP, and `created_at`. The active workspace is only a claim in the signed cookie.

`POST /api/auth/switch-workspace` loads `WorkspaceMember` for the target, then calls `enforce_session_record` with that workspace id, then reissues the cookie with the same `session_id`. TC-04-005 showed `resolve_current_membership` re-reads the membership on the request. That re-read still applies role, suspension, and removal. It does not, by itself, stop a session pointed at workspace B from switching back to A: the user is still a member of A.

Deleting "sessions whose active workspace is A" cannot be done from the row, and it would not be enough if it could. The session pointed at B would switch back. Deleting every row is the bug this ticket closes.

The cutoff lives on the membership row the admin already has to load. `enforce_session_record` loads that row for the workspace in the cookie (or the target workspace, for switch and workspace creation) and compares it to `user_sessions.created_at`. Null `created_at` is treated as already existing. Comparison is UTC and accepts naive or aware values. A missing membership is not a revocation; removal and suspension stay on their existing checks.

Switch uses `require_session_leaving_workspace`, which skips the cutoff only for the workspace being left, then runs `enforce_session_record` on the target with the cutoff on. The cookie is set only after that call returns. Login, OAuth, and MFA confirmation insert a new `user_sessions` row, so a new sign-in is after the cutoff.

Workspace creation calls `enforce_session_record` for the new workspace id before the membership row exists. There is no cutoff to apply. The new membership is inserted with a null cutoff.

## Migration

**Required.** `tc04005a_member_revoked_at` revises `tc17005a_share_token`, the single Alembic head on master when this branch was cut. Upgrade adds nullable `workspace_members.sessions_revoked_at`. Existing rows stay null, so current sessions keep working until an admin revoke. The revision id is 26 characters and fits `alembic_version.version_num` (`varchar(32)`). The revision does not import the application package.

Downgrade drops the column. Sessions that had been blocked from a workspace can use it again. That downgrade drops the revocation record. Re-upgrade does not restore the timestamps.

## Residual risks

- Removing the member deletes the membership row and the cutoff with it. Adding them again starts from null, so sessions that still exist can use the workspace. Removal already blocks access until that new grant.
- A session whose `created_at` equals the cutoff is blocked (`<=`). A sign-in that stores that same timestamp has to sign in again. The next later timestamp is allowed.
- Workspace API keys are not sessions. This endpoint does not revoke them. The parent test still covers that.
- `/api/auth/me` on a cookie pointed at the revoked workspace is 401, so the web app treats that browser as signed out. A client that calls switch directly can move that same session to another workspace. The dashboard does not, because it loads `/api/auth/me` first.
- Any future route that trusts the signed cookie without `enforce_session_record` would ignore the cutoff. Login, OAuth, MFA, switch, and workspace creation were the cookie reissue paths at this change. Switch and workspace creation check the target before `set_cookie`.
- The cutoff and `created_at` are both application UTC timestamps, not a database clock.

## Release note

An admin who revokes a member's sessions now ends that member's existing access to the current workspace only. The member stays signed in to other workspaces. They sign in again to use this workspace. Signing out of every workspace is still the member's own sign-out-everywhere action.

## Acceptance criteria

1. Revocation is scoped to the caller's workspace, as described above. Global sign-out remains `POST /api/auth/sessions/revoke-all`.
2. `apps/api/tests/release/test_tc04005a_revoke_scope.py` covers a member of A and B: the B session keeps working, A access is rejected, a B-pointed session cannot switch back to A or present a cookie that claims A, an A-pointed session can leave for B and still cannot return, a session created after the cutoff can use A again, and a membership id outside the caller's workspace is rejected with the stranger's session left in place. The parent API-key case in `test_session_revocation.py` now expects the session row to remain and the home-workspace cookie to be rejected.
3. This file documents the behaviour, the design, and the release note.
