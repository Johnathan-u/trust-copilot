## Contract

The frontend's slashless `POST /api/answers` previously redirected with 307. Both that path and legacy `POST /api/answers/` now register the same existing create/upsert handler directly. Successful responses retain exactly `id`, `question_id`, `text` and `status`. Create defaults and existing upsert behavior remain unchanged, including preserving existing text on an empty-text upsert and clearing the model outcome when human text replaces it.

Literal `PATCH /api/answers/bulk` is registered before `PATCH /api/answers/{answer_id}`. It now reaches the bulk handler rather than producing an integer-path 422 for the word `bulk`. The individual update handler is otherwise unchanged.

Bulk validates the complete requested set before adding or changing any answer:

| Request                                                                                      | Result                          | Persisted effect                                                       |
| -------------------------------------------------------------------------------------------- | ------------------------------- | ---------------------------------------------------------------------- |
| Empty list, duplicate IDs, nonpositive or out-of-range integer IDs, unsupported/empty status | 400 `Invalid request`           | No changes                                                             |
| Wrong ID/list type, including booleans, coerced strings/floats, null or missing list         | 422 body validation             | No changes                                                             |
| Any missing/foreign question, moved parent, or unavailable parent                            | 404 `Question not found`        | No changes, including authorized entries in the same request           |
| Unique questions with current, nondeleted parents in the caller's workspace                  | 200 with `updated` and `status` | Existing answer status updated; missing answer created with empty text |

IDs must be strict integers in the current database's positive signed-32-bit range. The complete set is resolved through a join to current questionnaires with the workspace and `deleted_at` predicates. A missing, foreign or unavailable object has the same neutral 404 response regardless of its position in a mixed request. No FK or trigger is disabled to construct these cases; physical parent deletion uses the existing cascade, while soft deletion exercises a retained but unavailable parent.

The successful `updated` count is the number of unique authorized questions handled. Repeating the same successful request does not add answer rows or change other persisted fields. The existing allowed bulk statuses remain `draft`, `approved`, `rejected`, `flagged`, `pending` and `insufficient_evidence`; this repair does not redefine model/generation status vocabulary. The existing `require_can_review` dependency is preserved. No auth, role, model, schema, migration, generation, UI, dependency or CI configuration changes are included.

## Verification

`tests/release/test_answer_routing.py` contains 134 cases: 67 local SQLite controls and the same 67 migrated PostgreSQL cases. Both variants mount the real production router, sign a session with the test runtime's generated signing value, and persist real user, session and workspace-membership rows. Only `get_db` is injected. Authentication and permissions are not mocked.

The cases cover both POST paths without redirect; first-answer defaults and existing upserts; dynamic individual updates; all three existing built-in roles and all six existing bulk statuses; retry without duplicates; invalid IDs and statuses; mixed foreign/missing/deleted/moved/removed-parent requests in both orders; anonymous access; current permission downgrade after signing an admin cookie; deleted session; and removed membership.

Denied requests compare every column in all relevant answer, question, questionnaire, document and authentication rows. Successful requests compare the same rows and permit only the intended answer changes, new rows and affected update timestamps. Cleanup records fixture-owned IDs, captures request-created answer IDs through those exact owned question IDs, deletes only those rows in FK order, and verifies the original full-row snapshot. Connections close even when cleanup assertions fail. SQLite foreign keys remain enabled; PostgreSQL uses the existing migrated fixture. Collection has no database side effects.
