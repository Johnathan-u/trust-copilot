# TC-02-002 — Lock compatible Python and PostgreSQL driver dependencies

**Epic:** E02 Toolchain and CI · **Baseline:** `1a0e6146` (origin/master when the branch was cut) · **Branch:** `tc/platform/TC-02-002`
**Evidence:** [`artifacts/acceptance/TC-02-002/`](../../../artifacts/acceptance/TC-02-002/README.md)
**Verification:** `cd apps/api && python -m pytest tests/release/test_python_lock.py -q` (CI runs it with `TC_REQUIRE_DB=1`).

## Problem at baseline

* `apps/api/pyproject.toml` held ranges only (`fastapi>=0.109`, `openai>=1.0`, …); every install re-resolved, so
  two builds a day apart could ship different code. No lock file, no hashes.
* `pytest` was a **runtime** dependency, so the production image carried the test runner. CI installed
  `ruff==0.5.6 pytest` ad hoc next to `pip install -e .`.
* The PostgreSQL driver relied on SQLAlchemy's dialect default. SQLAlchemy 2.1 maps `postgresql://` to psycopg 3,
  which is not installed; only the `<2.1` cap kept the app on `psycopg2`.
* `TC_REQUIRE_DB=1` failed the session when the DB was unreachable, but ad-hoc `pytest.skip(...)` calls in DB tests
  (58 in `tests/` at baseline: "Postgres not available", missing seed rows, ...) still passed CI as skips.

## Behaviour after this ticket

### Locks (AC2)
| File | Contents | Used by |
|---|---|---|
| `apps/api/requirements.lock` | runtime dependencies only, exact `==` pins, sha256 hashes, universal markers (any OS), Python 3.11 | `apps/api/Dockerfile` (all targets, so `deploy.yml` and compose), `scripts/run-migrations.ps1` |
| `apps/api/requirements-dev.lock` | runtime **plus** the `dev` extra (`pytest`, `ruff==0.5.6`), constrained to the runtime pins | CI, `scripts/seed-*.ps1`, local development |

* `pyproject.toml` keeps the human ranges (`sqlalchemy>=2.0,<2.1`, `psycopg2-binary>=2.9`, `pypdf>=6.21.3,<7`, …).
  `pytest` moved to `[project.optional-dependencies] dev` with `ruff==0.5.6` (same rev as the pre-commit hook).
* Installs are `pip install --require-hashes -r <lock>` then `pip install --no-deps` for the project itself, then
  `pip check`. A package whose hash does not match is refused, and the project cannot pull in an unlocked dependency.
* The lock is the **current** dependency set: the dev lock equals the packages master CI was installing at
  `1a0e614` (SQLAlchemy 2.0.55, psycopg2-binary 2.9.13, fastapi 0.162.0, pypdf 6.21.2, pytest 9.1.1, …);
  only platform-marker entries (e.g. Windows `colorama`) are added. The one deliberate exception is the
  **pypdf 6.21.3 security bump** (see Rulings).

### Driver (AC1)
* `sqlalchemy` stays `>=2.0,<2.1` (with a comment saying why) and `psycopg2-binary` is a direct dependency, so the
  `postgresql://` URL resolves to the installed `psycopg2` driver. psycopg 3 is neither locked nor installed;
  the release test fails if either changes.

### DB-test skips fail CI (Coordinator ruling)
`TC_REQUIRE_DB=1` already (ci-repair/TC-02-001) failed the session when Postgres was unreachable and made the
`client` fixture fail instead of skip. It did **not** catch skips raised inside tests or other fixtures. This ticket
extends the same switch rather than adding a new one: `tests/conftest.py` has a `pytest_runtest_makereport`
hook that, when `TC_REQUIRE_DB=1`, reports any skipped `integration` test as failed
(`TC_REQUIRE_DB=1: DB (integration) test skipped instead of running: <reason>`). `xfail` is untouched, and the
opt-in categories `provider`, `live_stack` and `external_data` keep their documented skips. Two tests that used to skip
on missing seed rows (`test_control_timeline`, `test_feedback_capture`) now create synthetic rows instead.

### Release test `apps/api/tests/release/test_python_lock.py`
Static checks: both locks exist, are produced by the script, use exact pins with hashes, and contain no option lines
or duplicates. Dev tools are only in the dev lock, and the dev lock repeats every runtime pin unchanged. Every
`pyproject.toml` requirement is locked within its specifier. SQLAlchemy is `<2.1` with `psycopg2-binary`. Negative
cases feed synthetic bad locks (missing hash, range pin, dev tool in runtime, version drift, SQLAlchemy 2.1, no driver,
psycopg 3, option line, duplicate). Environment checks: installed versions equal the dev lock, the runtime lock is
exactly the closure of the app's requirements (no missing or stray pins), and psycopg 3 is absent. AC1 probe: a fresh
interpreter imports `app.main` and runs `SELECT 1` through `engine` (dialect `postgresql`, driver/DBAPI `psycopg2`), at
the locked versions. Skip policy: a child pytest run shows a skipped DB test failing under `TC_REQUIRE_DB=1` and staying
a skip without it.

## Runbook

```bash
# install (local dev / CI)
cd apps/api
pip install --require-hashes -r requirements-dev.lock
pip install --no-deps -e .
pip check
# production image: Dockerfile installs requirements.lock only (no pytest/ruff)

# change a dependency: edit apps/api/pyproject.toml, then (needs uv, https://docs.astral.sh/uv/)
scripts/lock-python-deps.sh             # keeps existing pins, resolves only what changed
scripts/lock-python-deps.sh --upgrade   # re-resolve everything (security updates); review the diff
scripts/lock-python-deps.sh --upgrade-package <name>
# commit pyproject.toml + both locks together; test_python_lock.py fails if they disagree
```

## Rulings and deviations

* **PyMuPDF → pypdf.** The original ruling was to lock the current set "including pymupdf". #11 (TC-01-003a,
  `f30c174`) has since replaced PyMuPDF with `pypdf>=6.21.2,<7` on master, so the lock has `pypdf==6.21.2` and no
  PyMuPDF. `test_pdf_text_locator_corpus.py` already scans all manifests and lock files for the old package, so this
  ticket does not duplicate that check.
* **pypdf 6.21.3 security bump folded in (Coordinator update).** pypdf 6.21.3 (released 2026-10-27; security fixes:
  validated page count after decrypting, a limit on cross-reference stream entries) appeared after the lock was cut.
  Instead of a follow-up, the locks were regenerated with `scripts/lock-python-deps.sh --upgrade-package pypdf`: only
  the `pypdf` entry changes in both locks (6.21.2 → 6.21.3, both hashes equal PyPI's published sha256 for the wheel and
  sdist), and a second plain run is byte-identical. The `pyproject.toml` floor moves to `pypdf>=6.21.3,<7` so a
  re-resolve cannot fall back to the vulnerable version. The PDF tests and `test_python_lock.py` pass at 6.21.3.
* **Merged origin/master `ec40823`** (merge commit, no conflicts). TC-07-001 (#13) on master removes committed
  credential literals, so the AC1 probe now sets a per-run random `SESSION_SECRET` (`secrets.token_urlsafe`).
* **E01 dependency not blocking.** The backlog lists TC-01-003 (E01 legal) as a dependency. Per the Coordinator,
  E01 legal tickets do not block this work. Licence review of the locked set is not done here.
* **SQLAlchemy below 2.1:** kept as ruled. Moving to 2.1 means switching to psycopg 3 in a separate ticket.

## Limitations / follow-ups

* `python:3.11-slim` is not digest-pinned (TC-02-004 / TC-02-008). The build backend (`setuptools`, via build
  isolation), `pip` itself (`pip install -U pip`) and `pre-commit` in CI are not locked.
* The frontend lock is TC-02-003.
* DB tests that still depend on rows created by other tests will now **fail** (rather than skip) when run in an order
  where those rows don't exist. That is intended. Master `d527863` already fixed one such test
  (`test_questionnaire_answer_evidence`, TC-02-BUG-014).
