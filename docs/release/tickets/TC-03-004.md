# TC-03-004: Qualify the migration chain and an audited-data upgrade

This file records the implementation. It does not accept TC-03-004. AC1 and AC2 stay unverified until an independent reviewer accepts them. No migration file was added or edited. No customer document is in the fixture or the evidence.

## What the check does

The planning baseline `c20f949161ac12a619b396d30904448ffd74d532` has one alembic head, revision `075`. `apps/api/scripts/migration_baseline.py` discovers the current head with alembic at runtime and refuses to run when that count is not 1. The head name is not written in the script.

`qualify` builds the audited snapshot in an empty database: upgrade to `075`, then `apps/api/scripts/fixtures/audited_snapshot_075.sql`. The fixture inserts one synthetic workspace, user, membership, document (`storage_key`), questionnaire (`storage_key`), question, and answer. It then upgrades one revision at a time to the head, compares the database, downgrades to `075`, compares again, and upgrades to the head once more.

`fresh` upgrades an empty database to that same head. CI already does this with `alembic upgrade head` before the suite. The release test runs `fresh` on a side database so this command shows the same result.

`upgrade` is the operator path for a database that is already at revision `075`. It does not load the fixture and it does not downgrade.

A partial snapshot is refused. `alembic stamp 075` on a database with no core tables makes `upgrade` exit 2 with `MIGRATION_BASELINE_REFUSED`. The version row stays `075`. The tool does not call `alembic stamp`.

## Survival and backfill report

Before and after the upgrade from `075`, the report records per-table row counts, foreign-key definitions, sampled storage keys, and sampled answer text.

`survival.row_counts_match` is true when no baseline table lost rows and the seven audited tables kept the same counts. Rows a later migration inserts are listed under `survival.row_count_increases` and under `backfills`. On the synthetic snapshot the only increase is `frameworks`, from the catalog backfill in `tc21001_framework_catalog_rights`. `question_cell_mapping` updates the synthetic question (content hash, sheet, and question cell `B12` from the stored locator). Other listed revisions run data statements and affect 0 rows in this fixture.

Foreign keys that exist at `075` are still present at the head. The report's `survival.foreign_keys_missing` is empty. New foreign keys are counted, not treated as a loss.

Sampled keys are `synthetic/audited-snapshot/policy.pdf` and `synthetic/audited-snapshot/questionnaire.xlsx`. The sampled answer is `Access reviews run each quarter.` Status stays `approved`.

## Rollback

`qualify` records `rollback` and `reupgrade`. Downgrade to `075` keeps the sampled keys, the answer text, and the baseline table counts. The following upgrade reaches the same head and keeps those values. `question_cell_mapping_hold` exists only because that downgrade parked the question columns; the test checks the table is present after the round trip.

`upgrade` does not downgrade a database that was already at `075`. An operator downgrades with `alembic downgrade 075` after a backup, or restores the backup if that downgrade fails. Neither path stamps over an error.

## Contract

No API, permission, or UI contract changes. The negative case is the partial snapshot, not a permission denial.
