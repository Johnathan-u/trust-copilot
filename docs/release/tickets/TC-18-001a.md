# TC-18-001a: public intake retry path, response and abuse limits

Follow-up of TC-18-001. It collects the non-blocking items from the independent post-merge review of #203 (`b32234f`).
Epic E18. 5 points, P1. Depends on TC-18-001. Branch: `tc/TC-18-001a-intake-hardening`.

## Acceptance criteria

1. The Next handler at `apps/web/app/api/[[...path]]/route.ts:63-88` forwards `Idempotency-Key`. It currently drops the header, if it serves `/api/*` at all; the `next.config.js` rewrite may take precedence. This also matters for the deals, requests and gap-actions screens. One real test (Uvicorn + Next + Chromium, in the `test_trust_requests_browser.py` harness) aborts the first intake response after the save commits, retries, and finds one row and one stored file.
2. The form keeps `{fingerprint, key}` in `sessionStorage` (inside try/catch), so a reload after a lost response reuses the key.
3. A test sends two same-key `/submit` calls at once (threads plus a barrier) and asserts one row, one upload, and a 200 for one call with a 409 or a replayed 200 for the other.
4. The public submit response returns only what the visitor needs (for example `id`, `display_id`, `status`). It no longer includes `attachment_storage_key`, `submitted_host` or `workspace_id`.
5. Unauthenticated intake has its own per-route and per-workspace rate limit (Redis-backed in production), and the size cap for public uploads is reviewed.
6. UI edges:
   - The key comes from `crypto.randomUUID()` with a `getRandomValues` fallback, and any failure shows a message.
   - Text is limited by code point, so an emoji pair is never cut in half.
7. The runbook's "uncertain save" steps say a resubmission reuses the key only while the original tab is open, or after criterion 2, after a reload too.
8. Each code item has a test that fails without the fix.

## Evidence and sign-off

CI on both events, plus an independent review. Under OD-14 no separate owner sign-off is needed.
