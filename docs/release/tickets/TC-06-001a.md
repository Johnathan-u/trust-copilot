# TC-06-001a — Current active human membership

Status: local repair ready for independent review; PostgreSQL qualification and
exact-head CI remain pending. Claim: issue #85 comment `6513354940`, 5 points.
Base: `c2ac170f2a1572811342af67abfa4e703b14a628`.

Required and optional authentication previously accepted a signed cookie after
its membership was removed. Generic permission dependencies continued to use the
cookie's role after demotion; optional authentication also admitted suspended
members to unpublished trust articles. `/auth/me` independently displayed that
stale authority, and workspace switching could issue a cookie for a suspended
target membership.

The existing human-session dependencies now resolve the current membership from
the database, refreshing a previously loaded membership object. Missing or
suspended membership returns 403. Permissions use the current membership role and
the existing built-in/custom-role resolution. Optional authentication shares the
same validation; rejected human authority becomes anonymous, preserving the
existing published-only public article contract. `/auth/me` applies the same
membership resolution while remaining cookie-only. Switching workspace checks
that its target membership is active before issuing a cookie or audit event.

## Preserved account flows

An explicit `workspace_id=0, role=pending` credential can use only these existing
account/onboarding methods and paths:

| Method | Path |
| --- | --- |
| GET | `/api/auth/me`, `/api/auth/sessions`, `/api/auth/alerts`, `/api/auth/mfa/status`, `/api/workspaces/creation-policy` |
| POST | `/api/auth/change-password`, `/api/auth/sessions/revoke-others`, `/api/auth/logout`, `/api/auth/mfa/setup`, `/api/auth/mfa/confirm`, `/api/auth/mfa/disable`, `/api/auth/switch-workspace`, `/api/workspaces` |

The existing signup policy, creation cap and rate limit still apply. Successful
first-workspace creation issues the existing admin context; a pending credential
cannot access tenant operations or unpublished optional-auth content. A stale
`pending` role on a positive workspace never bypasses membership resolution.

MFA enrollment retains its existing narrower method/path allowlist and factor
validation. Its effective role remains `mfa_enrol` with zero permissions even when
the current member is an admin. Removed/suspended membership cannot enroll. The
existing reset, setup, confirmation and session-replacement controls are retained.

API-key authentication keeps its existing precedence, workspace role, expiry and
permission behavior. No new owner/viewer mapping, principal type, session expiry
or session-ID rule, migration, dependency, parser change or additional auth-route
change is included. This is not full TC-06-001 or TC-04-004 acceptance.
