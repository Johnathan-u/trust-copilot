# TC-25-005 Consent-backed case study authoring publication

Status: implemented on `tc/ca/TC-25-005`. Not yet in review. PR #2 (TC-01-005) is still open and was not merged into this branch.

## What changed

A case study can be drafted, submitted for review, approved, and published. Setting `status` to `published` on `PATCH /api/case-studies/{id}` no longer publishes. Publish checks the current revision:

- Every quoted organization has an active consent for that revision.
- Each of those consents permits every quoted result.
- If any consent or permission is missing, nothing is published.

A row is a customer claim only when it is published, not synthetic, review-approved, and fully consented. `customer_claim` is derived from those stored facts. A column set by hand, a seed, or a fixture cannot make the API or the UI show a customer claim.

Synthetic studies keep `data_basis = synthetic_example` and `customer_claim = false` even after a consented publish. A synthetic study with no quoted organization and no quoted result can publish after review without consent records, and it stays labeled synthetic.

The blank template (`GET /api/case-studies/template`) is `data_basis = blank_template`, `customer_claim = false`. Suggested metric names are field names, not measured results.

## Quoted organizations and results

- Quoted organizations are the trimmed `company_name` plus `quoted_organizations`. Match is exact after trim.
- Quoted results are `quote` (when `quote` is non-empty), `results_narrative` (when `results` is non-empty), and `metric:<key>` for each metrics key.
- Permission is the full set: every quoted organization must consent, and that consent must permit every quoted result. One missing pair blocks the whole publish.
- Grants store `granted_revision`. A content edit increments `revision`, clears review and publication, and makes older grants stale.

## API

Existing `/api/case-studies` fields and types are unchanged. The response is explicitly `schema_version: case-study.v2` and adds consent, review, synthetic, and claim fields. List responses still use `case_studies` and add `schema_version`.

Workflow routes, all under the same router:

| Method | Path | Permission |
|---|---|---|
| POST | `/api/case-studies/{id}/consents` | admin (`can_admin`) |
| POST | `/api/case-studies/{id}/consents/{consent_id}/revoke` | admin |
| POST | `/api/case-studies/{id}/result-permissions` | admin |
| POST | `/api/case-studies/{id}/result-permissions/{permission_id}/revoke` | admin |
| POST | `/api/case-studies/{id}/submit-review` | admin |
| POST | `/api/case-studies/{id}/review` | reviewer (`can_review`) |
| POST | `/api/case-studies/{id}/publish` | admin |
| POST | `/api/case-studies/{id}/withdraw` | admin |

Create, update, and delete stay admin-only. Read stays any signed-in member. Another workspace's id returns 404. Original 404 details on the CRUD routes stay strings.

Workflow failures use `api-error.v1`: `code`, `message`, `msg`, `request_id`, `retryable`, `field_errors`. `msg` is there so the existing web error helper still shows the message.

`POST .../publish` accepts `Idempotency-Key`. The stored key is scoped as `case-study:{workspace_id}:{case_id}:{header}`. A failed attempt is cached as that failure. After the missing consent is added, publish again without that key, or with a new key. A successful publish retried with the same key, or with no key, returns the same record and does not change `published_at`.

## UI

`apps/web/app/dashboard/case-studies/page.tsx` is the authoring screen. It is linked from the compliance section of the sidebar. Claim labeling goes through `apps/web/lib/caseStudyConsumer.ts` (`parseCaseStudyResponse`, `displayLabel`). The page does not decide on its own that a row is a customer claim.

## Persistence

Migration `076_case_study_consent` (revises `075`):

- Adds the case-study columns and `case_study_organization_consents` / `case_study_result_permissions`.
- Composite foreign keys require the consent's `(case_study_id, workspace_id)` to match the case study, and a result permission's consent to belong to that same case study.
- Backfill copies `status` and `published_at` into `pre_consent_status` and `pre_consent_published_at`, sets `customer_claim = false`, and moves previously published rows back to `draft` with `published_at` cleared. Those rows had no consent evidence.

Rollback (`alembic downgrade 075`):

- Restores `status` and `published_at` from the snapshot where `pre_consent_status` is set.
- Drops both consent tables and the new columns. Consent rows created after this migration do not survive the downgrade.
- `alembic upgrade head` again treats any published row as unconsented and clears it, so a dropped consent cannot come back as a customer claim.

Runbook, from `apps/api`, with `DATABASE_URL` pointing at the target database and `TRUST_COPILOT_TESTING` unset for a normal app database:

```text
python -m alembic downgrade 075
python -m alembic upgrade head
```

Do not put the database password in tickets, logs, or acceptance artifacts.
