# TC-25-005 Consent-backed case study authoring publication

Status: implemented on `tc/ca/TC-25-005`. PR #25 is open. Master `1a0e614` is merged.

## What changed

A case study can be drafted, submitted for review, approved, and published. Setting `status` to `published` on `PATCH /api/case-studies/{id}` no longer publishes. Publish checks the current revision:

- Every quoted organization has an active consent for that revision.
- Each of those consents permits every quoted result.
- If any consent or permission is missing, nothing is published.

A row is a customer claim only when it is published, not synthetic, review-approved, and fully consented. `customer_claim` is derived from those stored facts. A column set by hand, a seed, or a fixture cannot make the API or the UI show a customer claim.

Synthetic studies keep `data_basis = synthetic_example` and `customer_claim = false` even after a consented publish. A synthetic study with no quoted organization and no quoted result can publish after review without consent records, and it stays labeled synthetic.

The blank template (`GET /api/case-studies/template`) is `data_basis = blank_template`, `customer_claim = false`. Suggested metric names are field names, not measured results.

## Quoted organizations and results

- Quoted organizations are the trimmed `company_name` plus `quoted_organizations`. Match is exact after trim.
- Quoted results are `quote` (when `quote` is non-empty), `results_narrative` (when `results` is non-empty), and `metric:<key>` for each metrics key.
- Permission is the full set: every quoted organization must consent, and that consent must permit every quoted result. One missing pair blocks the whole publish.
- Grants store `granted_revision`. A content edit increments `revision`, clears review and publication, and makes older grants stale.

## API

Existing `/api/case-studies` fields and types are unchanged. The response is explicitly `schema_version: case-study.v2` and adds consent, review, synthetic, and claim fields. List responses still use `case_studies` and add `schema_version`.

Workflow routes, all under the same router:

| Method | Path | Permission |
|---|---|---|
| POST | `/api/case-studies/{id}/consents` | admin (`can_admin`) |
| POST | `/api/case-studies/{id}/consents/{consent_id}/revoke` | admin |
| POST | `/api/case-studies/{id}/result-permissions` | admin |
| POST | `/api/case-studies/{id}/result-permissions/{permission_id}/revoke` | admin |
| POST | `/api/case-studies/{id}/submit-review` | admin |
| POST | `/api/case-studies/{id}/review` | reviewer (`can_review`) |
| POST | `/api/case-studies/{id}/publish` | admin |
| POST | `/api/case-studies/{id}/withdraw` | admin |

Create, update, and delete stay admin-only. Read stays any signed-in member. Another workspace's id returns 404. Original 404 details on the CRUD routes stay strings.

Workflow failures use `api-error.v1`: `code`, `message`, `msg`, `request_id`, `retryable`, `field_errors`. `msg` is there so the existing web error helper still shows the message.

`POST .../publish` accepts `Idempotency-Key`. The stored key is scoped as `case-study:{workspace_id}:{case_id}:{header}`. A failed attempt is cached as that failure. After the missing consent is added, publish again without that key, or with a new key. A successful publish retried with the same key, or with no key, returns the same record and does not change `published_at`.

## UI

`apps/web/app/dashboard/case-studies/page.tsx` is the authoring screen. It is linked from the compliance section of the sidebar. Claim labeling goes through `apps/web/lib/caseStudyConsumer.ts` (`parseCaseStudyResponse`, `displayLabel`). The page does not decide on its own that a row is a customer claim.

## Persistence

Migration `tc25005_case_study_consent` in `apps/api/alembic/versions/tc25005_case_study_consent.py` (revises `tc11001_model_outcome_codes`):

- Revision id is `tc25005_case_study_consent`, not `076`. Master head after `1a0e614` (PR #16, which follows PR #8) is `tc11001_model_outcome_codes`. This revision's `down_revision` is that id. PR #30 (`tc25011`) also re-parents onto the current head. Whichever of PR #25 and PR #30 merges second re-parents onto the other.
- Adds the case-study columns and `case_study_organization_consents` / `case_study_result_permissions`.
- Composite foreign keys require the consent's `(case_study_id, workspace_id)` to match the case study, and a result permission's consent to belong to that same case study.
- The upgrade never deletes a case study row. It only unpublishes. Backfill copies `status` and `published_at` into `pre_consent_status` and `pre_consent_published_at`, sets `customer_claim = false`, and moves previously published rows back to `draft` with `published_at` cleared. Those rows had no consent evidence.
- Reads do not reconcile or commit. `GET /api/case-studies` and `GET /api/case-studies/{id}` leave the stored row, including `updated_at`, unchanged. The response still fails closed in memory.

Rollback (`alembic downgrade tc11001_model_outcome_codes`) is lossless while the database stays on that parent:

- Before anything is dropped, consent rows, permission rows, and per-row review, revision, and content fingerprint metadata are copied into `case_study_consent_archive`, `case_study_result_permission_archive`, and `case_study_review_archive`. Those archive tables have no foreign keys. The fingerprint covers every parent-revision content column: title, company name, industry, company size, challenge, solution, results, quote, quote attribution, and metrics JSON. Quoted organizations are archived too. `synthetic` is not on the parent revision, so it is archived with the review row and is not part of the match. That column list is frozen in the migration and the migration does not import the application.
- `status` and `published_at` are restored from the snapshot only for rows that are still in the exact state the upgrade left them in (`review_status = none`, `revision = 1`, no claim, no publication, not synthetic, `data_basis = unverified`, no reviewer, no quoted-organization json, and the status the upgrade wrote). A later workflow change, including `in_review`, is not overwritten with the snapshot.
- The live consent and permission tables and the new columns are then dropped. The case study rows stay. The archive tables remain only for that downgraded window.

`alembic upgrade head` after that downgrade loads the archives back into the live tables, including original consent and permission ids, then drops the three archive tables. Published status is restored only when the content fingerprint still matches and the live status still matches the archived status. A row whose downgrade restored the pre-consent snapshot is compared to `pre_consent_status` and `pre_consent_published_at` instead, so a second round trip still sees revision 1 and can restore that snapshot again. If the status or the fingerprint changed on the parent revision, the row comes back as `draft` with `published_at` null, `publication_authorized` false, `review_status` `none`, reviewer fields cleared, and `revision` set to the archived revision plus one, so the old consent does not cover it. A row with no restored active consent is not published and is not a customer claim. Rows created while the database was on the parent revision are backfilled like a first upgrade: a published row with no consent is unpublished, and no case study row is deleted.

Runbook, from `apps/api`, with `DATABASE_URL` pointing at the target database and `TRUST_COPILOT_TESTING` unset for a normal app database:

```text
python -m alembic downgrade tc11001_model_outcome_codes
python -m alembic upgrade head
```

Do not put the database password in tickets, logs, or acceptance artifacts. Do not downgrade through `tc11001_model_outcome_codes` to `075` unless you also mean to undo the framework-catalog and model-outcome migrations.

## Logged follow-ups (no extra product code)

- TC-25-005b: a separate-reviewer rule so an admin cannot approve their own study. Not implemented. An admin still has `can_review`.
- Free-text organization mentions inside challenge, solution, quote, or results do not by themselves open a consent requirement. Consent runs on `company_name` and `quoted_organizations`. That is a documented limitation.
- Archive retention: the three archive tables exist only while this revision is downgraded. They hold consent, permission, review, and fingerprint rows so the upgrade can restore them. Re-upgrade drops the tables after that restore. They are not a long-term audit store. Copy them before upgrading again if that window's copy must be kept.
- `GET /api/case-studies/template` is unauthenticated. The body is the static blank template (`blank_template`, `customer_claim` false, no customer). That is acceptable.
- TC-25-005a, added by the coordinator on round 3 and not implemented here: a GET of a stale row should report the effective status rather than the stored `published`. Content `PATCH` edits should be written to the audit log. Per-org attribution, logged earlier under the same follow-up id, is also still not implemented.

## Coordinator rulings (2026-10-27)

- A named organization alone counts as a customer claim. In this schema that is `company_name` or `quoted_organizations` (the name, or the logo identification recorded there). Consent is required before that row can be published as a claim, even when it has no quote and no result.
- The consent rule stays the full set of quoted organizations × quoted results. Follow-up ticket TC-25-005a is per-org attribution: each result belongs to one organization and needs that organization's consent. TC-25-005a is not implemented here.
- `consent_reference` stays an operator reference string. Signed evidence is TC-26-015. This ticket does not store or verify a signed document.
- The workflow routes and `/dashboard/case-studies` are in `docs/acceptance/scope-freeze.md`, labelled scope-freeze amendment approved by coordinator 2026-10-27.
- Claims-register row A4 is updated in this branch. The claim text is: naming an organization is a customer claim and requires consent before publishing. It is Supported only for the blank template and the consent gate. Signed consent evidence stays with TC-26-015, and reviewer signoff is still open.
