# TC-04-007a: count forgot-password attempts before user lookup

Follow-up of TC-04-007. Baseline reconciliation batch 11 (PR #315) recorded the gap in `docs/release/verification/TC-04-007.md` on `docs/baseline-recon-batch11`, against master `2647b2e2ad5ef575ee354a3c9c92a8bd16680dbc`. Closed unmerged #161 used this id earlier. That branch is not on master.

## Problem

`POST /api/auth/forgot-password` checked `reset:ip`, loaded the user, and called `record_attempt` only when that row existed (`apps/api/app/api/routes/auth.py` on `2647b2e`, lines 781-787). Eleven requests for a known address became 429. The same eleven requests for an unknown address stayed 200 with `If that email is registered, you will receive a reset link.` The status split is an account-enumeration side channel. The 200 text was already the same.

## What this change does

The handler still refuses when `reset:ip` is already at the limit, then records the attempt, then loads the user. A missing row returns the same generic 200 and consumes the same IP window. Request 11 is 429 for both, with `Too many requests. Try again later.` The route has an IP key only. No per-email key was added. The limiter backend, the limit (10 in 60 seconds), and both response bodies stay as they were.

`resend-verification` already records its IP key and its email key before the user lookup (`auth.py` lines 542-547). A known address and an unknown address already share that window. That handler is unchanged.

`verify-invite-code` keys the window by client IP and email. An empty code is recorded before the lookup. An unknown address and a wrong code both miss, both record, and both return 400 `Invalid email or verification code`, then 429. A matching code returns the token. That is not the known-versus-unknown status split, so that handler is unchanged.

With `TRUST_COPILOT_DEV_RETURN_RESET_URL` set outside production, a known address still includes `reset_url`. Production keeps that flag off. This change leaves that development body in place.

## Acceptance criteria

1. Eleven forgot-password requests for a known address and eleven for an unknown address, each from an empty `reset:ip` window, produce the same status sequence and the same bodies: ten generic 200 responses, then one 429.
2. `apps/api/tests/release/test_forgot_password_enumeration.py` fails on the unfixed handler and passes after this change.
3. No migration, limiter-backend change, CI change, or gate change.
