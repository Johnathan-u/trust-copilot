# TC-21-001 Licensed versioned framework catalog enablement

**Status:** scaffold implemented. Every advertised framework is **BLOCKED** pending content-rights decision **TC-01-007**.

This ticket does not load, paste, or invent framework control text. ISO and HITRUST synthetic `DEV` keys, and the development seed catalog, are dev/test data. They are not a production catalog and cannot be enabled as one.

TC-01-003 is an E01 legal/rights ticket. For this engineering change the dependency is satisfied by the scaffold-only scope: the mechanism exists, and no framework content is delivered. E01 still gates release, not this change.

## Advertised catalogs

These keys are the whole production catalog surface. Each one has a catalog version slot, source provenance, a rights/licence status, and an enablement state.

| Catalog key | Display name | Rights | Licence | Enablement |
| --- | --- | --- | --- | --- |
| `SOC2` | SOC 2 | `blocked_pending_rights` | `not_cleared` | `blocked` |
| `HIPAA` | HIPAA | `blocked_pending_rights` | `not_cleared` | `blocked` |
| `ISO27001` | ISO 27001 | `blocked_pending_rights` | `not_cleared` | `blocked` |
| `NIST_CSF_2` | NIST CSF 2 | `blocked_pending_rights` | `not_cleared` | `blocked` |
| `NIST_800_53_R5` | NIST 800-53r5 | `blocked_pending_rights` | `not_cleared` | `blocked` |
| `NIST_800_171_R3` | NIST 800-171r3 | `blocked_pending_rights` | `not_cleared` | `blocked` |
| `SIG` | SIG | `blocked_pending_rights` | `not_cleared` | `blocked` |

| `HITRUST` | HITRUST | `blocked_pending_rights` | `not_cleared` | `blocked` |

Bare `NIST` is not a production catalog. The three NIST rows above are separate and blocked.

There is no environment variable or database flag that clears rights. `production_catalog` is forced false, and a PostgreSQL check constraint rejects `production_catalog = true` and `enablement_state = 'enabled'`.

New scaffold rows store `rights-pending` in the existing `version` column. That sentinel is not a standards-body publication. The response field `content_version` is null until a later rights decision records a licensed version.

## API

Mounted in `apps/api/app/main.py` at prefix `/api`.

- `GET /api/compliance/frameworks` (`require_can_review`)
- `POST /api/compliance/frameworks/enable` (`require_can_admin`)

The list remains a JSON array. Each item still has `id`, `name`, `version`, and `created_at`. Additive fields include `catalog_key`, `source_provenance`, `rights_status`, `licence_status`, `enablement_state`, `catalog_kind`, `production_catalog`, `rights_ticket`, `contract_version` (`framework-catalog/v1`), `content_version`, `dev_test_only`, and `blocked_reason`.

`GET /api/compliance/frameworks` is read-only. It does not insert or update catalog rows. A missing advertised catalog is projected in memory as blocked. A tampered stored rights value is still reported as blocked; the stored row is left unchanged. The list does not return control titles, descriptions, or keys.

`POST /api/compliance/frameworks/enable` writes only an audit event. It does not create or rename catalog rows. The event snapshots `catalog_key` and `name`. Foreign keys on that table use `ON DELETE SET NULL`, not cascade.

Customer-facing errors and `blocked_reason` say "Pending content licensing". The ticket id `TC-01-007` stays in logs and in this document. The rights gate is enforced on enablement. Before any catalog can be enabled, every reader of `enablement_state` must apply the same gate. This list endpoint already projects advertised rows as blocked.

The enable body is still `{ "name": string, "version"?: string }`. Extra properties are rejected. A refusal uses `framework-catalog-error/v1` inside FastAPI `detail`:

- `code`, `message`, `request_id`, `retryable`
- optional `field_errors`
- `catalog_key`, `rights_status`, `licence_status`, `enablement_state`, `rights_ticket`
- `partial_failure` and `steps` when the audit write fails

| Situation | HTTP | `code` |
| --- | --- | --- |
| Empty name | 400 | `framework_name_required` |
| Name is not an advertised catalog | 400 | `framework_not_advertised` |
| Rights not cleared | 409 | `framework_rights_not_cleared` |
| Synthetic DEV key or dev version (`CSF-dev`, `dev-themes`, `HITRUST-DEV-*`, `ISO-DEV-*`, `DEV-*`) | 409 | `framework_dev_catalog_not_production` |
| Blocked state saved, audit foreign key failed | 409 | `framework_enablement_partial_failure` |
| Not signed in | 401 | existing auth `detail` string |
| Signed in without admin | 403 | existing auth `detail` string |

Authentication and permission errors stay on the existing auth contract. Catalog refusals are the versioned contract.

Retrying enablement does not create a second production row and does not flip `enablement_state` to enabled. A partial failure still leaves the catalog blocked; a later retry with a valid workspace writes the refusal audit and returns `framework_rights_not_cleared`.

## Migration and rollback

Revision `tc21001_framework_catalog_rights` (`apps/api/alembic/versions/tc21001_framework_catalog_rights.py`), `down_revision` `075`. The revision id is not a bare number, so it does not collide with another branch's `076`. The migration does not import the application package. The catalog constants and helpers it uses are a frozen snapshot inside the revision, duplicated on purpose so a later application change cannot break upgrade or downgrade.

Upgrade adds nullable catalog columns, backfills existing rows, inserts any missing advertised blocked rows, creates `framework_catalog_events`, and adds the production check constraint. Backfill:

- Rows with a synthetic dev version, a `DEV` control key, or a dev-seed name/version plus at least one control become `dev_synthetic` / `dev_only` and do not keep a production `catalog_key`.
- A non-dev row whose name matches an advertised catalog becomes that blocked slot. Its `name` and `version` are not changed, including a blank version. The API display name comes from `catalog_key` through the registry.
- The insert of a missing advertised row is guarded with `WHERE NOT EXISTS`, so a second row is not created for a catalog key or an exact name that is already stored. New rows, and only new rows, use the `rights-pending` version sentinel.
- Any other pre-existing row becomes `legacy_unclassified` and blocked. It is not a production catalog.

Downgrade:

1. Drops the check constraint, the catalog-key unique index, and `framework_catalog_events`.
2. Deletes framework rows with `scaffold_inserted = true` only when they have no `framework_controls` child.
3. Drops the added columns.

A scaffold row that later gained controls is left in place so the foreign key is not broken. After downgrade it is an ordinary `frameworks` row again (`name`, `version`, `created_at` only).
