## Bounded acceptance

One PostgreSQL pytest test owns two actual API/Next process lifetimes and invokes
two dedicated Playwright phases. Requests pass through the real Next proxy,
FastAPI authorization/routes and PostgreSQL. There are no response mocks or
route, dependency, authentication or storage-method replacements.

1. A real reviewer signs in through the login UI. The incoming list excludes a
   different workspace's request and renders an actual `internal_note` row.
   The reviewer creates two replies and approves their exact first revisions,
   then saves a third reply without approving it.
2. Both service processes are terminated and reaped. New API and Next processes
   start, a new browser context begins without cookies, and the reviewer signs
   in again. Complete database reply rows and UI/API body, revision and approval
   fields must survive; the unapproved draft still cannot be sent.
3. Editing the first reply through the UI invalidates its approval. A second
   real signed-in administrator context saves a concurrent revision. The stale UI
   save must receive 409, retain local text, require a reload and explicit review,
   and display the newly saved text beside the retained edit.
4. Sending the second approved reply with the actual unavailable provider
   configuration must report unavailable, preserve zero delivery attempts and
   null delivery timestamps, and prevent a blind UI resend.
5. Missing and foreign request attachment endpoints return the same real 404.
   An owned request without an attachment key returns its specific 404; the UI
   retains local input. An administrator suspends the reviewer through the real
   membership API, and the existing reviewer context receives 403 on another
   attachment download while retaining its input. Full protected request and
   internal-note rows remain unchanged; reply rows retain their expected state.

The socket guard denies a uniquely reserved, non-listening loopback storage
endpoint with synthetic credentials. Actual `StorageClient` construction and
startup bucket initialization remain intact. Startup storage unavailability is
explicitly recorded, and **zero post-readiness storage or external attempts** are
required. This proves negative authorization/missing-metadata paths only; it
does not qualify object storage or an existing object's download.

## Isolation and execution

The fixture uses unique workspaces/users and explicitly tracks inserted IDs,
including any missing startup catalog tags that it seeds itself. Cleanup uses
owned workspace/actor/request IDs and associated notification dedupe keys, then
compares full baseline table hashes. It never resets sequences, disables foreign
keys/triggers, deletes a global key-set difference or touches existing volumes.
The unchanged #117 process helpers terminate only owned process groups and reap
their parents; both service ports must stop listening before restart.

Run from `apps/api` with the existing isolated test PostgreSQL and locked web
toolchain/Chromium installed:

```sh
TC_REQUIRE_DB=1 TC_REQUIRE_WEB_TOOLCHAIN=1 python -m pytest tests/release/test_trust_requests_browser.py -q
```

Missing PostgreSQL/toolchain/browser support is a failure, never a skip. The
coordinator owns CI wiring and upload of
`apps/web/playwright-report/trust-requests-restart/` and
`apps/web/test-results/trust-requests-restart/`. Service logs remain temporary;
published reports contain synthetic data, process/attempt counts and assertions,
with no cookies, session credentials, trace, video or screenshot capture.
