## Backend contract

Public JSON and multipart intake share validated ASCII mailbox syntax, 255-character names/subjects and a 1–10,000-character message. NUL and unpaired surrogate text are rejected. Attachment types use the existing allowlist and configured byte limit. The request remains uncommitted until its attachment succeeds. The route allocates the storage key before upload, so even a write-then-timeout failure has a known compensation target. Upload or database failure rolls back the request and attempts blob compensation; database rollback/claim-release and blob deletion are independently protected. A failed deletion logs only its generated opaque storage key for reconciliation; request text, original filenames and backend exception text are not logged. An optional workspace-scoped `Idempotency-Key` replays the same durable response, rejects changed payloads and uses owner-fenced claim completion. Exceptions once COMMIT begins are explicitly uncertain: the route retains the blob and retry claim/response, logs only the generated key and request id, and reports a safe 502. It never deletes an attachment that may belong to a committed row. Same-key replay can recover the committed result; unconfirmed writes require reconciliation. Automatic compensation is limited to proven pre-commit failures. Distributed exactly-once blob storage is not claimed.

Private object access scopes the lookup to the current workspace, returning equal missing/foreign/unscoped 404 responses. GET delete-preview performs no audit write. Current active workspace membership and review permission are rechecked because the signed session role can be stale. API keys use their current database role; they cannot approve as a human. Assignees must be active members of the request's workspace.

Replies are created as drafts. The retained `send_email=true` option explicitly returns 409 without inserting a reply or sending mail. The supported sequence is:

1. POST `/{request_id}/replies` with `body` creates revision 1.
2. PATCH `/{request_id}/replies/{note_id}` with `revision` and `body` edits an unsent draft and invalidates prior approval.
3. POST `/{request_id}/replies/{note_id}/approve` with `revision` records the current human reviewer, timestamp, exact revision and body digest.
4. POST `/{request_id}/replies/{note_id}/send` with `revision` records durable sending intent before invoking the existing email provider. Provider `True` becomes `accepted`; false/exception becomes `uncertain`. `accepted` describes provider acceptance, not recipient delivery. Console/disabled providers are `unavailable` and are not invoked. Repeated `sending`, `accepted`, or `uncertain` sends do not call the provider again.

The SMTP consumer requests the existing sensitive-message path. Failed SMTP delivery logs neither the reply body, subject, recipient nor provider exception text in development or production. This does not change approval requirements, accepted/uncertain outcomes, or no-resend handling. Other provider implementations retain their existing contract.

The notes response exposes revision, approval identity/time and delivery outcome, timestamps and attempt count. Accepted/uncertain/in-flight replies cannot be edited; a new draft is required. Completion requires a persisted reviewed reply with provider acceptance and an acceptance timestamp. Legacy replies retain unknown approval/delivery rather than receiving invented provenance; edit with revision 0 explicitly starts reviewable history.

## Migration and rollback

`tc18001_reviewed_replies` adds nullable intake version and reply provenance fields. API bounds match database checks and VARCHAR bounds; reviewer foreign key/index match ORM metadata. The downgrade saves non-default values in request/note-linked hold tables before removing columns. Re-upgrade restores provenance only when body, note type, parent request, workspace, recipient and subject still match the held fingerprint. Text or delivery context changed by an older binary leaves the new fields null and retains the original provenance in the hold table, requiring fresh review. Parent-row deletion cascades to held metadata. Migration tests execute PostgreSQL DDL transactionally, assert non-default roundtrip and changed-body behavior, and allow future descendant heads.

## Reviewer UI and public intake

The reviewer screen's explicit draft, approve, and send sequence is the TC-15-039a consumer (`apps/web/app/dashboard/trust-requests/page.tsx`, `apps/web/lib/trust-request-consumer.ts`, `apps/web/e2e/release/screen-trust-requests.spec.ts`). TC-15-039b runs that screen through real Uvicorn, Next, and Chromium against PostgreSQL across two process lifetimes in `apps/api/tests/release/test_trust_requests_browser.py` and checks the database rows after each phase. The assignee is read-only text taken from the saved request. Those checks qualify the reviewer UI. They do not qualify live SMTP. "Accepted" remains provider acceptance, not recipient delivery.

Public intake is `POST /api/trust-requests/submit` from `/trust/[slug]`. The form trims the email, name, subject, and message, refuses a blank message, and limits name, subject, and email to 255 characters and the message to 10,000. Those limits match the API. One `Idempotency-Key` is kept for the same trimmed details, including the selected file name, size, and last-modified time, and is sent again after a lost response or an HTTP error. A successful response clears the key. Changing the details starts a new key. The API still treats the header as optional for other clients. When the header is present, a retry returns the stored response and does not insert a second request or upload the attachment again. The same key with a different body returns 409 and the detail `This retry key was already used for a different request.` The form renders only a string. A validation list is not passed into the page; the visitor sees a fixed message and the rejected input is not copied into that message.

An uncertain commit logs `trust intake save outcome requires reconciliation` with `request_id` and `storage_key` and does not delete the blob. A failed pre-commit blob delete logs `trust attachment cleanup requires reconciliation` with `storage_key` only. A failed database rollback or claim release logs `trust intake database cleanup requires reconciliation` with neither identifier. Operators follow `docs/ops/trust-intake-reconciliation.md`. No schema change is added for this gap closure, so there is no new migration or downgrade.
