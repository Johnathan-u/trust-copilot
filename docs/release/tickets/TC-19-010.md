## Inbox behavior

Every personal inbox request rechecks the current active workspace membership and the current role's administrative permission, including workspace-scoped custom roles. Removed or suspended members are denied. List, unread count, mark-one and read-all share the same recipient/admin-only filter. A hidden, foreign or missing notification returns the same 404. Machine API keys retain empty list/count responses and receive 400 `User context required` for either mutation.

Pagination orders by creation time descending, then notification ID descending. Unread count evaluates the same personal read state used in list responses. A retry does not create another receipt or change the first read timestamp. Concurrent broadcast read-all calls count only receipts actually inserted; unique-key conflict handling makes duplicate calls safe. GET requests do not write.

Direct `notify_user` dispatch validates active workspace membership before insertion. A real database rejection rolls back the insertion, and a subsequent valid call can use the session. Existing personal channel preferences stay on TC-19-009's notifications API, which this branch does not edit.

## Approved receipt schema and migration

[Coordinator ruling](https://github.com/Johnathan-u/trust-copilot/issues/85#issuecomment-6504557554) approves `in_app_notification_receipts`, keyed by `(workspace_id, notification_id, user_id)`, with a timezone-aware read timestamp. Composite foreign keys reference the notification and workspace membership in that same workspace. Additive unique constraints on the parent key columns make those references enforceable; no compatible unique constraint existed at the implementation base.

For a legacy `user_id=NULL` broadcast, effective read state is the caller's receipt OR the existing legacy `is_read` flag. Historical read broadcasts stay read. No receipt is backfilled. Mark-one/read-all create only the caller's needed receipts and never change the legacy flag. Existing per-user rows retain their `is_read` field.

Revision `tc19010_inbox_receipts` now follows the actual landed `tc17004_faq_review` from master `58c9e563d60c19c20225a1c317fc4d85d343ab2e`. The parent/evidence change is separate from pure master merge `b8ca69db04934fbc10fe4f01c61f937cf8553d81`. Coordinator ruling [6511936256](https://github.com/Johnathan-u/trust-copilot/issues/85#issuecomment-6511936256) advances this independent migration ahead of blocked #93/#96; neither is a functional dependency. Any migration landing first requires another actual-parent check.

Upgrade leaves existing notification values unchanged and does not infer historical personal reads. Existing duplicate `(workspace_id, user_id)` memberships fail the added unique constraint; the migration never silently deletes or deduplicates memberships. Before rollout, inspect `SELECT workspace_id, user_id, COUNT(*) FROM workspace_members GROUP BY workspace_id, user_id HAVING COUNT(*) > 1` and resolve any conflict through the owning workflow.

Downgrade copies every receipt and exact timestamp to `in_app_notification_receipts_archive`, then drops the live table and this migration's parent uniqueness constraints. Archive creation refuses to overwrite an existing archive. Re-upgrade restores every archived row in the migration transaction and drops the archive only after successful restoration. Invalid references after parent changes while downgraded fail the transaction and retain the archive; no receipt is skipped. Keep the archive with the database backup and restore the corresponding parents before retrying a blocked upgrade. Do not discard it to force an upgrade. Two downgrade/upgrade cycles with multiple users and nondefault timestamps, unchanged notification snapshots, and invalid-parent restoration are covered by the PostgreSQL regressions.
