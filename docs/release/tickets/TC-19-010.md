# Personal notification inbox and preferences

Status: regression stage; production unchanged. Assigned queue: [coordination issue #85](https://github.com/Johnathan-u/trust-copilot/issues/85#issuecomment-6503307759).

## Intended contract and plan

Only an active current workspace member can read or mark their intended notifications. Mark-one must apply the same admin-only and recipient filter as list/count/read-all. Current role and custom administrative permission must be rechecked. Machine API keys have no personal notification context and cannot mark shared rows. Pagination must be stable at equal timestamps, and unread counts must reconcile after retry and a new database connection. GET never writes.

The notification creation service must refuse foreign, suspended and missing recipients before inserting a row. Existing personal channel preferences remain on the notifications API and are exercised here; that route belongs to TC-19-009 and is not duplicated or edited.

1. Run new PostgreSQL regressions in existing CI; local collection does not prove database behavior.
2. Implement current-membership visibility, mark authorization, stable pagination, and active recipient validation within inbox routes/services.
3. Await the Coordinator ruling before any schema/model changes for legacy shared read state, then implement only the approved contract.
4. Verify API/persisted outcomes, cleanup counts, negative and retry cases; obtain independent review and all required exact-head CI checks before readiness.

## Schema decision pending

Current per-user dispatch creates one row per recipient. Legacy rows may have `user_id=NULL`, so their single `is_read` currently clears the notification for everyone when one user reads it. Two regression cases capture personal semantics for these shared rows.

[Pre-migration request](https://github.com/Johnathan-u/trust-copilot/issues/85#issuecomment-6503913122) proposes a per-user receipt table with same-workspace references and read timestamps. GETs would join without writing, while mark-one/read-all create only the current member's receipts. No historical personal receipt would be inferred from the old shared flag. The migration/model portion remains blocked pending approval and scheduling; no schema file is added in this regression commit.
