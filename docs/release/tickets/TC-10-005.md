# TC-10-005 Coordinate transaction job enqueue and storage writes

**Status:** implemented. No migration. No outbox table. `alembic heads` stays the single head that `origin/master` already had.

Evidence: [`artifacts/acceptance/TC-10-005/`](../../../artifacts/acceptance/TC-10-005/README.md).

The job queue is the `jobs` table. Document and questionnaire uploads already insert the row and the job in one transaction (`enqueue_job(..., commit=False)`), then commit once. Export enqueue only inserts a job. The export object is written later, by the worker, and the export row commits after that write.

## What can still diverge

| Path | Object | Database | If the commit fails | If the job is missing |
|---|---|---|---|---|
| `POST /api/documents/upload` | raw object, then the document and `index_document` job | one transaction | roll back; delete the object when no row references it | a committed `uploaded` document is re-queued |
| `POST /api/questionnaires/upload` | raw object, then the questionnaire and `parse_questionnaire` job | one transaction | same | a committed `uploaded` questionnaire is re-queued |
| Trust-request attachment | object, then a second commit of the attachment columns | request row is already committed | roll back the attachment columns; delete the object when nothing references it | no job on this path |
| `run_export` | deterministic `exports/{workspace}/job-{id}{ext}`, then `export_records` | one commit | roll back; delete the object when nothing references it | the export job is the row that was already claimed |

A failed delete is logged and left in place. The sweep removes it later. A delete is refused when a row still names that key, or when the reference read itself fails.

## Sweep

`reconcile_orphan_objects` lists the raw and export buckets. It deletes a key only when all of the following are true:

* The key is `raw/{workspace}/…`, `trust-requests/{workspace}/…`, or `exports/{workspace}/…`. Any other layout is kept.
* No document, questionnaire, export, trust-request attachment, or evidence `content_ref` uses it. Soft-deleted rows count. A reference in any workspace counts.
* No queued or running job has that `input_version` or a payload `storage_key`. A completed or failed job does not keep an otherwise unreferenced object.
* The object store's `LastModified` is strictly older than the grace. An equal timestamp is kept. A missing timestamp is kept.

The reference load and the listing both finish before any delete. Immediately before each delete the key is read again, so a row that landed in that window is spared. A delete error is recorded and the sweep continues. Running it again deletes nothing that is already gone. Dry-run reports the same candidates and deletes nothing.

Object age is the store clock compared with the process UTC clock. There is no new column. `STORAGE_ORPHAN_GRACE_SECONDS` defaults to 7200 and is clamped to 60–604800. An invalid value falls back to 7200, then that clamp. A value below `WORKER_JOB_MAX_RUNTIME_SEC` is logged: an export can upload its object before the row commits.

Raw upload keys stay random. A content-hash key would let a rolled-back second upload of the same bytes delete the live object. The sweep lists keys instead of recomputing them. Export keys were already one object per job.

## Missing jobs

`reconcile_missing_jobs` queues `index_document` for an `uploaded` document, and `parse_questionnaire` for an `uploaded` questionnaire, when no queued or running job of that kind already names the row. A questionnaire with no storage key is skipped. Each new job commits on its own, because the domain row is already committed. One failure is logged and the next row is still attempted. The same call again does not insert a second job.

The worker startup hook does both, then sweeps. The name of that hook is still `enqueue_missing_index_jobs`. An idle worker sweeps again only after a full grace period. A storage outage is logged. It does not stop the claim loop.

## Runbook

There is no HTTP route. An admin, an editor, and an anonymous caller all get 404 for `/api/storage/reconcile` and `/api/admin/storage-reconcile`.

From `apps/api`, with the worker's environment:

* **See orphans, delete nothing.** `python -m app.services.storage_reconcile`
* **Delete eligible orphans in one workspace.** `python -m app.services.storage_reconcile --execute --workspace-id 123`
* **Also queue uploaded rows that have no job.** add `--enqueue-missing`. That flag writes jobs even on a dry-run. It does not delete objects unless `--execute` is also present.
* **Exit 0.** Dry-run, or every delete succeeded.
* **Exit 1.** At least one delete failed. Those objects are still there. Run it again after the storage error is fixed.
* **Exit 2.** The listing or the reference read failed. Nothing further was deleted.

A workspace filter only chooses prefixes. It does not ignore a reference that belongs to another workspace. Do not set the grace below the longest export you expect to have in flight. Raise it if the object store clock runs ahead of the worker.

## Config

| Variable | Default | Clamp | Meaning |
|---|---|---|---|
| `STORAGE_ORPHAN_GRACE_SECONDS` | `7200` | `60`–`604800` | Unreferenced objects younger than this are kept. |

`docker-compose.prod.yml` passes it to the worker. `.env.example` documents it. The generated table in `docs/release/config-contract.md` includes it.

## Tests

`apps/api/tests/release/test_enqueue_consistency.py`. In-memory storage, the side `*_test` database, no network, no real keys. The fixture records `max(id)` and counts for every table it writes, including `audit_events` and `user_sessions`, deletes rows above that id, and asserts the counts. It does not call `setval`. The fake store is cleared at the end of the test.

The file does not import on master: `app.services.storage_reconcile` is not there. The upload routes on master already roll the row back and best-effort delete the object. They do not sweep a failed delete, they do not refuse that delete when another row holds the key, they do not re-queue a questionnaire that has no parse job, and a failed export commit leaves the object.

## Choices

* No outbox and no new column. Listing plus the existing key columns is enough.
* Random raw keys, not content hashes.
* Grace is strict. The boundary instant is kept.
* A failed reference read never deletes.
* No new route, so there is no new permission to grant. The CLI is the operator path and it dry-runs unless `--execute` is set.
* Trust-request attachments and evidence content refs are protected even though the acceptance text names documents, questionnaires, and exports. Dropping them would delete a live original.
* Completed jobs do not protect an object. Otherwise a finished job would keep an orphan forever.
