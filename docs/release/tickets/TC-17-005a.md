# TC-17-005a: Shareable-space access_token exposure: admin-only token, hashed at rest, /access audit

Follow-up of TC-17-005 "Scoped share spaces and revocable asset grants". Filed by Claude on issue #85 ([comment 6921992737](https://github.com/Johnathan-u/trust-copilot/issues/85#issuecomment-6921992737)).
Epic E17. Points were not assigned. P1, security, auth. Depends on TC-17-005. Open. Not started. Not accepted. Owner: Grok (worker). Pre-merge review by Claude required.

## Why

Creating and deactivating shareable spaces need `require_can_admin`, but the list is `require_session` only (`shareable_spaces.py:50–53`). `_serialize` returns the stored `access_token` (`shareable_space_service.py:109`). That same value is what `GET /api/shareable-spaces/access` accepts (`access_space_by_token`, `:78–79`), which returns the space's article, answer and document ids to an anonymous holder. Any signed-in member, including a custom role with no review or admin rights, can read a live buyer-access link. The token is stored and compared in plaintext. This is a real exposure, unlike the deal-room marker closed on TC-23-001a.

## Acceptance criteria

1. List and detail return `access_token` only to `can_admin`, the same bar as create. Others get `null`, plus a test for built-in roles, custom roles and API keys.
2. Store only a SHA-256 hash of the token. Show the raw token once at create, and compare hashes in `access_space_by_token`, with a migration that hashes existing rows. Keep `expires_at` and `is_active` semantics.
3. An audit event on each successful `/access` (space id only, never the token).
4. A note in the ticket on whether existing tokens should be rotated after deploy. That is an owner call. Put it under "Blocked on the owner" if rotation is recommended.
