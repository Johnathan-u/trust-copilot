# TC-17-005a: shareable-space access tokens are readable by any signed-in member

Child of TC-17-005. Filed by Claude in #85 ([comment 6921992737](https://github.com/Johnathan-u/trust-copilot/issues/85#issuecomment-6921992737)).
Epic E17. Points were not assigned. P1, security, auth. Closed by the coordinator. Not an original-parent acceptance.

## Acceptance criteria

1. List and detail return `access_token` only to `can_admin`, the same bar as create. Others get `null`. Tests cover built-in roles, custom roles, and API keys.
2. Store only a SHA-256 hash of the token. Show the raw token once at create, and compare hashes in `access_space_by_token`, with a migration that hashes existing rows. Keep `expires_at` and `is_active` semantics.
3. An audit event on each successful `/access` (space id only, never the token or its hash).
4. A note on whether existing tokens should be rotated after deploy. That is an owner call.

## Implementation notes

There is no `GET /api/shareable-spaces/{id}` route. `get_space` is the detail serializer. It redacts the same way as the list. A request for that path stays 404 or 405 and does not return a token.

`GET /api/shareable-spaces` stays on `require_session` (`apps/api/app/api/routes/shareable_spaces.py:57`). `_caller_can_admin` (`shareable_spaces.py:50`) uses `_resolve_permission` for `can_admin`, the same check as `require_can_admin`. Callers who pass get `has_access_token`. Everyone else does not get that field. `access_token` on list, detail, deactivate, and the public space object is JSON `null` (`shareable_space_service.py:142-161`). The raw token is returned only from `POST /api/shareable-spaces` (`shareable_space_service.py:49-68`), which stays `require_can_admin`. After that response, the raw token is not stored, so an admin cannot read it back. `has_access_token` is true when `token_hash` is set.

The stored credential is the SHA-256 hex digest of the UTF-8 token (`shareable_space_service.py:21-26`). `access_space_by_token` looks up `token_hash` and confirms the match with `hmac.compare_digest` (`shareable_space_service.py:28-33` and `:105-110`). A row that still has plaintext in `access_token` and a null hash is not accepted. Empty and overlong presented tokens are rejected before the query. `is_active` and `expires_at` are checked in the same order as before. Expired, deactivated, and unknown tokens do not write an audit.

Migration `tc17005a_share_token` revises `question_cell_mapping`, the single Alembic head on master when this branch was cut (`apps/api/alembic/versions/tc17005a_share_token.py:24-25`). Upgrade adds nullable `token_hash`, unique index `ix_shareable_spaces_token_hash`, copies the digest of each non-null `access_token`, and sets `access_token` null. It does not change `expires_at` or `is_active`. Downgrade drops `token_hash`. It cannot rebuild the raw tokens, so `access_token` stays null and previously issued links stop working on the previous release. That downgrade is lossy. Re-upgrade does not mint replacements. The revision does not import the application package. `alembic heads` is that one revision.

A successful `GET /api/shareable-spaces/access` calls `persist_audit` with action `shareable_space.accessed`, `resource_type` `shareable_space`, and both `resource_id` and `details.space_id` set to the space id (`shareable_space_service.py:129-138`). `user_id` and `email` stay null. The log line is the space id only.

The hash change did not add a web caller of `GET /api/shareable-spaces`. The deals page `access_token` is the unstored room marker from TC-23-001a and is unchanged. AC4 adds the admin list at `/dashboard/shareable-spaces`, which calls that list and `POST /api/shareable-spaces/{id}/rotate`. A null list token is still never rendered. `web-release-e2e` still covers the deals screen.

## Blocked on the owner

Rotate every live shareable-space token after this deploy.

The migration keeps a previously issued raw token working. It stores the hash of the value that was already in the database, and `/access` still accepts that same raw token. It does not invalidate copies. Before this change, `GET /api/shareable-spaces` returned the stored plaintext to every signed-in member, including a custom role or API key with no admin rights, and the database held that plaintext. Anyone who listed spaces, and any backup or log of those responses, should be treated as holding a live buyer link until the space expires or is deactivated.

AC4 remains an owner step for live spaces. [Comment 6929751304](https://github.com/Johnathan-u/trust-copilot/issues/85#issuecomment-6929751304) records the owner's approval on 2026-11-16 to rotate every space that was live before the hash change. The note this child shipped with was to deactivate each live space and create a new one. That comment replaces that route with a rotation that keeps the space id, and the owner sends each buyer the new link after it lands. The mechanism is `POST /api/shareable-spaces/{id}/rotate`, so the space id and any deal `room_id` stay put. The procedure is `docs/ops/shareable-space-token-rotation.md`. This file does not rotate tokens, does not accept TC-17-005 or TC-17-005a, and does not complete AC4. AC4 stays open until the owner confirms the live spaces were rotated and each buyer has the new link.
