# TC-07-006 — Reject oversized uploads before buffering

Status: implemented on this branch. This note does not accept the ticket. Independent review is still open. No migration and no tracker edit.

Evidence: [artifacts/acceptance/TC-07-006/README.md](../../../artifacts/acceptance/TC-07-006/README.md).

## Behavior

Document, questionnaire, and trust-request uploads share `read_bounded_upload` in `apps/api/app/services/file_service.py`. It reads at most `settings.max_upload_bytes` (the `MAX_UPLOAD_BYTES` setting, default `50 * 1024 * 1024`, which is 52428800). The next byte, or a chunk that already crosses the cap, raises HTTP 413 and is not appended. The rest of a larger body is not read.

`FileService.upload_raw` uses that reader. Document upload calls `upload_raw` and did not need its own read. Questionnaire upload no longer calls `file.file.read()`. After the size check, and before the extension check, it runs the existing workbook refusal so a macro `.xlsm` still returns that checker's detail and stores nothing. Trust intake (`_persist_intake`) uses the same reader. Its 413 detail stays `File is too large.` A whole number of MiB is still `File exceeds max size (50MB)`. Any other cap names the byte count, so a limit under 1 MiB is not reported as `0MB`.

`upload_trust_request_attachment` is not used by a route. The upload log tests and TC-07-011 describe it, so it now calls the same reader instead of being deleted.

A size rejection logs `size_bytes` as the number of bytes observed before the read stopped (the cap plus the one probe byte, or the length of a chunk that over-delivered). It does not log the unread remainder. `tests/test_tc07011a_upload_log_redaction.py` expects `size_bytes=9` for a 10-byte body and an 8-byte cap.

The 413 is raised before a document, questionnaire, trust request, or job row is inserted and before `storage.upload`. An exception during the read takes the same path: the route rolls back and does not store an object. A client that disconnects while the multipart body is still arriving never reaches that insert.

## Proxy

Production Caddy (`infra/caddy/Caddyfile.production`) sets `request_body { max_size {$MAX_UPLOAD_BYTES:52428800} }` on `handle /api*`. `docker-compose.prod.yml` passes `MAX_UPLOAD_BYTES` into the Caddy container. `deploy.sh` uses `--env-file .env.production`, so Caddy and the API see one value. Unset stays 52428800.

The Next.js proxy (`apps/web/app/api/[[...path]]/route.ts`) reads `MAX_UPLOAD_BYTES` on each request (`apps/web/lib/upload-limit.ts`). A `Content-Length` above the cap returns 413 and does not read the body. Otherwise the body is streamed with `duplex: 'half'` through a counter that does not forward the chunk that would pass the cap. The default is the same 50 MiB. A non-numeric or non-positive value fails closed (every non-empty body is 413).

The configuration note is in `docs/release/config-contract.md` and `.env.example`.

## Tests

From `apps/api`:

```sh
python -m pytest tests/release/test_upload_stream.py -q
```

The file posts just under, exactly at, and just over a lowered cap to `/api/documents/upload`, `/api/questionnaires/upload`, and `/api/trust-requests/submit`. Over the cap is 413, and no document, questionnaire, trust request, job, or stored object is left. It also drops the client mid-body and raises during the read. Direct reads assert the stream is not drained and that the overflow is not retained. The web unit test is `apps/web/tests/unit/api-proxy.test.ts`.

## Rollback

Revert this change. There is no schema change and no backfill. After revert, document and questionnaire uploads buffer the whole body before 413, the proxies do not enforce the cap, and an interrupted read is again untested.
