# TC-14-005 — Loading, empty, error, retry, and partial success

## Behavior

Dashboard reads no longer treat a failed response as an empty list, and a skeleton is not the only feedback while a request is still pending.

`presentHttpFailure()` in `apps/web/lib/api-error.ts` maps a failed read to one of five kinds: offline, not available (HTTP 403), not found (HTTP 404), server (HTTP 5xx), and a generic rejected state for other unsuccessful responses. The title and description are fixed strings. They do not include the status code, and they do not repeat the response body.

Shared components in `apps/web/components/ui` use the existing `--tc-*` tokens:

- `LoadingState` shows a skeleton immediately and sets `aria-busy`. After 8 seconds it replaces the skeleton with "This is taking longer than usual" and a Try again button. That region is `role="status"`. Focus moves to the heading, and the next Tab stop is Try again.
- `EmptyState` is only for a successful payload with nothing to list. It can include an action. It is not an alert.
- `ErrorState` is `role="alert"`. The word "Error" is text, and the heading names the kind. Try again is a button.
- `PartialSuccess` is used when at least one section loaded and another failed. Loaded sections stay on the page. Each failed section has its own Try again button. If the main section failed and every other section is empty or still failed, the page shows `ErrorState` instead, because there is nothing else to show.

The dashboard home loads shortcuts and security notices separately. A successful empty shortcut list offers Open documents. HTTP 500, 403, 404, and a dropped connection each show their own error. A hung shortcut request shows the slow state, and Try again loads the list when the service answers. If notices fail and shortcuts succeed, the shortcuts stay and the notice failure is announced.

The signed-in shell uses the same loading and error states for the session request. HTTP 401 still sends the person to login. Any other session failure shows the error state and does not draw an empty workspace. The notification count is omitted when that request fails, instead of showing zero. Search does not report "no results" for a failed search.

List pages in the dashboard, including documents, questionnaires, exports, requests, members, trust articles, audit, notifications, coverage, and the Gmail and Slack connections, use the same rule: a non-success response is an error or a partial success, not an empty collection. Route-level `loading.tsx` and the dashboard error boundary use the same timeout and error state.

`prefers-reduced-motion: reduce` turns off the skeleton pulse.

## What this ticket does not change

No database migration or backfill. Rollback is reverting this change. Reviewer signoff is pending a reviewer other than the implementer.

Onboarding's create-workspace submit path is unchanged. That page does not load a list, and a parallel change owns its submit errors.

`formatApiErrorDetail()` is unchanged. Mutation messages that already use it, including notification policy updates, still use that helper. Load failures do not.

The public trust page is outside the signed-in shell and is unchanged.

## Ambiguities resolved

- Master had moved past `6f620b1` to `8ab5e3f`. This branch starts from that master. `6f620b1` is an ancestor.
- HTTP 401 on the session request stays a redirect to login. A 401 on a section inside the shell uses the generic rejected copy, not an empty list.
- HTTP 400 and 422 use the same generic rejected copy. They are not shown as empty.
- A 200 body that is not a list is an error, not an empty list.
- A failed primary section plus a successful empty secondary is a full error. Partial success requires something that actually loaded, or a real empty primary beside a failed secondary.
- The skeleton timeout is 8 seconds.
- Copy does not say which permission failed, and it does not quote the server's detail string.
