# TC-18-002 — outbound vendor requests

Status: merged. The backend lifecycle landed in #86. The dashboard lifecycle consumer landed in #118. Create, send, and resend use the idempotency owner fence that landed in #202. This note records that contract, the real-API browser qualification, the minimal public final-submit form, and the operator steps for a delivery that is stuck. It is not an independent acceptance. Questionnaire drafts, resume, attachments, and per-question completeness remain TC-18-003.

## Contract

Creation validates an ordinary ASCII mailbox, a message of at most 10,000 characters, and an optional live questionnaire in the same workspace. Current membership and permission are locked and rechecked on every private mutation, including after the idempotency claim commits. API-key administration is allowed because these operations do not assert human approval. Missing and foreign ids return the same 404. GET performs no writes.

A new request issues one random grant and stores only its SHA-256 hash. List and idempotency replay keep `link_token` null. The first create response includes the raw link. New grants expire after seven days by default; creation accepts 1–90 days. Pre-migration raw grants are accepted only within seven days of their recorded creation. That compatibility rule does not backfill provenance. Unknown, expired, and revoked grants return the same generic 404 for public GET and submit. The public page shows that same sentence for every one of those outcomes and does not say which one it was.

Create takes an optional scoped Idempotency-Key. Send and resend require one. The key is stored as `ws:{workspace_id}:vendor-create:new:{client_key}`, `ws:{workspace_id}:vendor-send:{request_id}:{client_key}`, or the same shape with `vendor-resend`. #202 records a random `owner_token` on the claim. `set` and `release` update the row only while it still carries that token, so a late finisher cannot overwrite a replacement owner. Replays return the stored result and do not contact the provider again. The stored body is the request id and input digest, not the raw grant.

Each SMTP send persists its intent and replay marker before contacting the provider. Console and disabled providers do not call the provider. They record `delivery_status=unavailable` and `last_delivery_error=provider_unavailable`, leave the current grant in place, and return no new link. `accepted` means provider acceptance, not mailbox receipt. A false or exception outcome is `uncertain` with `last_delivery_error=delivery_uncertain`. A crash after the intent commit leaves durable `sending`. `sending` and `uncertain` both reject another send or resend with HTTP 409 and the detail `The previous delivery outcome is unknown. Reconcile it before sending again.` There is no automatic resend. An explicit resend after a known `accepted` outcome rotates the previous grant. Resend after `unavailable` is the dashboard's Resend action only when the row is already `accepted`; the console provider then records `unavailable` again and does not rotate the grant.

Final submit writes bounded response text (20,000 characters), its digest, and a timestamp under a row lock, and sets `status=completed`. An identical retry returns the original receipt. A changed retry returns 409. Only a persisted submission establishes completed status. A legacy `status=completed` without `submitted_at` is not treated as submitted. Public GET stays metadata-only. Final submit returns status, timestamp, and digest.

The public page at `/vendor-response` posts that final response with the grant token. It is one text field and a submit button. It does not collect questionnaire answers. Invalid, expired, and revoked grants render one generic message, `This link is invalid or has expired.` A second click while the first submit is in flight does not send another request. If the first response is lost, submitting the same text again accepts the original receipt and shows the request completed. A different text shows `A different final response was already submitted.` and does not replace the stored response.

## Dashboard

`/dashboard/requests` is the lifecycle consumer from #118. It reads `schema_version` `1`, derives completed only from `submitted_at`, and does not offer a cosmetic Completed progress action. Delivery labels are:

| `delivery_status` | Label |
| --- | --- |
| `not_sent` | Not sent |
| `sending` | Delivery awaiting confirmation |
| `accepted` | Accepted by email provider |
| `uncertain` | Delivery outcome unknown |
| `unavailable` | Email delivery unavailable |
| `unknown` | No recorded delivery outcome |

`sending` and `uncertain` hide Send and Resend and show `Reconcile the previous delivery before sending again.` Revoke still requires confirmation. The badge and the row have to agree with `vendor_requests`: completed appears only after `POST /api/vendor-response/submit`.

## Operator runbook

Use this when an invitation stays in `sending` or `uncertain`. Those two states block another send. This application has no endpoint that clears them, and it does not store a provider message id. Do not add a route, and do not `UPDATE` `delivery_status` to force another send. A hand edit would bypass the durable intent.

1. Read the stuck rows. Do not copy `response_payload`, `link_token`, or `link_token_hash` into a ticket.

```sql
SELECT id, workspace_id, vendor_email, status, delivery_status,
       last_delivery_at, last_delivery_error, expires_at, revoked_at, submitted_at
FROM vendor_requests
WHERE delivery_status IN ('sending', 'uncertain')
ORDER BY id;
```

2. Read the delivery audit for that id. The action values the service writes are `vendor_request.delivery_started`, `vendor_request.delivery_accepted`, `vendor_request.delivery_uncertain`, and `vendor_request.delivery_unavailable`.

```sql
SELECT id, occurred_at, action, user_id
FROM audit_events
WHERE resource_type = 'vendor_request'
  AND resource_id = :request_id
  AND action IN (
    'vendor_request.delivery_started',
    'vendor_request.delivery_accepted',
    'vendor_request.delivery_uncertain',
    'vendor_request.delivery_unavailable'
  )
ORDER BY id;
```

3. Tell the two stuck states apart from those rows:

- `sending`, with `vendor_request.delivery_started` and no later `delivery_accepted` or `delivery_uncertain`: the intent committed and the outcome did not. The provider may already have accepted the message. `last_delivery_error` is null.
- `uncertain`, with `last_delivery_error = 'delivery_uncertain'` and `vendor_request.delivery_uncertain`: the provider returned false or raised after the intent commit. The message may still have been accepted.
- `unavailable` with `last_delivery_error = 'provider_unavailable'` is not this case. The console or disabled provider was not called. The dashboard still offers Send, and another send is allowed.

4. See whether the original send or resend stored a replay. Do not select `response_body` or `owner_token`. A stored body means a replay will not send again. An empty body means the claim is still in progress until its lease expires.

```sql
SELECT idempotency_key, status_code,
       response_body IS NOT NULL AS has_response, expires_at
FROM idempotency_keys
WHERE idempotency_key LIKE 'ws:' || :workspace_id || ':vendor-send:' || :request_id || ':%'
   OR idempotency_key LIKE 'ws:' || :workspace_id || ':vendor-resend:' || :request_id || ':%'
ORDER BY idempotency_key;
```

5. Use only the product actions that exist:

- Leave the row. `POST /api/vendor-requests/{id}/send` and `POST /api/vendor-requests/{id}/resend` with a new Idempotency-Key return 409 `The previous delivery outcome is unknown. Reconcile it before sending again.` and do not contact the provider.
- Repeating the original Idempotency-Key returns the stored result and does not send again. For a crash after the intent commit, that result still says `sending`.
- The dashboard shows `Delivery awaiting confirmation` or `Delivery outcome unknown`, hides Send and Resend, and says to reconcile the previous delivery before sending again.
- Revoke is still available: the Revoke link control, or `POST /api/vendor-requests/{id}/revoke`. Revoke does not send mail and does not change `delivery_status`.
- Decide whether the provider accepted the message from that provider's own logs. This database does not record a message id, so there is no query here for that fact.

`accepted` is a finished provider acceptance. Resend is the explicit way to rotate that grant. It is not a stuck state.

## Verification

The real-API check is `apps/api/tests/release/test_vendor_requests_browser.py`. It drives `/dashboard/requests` through Chromium, Next, and the API into PostgreSQL, with no API route mocks. The console provider's send and resend show `Email delivery unavailable`, not delivered. The flow creates, sends, revokes, and resends, restarts both processes, and checks that the badges match the `vendor_requests` rows. `completed` is absent until the public form posts `POST /api/vendor-response/submit`.

Commands, the pre-form failure, and the form's passing unit run are in `artifacts/acceptance/TC-18-002/`. Exact-head `build` and `web-release-e2e` on push and pull_request qualify the head. Local PostgreSQL is not a substitute for those runs.

## Limits

No live SMTP delivery is claimed. Console and disabled providers are `unavailable` on purpose. There is no supported write that turns `sending` or `uncertain` back into a sendable state. The public form submits one final response; it does not implement the questionnaire. Independent acceptance is still open.
