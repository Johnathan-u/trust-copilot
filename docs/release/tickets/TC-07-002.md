# TC-07-002: Separate key purposes and rehearse credential migration

Session signing, OAuth state, MFA and connector encryption no longer share one derived key.
Each purpose has a versioned env keyring. This is not a KMS or a secret manager; that remains
an owner release decision. Overlap with session-record work and key-backup work stays limited
to the signing key id stored on `user_sessions`.

## Keyrings

| Purpose | Env | Used for |
|---|---|---|
| session | `SESSION_KEYRING` | `tc_session` cookies |
| oauth_state | `OAUTH_STATE_KEYRING` | signed OAuth state |
| mfa | `MFA_KEYRING` | `user_mfa.totp_secret_encrypted` |
| connector | `CONNECTOR_KEYRING` | credential store, Slack bot token, Gmail access and refresh tokens |

The first `kid:secret` is current. Later entries are retired. A secret must not contain a comma.
When the variable is unset, the current id is `v0-legacy` and the key is HKDF(SESSION_SECRET, purpose).
Prefixed values keep that HKDF derivation when `v0-legacy` is explicitly retained, including
after a new key becomes current. Values with no key id use the retained `v0-legacy` entry's
previous SHA256 Fernet or raw HMAC derivation. An explicit purpose keyring must include
`v0-legacy:<previous root>` to read those values; it does not implicitly trust `SESSION_SECRET`.
An explicitly retained `v0-legacy` entry can also read prefixed values written with the earlier
SHA256 implementation. This compatibility read is limited to that purpose and entry.
Session cookies signed by a retired key are rejected, including unprefixed legacy cookies.

Production rejects a weak or placeholder purpose key, a repeated key id, and the same key material
on two purposes. Messages name the variable only.

## Rotation

`cd apps/api && python scripts/rotate_purpose_keys.py --dry-run`

The command refuses `APP_ENV=production`. Run it on a copy. It prints counts only.
`--after-id` resumes after a row id. A second run does not re-encrypt rows already on the current id.

An MFA secret that cannot be opened is stored as `reenrol.<kid>`. `enabled` stays true, so the
factor is not silently disabled and the account is not left returning 500. Password login then
fails with error code `mfa_reset_required` and does not create a session or set a cookie, so
there is no path to `POST /api/auth/mfa/setup`.

Every failed MFA decrypt is written to `audit_events` as `crypto.decrypt_failed` with the user
id, key id and reason only. The rotation command writes the same kind of row for each decrypt
it cannot finish, including connector ciphertext. Rows already marked `reenrol.<kid>` are left
unchanged and are not decrypted again.

An active administrator of that user's workspace calls
`POST /api/members/clear-mfa-reenrol/{user_id}`. The route checks the actor's current persisted
membership and permissions, so a stale administrator cookie does not authorize a reset.
The call replaces `reenrol.<kid>` with `reenrol-pending!.<encrypted secret>`, removes the target's
sessions, login challenges and recovery codes, and writes `auth.mfa_reenrol_cleared` with the
actor, target and workspace. The MFA row and workspace policy are kept; the audit records
`mfa_required`. A non-admin receives 403. An administrator of another workspace receives 404.

The next password login returns `requires_mfa_enrol` and grants a five-minute enrollment-only
session. The sign-in page stays on that response and calls `POST /api/auth/mfa/setup` and
`POST /api/auth/mfa/confirm`. It does not open the dashboard with that cookie. The session
can read its own profile, MFA status and current session metadata, start/confirm MFA setup,
or log out. It has no workspace privileges and cannot switch workspaces or revoke other
sessions. An administrator starts that reset from Members with **Reset MFA sign-in**, which
calls `POST /api/members/clear-mfa-reenrol/{user_id}`. The stored
pending marker also blocks old normal cookies until enrollment completes; ordinary disabled
or unfinished optional MFA enrollment does not acquire this restriction. Setup and key
re-encryption preserve the pending marker. A valid TOTP confirmation checks current active
membership, then atomically enables the factor, removes the pending marker and replaces the
restricted session with a new normal session using the current role. A failed confirmation
does not grant a normal session. There is no self-service clearance of an unreadable factor.

Retired session key ids, and rows with no key id once the current session key is not `v0-legacy`,
are deleted from `user_sessions`. Cookies signed with a retired key do not verify.

## Column

`user_sessions.signing_key_id` is nullable (`tc07002_session_key_id`). Downgrade archives
non-null key metadata in `tc07002_session_key_archive` before dropping that column, in the
same transaction. Re-upgrade restores a key only to an existing row with the same `id`,
`user_id`, `session_id`, and `created_at` (including a null creation time). It never inserts
session rows. Changed identities and sessions created while downgraded keep a null key;
unmatched archive entries remain available instead of being discarded. Successful restores
consume only their matching archive entries, and subsequent cycles preserve the current key.

This is exact-identity restoration: a deliberately recreated row with all four identity
fields identical cannot be distinguished from the original row. No session lifecycle tracking
is introduced. Ciphertext stays in the existing columns. A prefixed MFA token for a long
synthetic secret fits `totp_secret_encrypted` String(512).

## Owner eyes

These are not engineering defects in the rehearsal. They need the owner before production
custody or a live rotation.

- **KMS custody.** Keys are versioned environment variables, not a cloud KMS or a secret
  manager. Unset keyrings derive `v0-legacy` with HKDF from `SESSION_SECRET`.
- **Distinct production keyrings.** Production rejects a weak key, a repeated key id, and
  the same material on two purposes only when a keyring is set. Compose does not require
  `SESSION_KEYRING`, `OAUTH_STATE_KEYRING`, `MFA_KEYRING`, or `CONNECTOR_KEYRING`.
- **Production rotation.** `scripts/rotate_purpose_keys.py` refuses `APP_ENV=production`
  and has no override. It prints counts only and must be run on a copy. This verification
  did not rotate a production database or a live provider token.
- **Sole-administrator recovery.** The reset requires another active administrator of that
  workspace. There is no in-product break-glass when the only administrator is the locked
  account.
- **Forced sign-out.** A retired session key is rejected immediately, including an
  unprefixed legacy cookie. The rehearsal deletes retired and, once the current session key
  is not `v0-legacy`, null `signing_key_id` rows. OAuth state still accepts a retired key
  inside its ten-minute window.
- **Backup.** A purpose secret cannot contain a comma. Losing the current key without the
  previous entry retained makes MFA ciphertext unreadable (re-enrol) and leaves connector
  ciphertext in place. The app does not back up keyrings.
- **Downgrade identity.** Restoring `signing_key_id` matches `id`, `user_id`, `session_id`,
  and `created_at`. A row recreated with those four fields identical cannot be told apart
  from the original. The migration does not rewrite ciphertext.
- **Review.** Independent review of this head is still the coordinator's gate. This record
  does not mark the ticket accepted.
