## Behavior and scope

A chunk's own workspace previously sufficed for retrieval even when its document
had moved, belonged to another workspace, or was archived. Keyword, semantic
fallback and pgvector queries now require an existing Document whose primary key
matches the chunk's document foreign key, whose workspace matches the request,
and whose `deleted_at` is null. The SQL predicate runs before candidate limits
and vector ranking. Both keyword passes share the predicate.

Per the explicit ruling, parentless chunks are ineligible because they have no
authoritative current provenance. Rows are retained. The production indexer
already supplies a document parent. The fixture's valid foreign-key states
exercise stored-state authorization; they do not assert that a public mutation
endpoint permits those states.

Own active-parent chunks remain eligible. Metadata cannot grant eligibility.
Existing metadata projection, document-scope normalization/filtering, scores,
mapping boosts, batch session/thread behavior and output shape are preserved.
Historical archived-document export behavior is unchanged. No model, migration,
auth, dependency, provider, cache or source-version changes are included.

## Acceptance evidence

- 30 SQLite cases with foreign keys enabled and real stored member/session auth.
- The same 30 cases against the migrated PostgreSQL fixture.
- 11 additional PostgreSQL cases using the actual pgvector operator and known
  synthetic 1536-dimensional embeddings, including scores, limits, current
  parent changes, explicit scope, hybrid search and batch retrieval.

Coverage includes ordinary and rare keyword paths, semantic fallback, search,
batch, both HTTP search spellings, denied workspace requests, suspended current
membership and removed sessions. It includes foreign, archived, moved,
parentless, hard-deleted and ordinary foreign-workspace chunks, active positive
controls, misleading metadata, and own/mixed/foreign/unknown document filters.
The hard-delete control verifies real FK cascade; retrieval itself deletes no
rows. Limit controls retain exactly one eligible candidate without assuming an
ordering among eligible SQL rows.

Every read compares full-row hashes and counts across 18 relevant tables and
checks pending ORM mutations. Cleanup deletes only exact fixture-owned IDs in
foreign-key order and compares the complete original snapshot. PostgreSQL uses
the existing migrated fixture. Collection performs no database setup. The HTTP
tests use the real no-provider-key embedding path; no provider calls or auth,
SQL, embedding, or pgvector mocks qualify these cases.
