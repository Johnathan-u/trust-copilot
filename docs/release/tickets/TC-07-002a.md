# TC-07-002a: require four distinct production keyrings; key rotation and recovery runbook

Follow-up of TC-07-002, added by owner sign-off OD-13 (2026-11-06, `docs/acceptance/release-decisions.md`).
Jira: [SCRUM-551](https://reinhartjm294trustcopilot.atlassian.net/browse/SCRUM-551). Epic E07. 2 points, P1.
Depends on TC-07-002. Branch: `tc/TC-07-002a-production-keyrings`.

## Why

Production checks only the keyrings that are set. An unset keyring falls back to a key derived from
`SESSION_SECRET` (`v0-legacy`). OD-13 accepted TC-07-002 on the condition that production sets four
distinct keyrings, with the rotation and recovery steps written down.

## Acceptance criteria

1. In production, the config contract (`apps/api/app/core/config_contract.py`) refuses to start unless
   `SESSION_KEYRING`, `OAUTH_STATE_KEYRING`, `MFA_KEYRING` and `CONNECTOR_KEYRING` are all set and strong,
   and are different from each other and from `SESSION_SECRET`. Messages name the variable, never the value.
   Development and test behaviour is unchanged.
2. `docker-compose.prod.yml`, `.env.example` and the generated `docs/release/config-contract.md` require
   all four. Release tests cover each refusal: missing, weak, duplicate, and equal to `SESSION_SECRET`.
3. An operator runbook (`docs/ops/key-rotation.md`) covers:
   - production rotation: run `apps/api/scripts/rotate_purpose_keys.py` on a copy, then cut over;
   - backing up keyrings;
   - recovering a workspace whose sole admin is locked out of MFA: a database-level procedure that leaves
     an audit record.

## Evidence and sign-off

CI release tests plus the runbook, reviewed by an independent reviewer. Under OD-14 no separate owner
sign-off is needed.
