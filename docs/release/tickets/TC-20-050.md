## What the sync does

`POST /api/crm/sync/salesforce` with `{ "pipeline_id", "connection_id"? }` checks `SALESFORCE_API_BASE_URL` and queues one `crm_sync` job. The response has `source`, `kind`, `job_id`, `status`, `connection_id`, `pipeline_id`, and `workspace_id`. It does not set `mock`.

The worker reads the selected pipeline from that base URL. The client speaks the Salesforce REST query shape: `GET /services/data/v59.0/query?q=SELECT ... FROM Opportunity WHERE PipelineId = '<pipeline>'`, then follows `nextRecordsUrl` until `done` is true. `nextRecordsUrl` must stay on the configured origin and under `/services/data/`. Redirects are refused. Salesforce hostnames are refused. No `Authorization` header is sent.

Each Opportunity is upserted on `(workspace_id, connection_id, provider, crm_external_id)`. `crm_external_id` is the external id in that unique key. The row stores `close_date`, `expected_close_date`, `currency`, and `crm_stable_id`. The stable id is `{workspace_id}:{connection_id}:salesforce:{external_id}` and is not rewritten on a later page. A retry of the same page updates that row.

`crm_connections` stores the cursor. While a pass is in progress, `cursor_kind` is `page` and `cursor` is the next page to read. After the last page, `cursor_kind` is `complete` and `cursor` is the newest `LastModifiedDate` from that pass. A failed page leaves the cursor on the page that did not commit, so the next attempt resumes there. Deals from earlier pages stay one row.

When a pass finishes, deals for that connection whose external id was not in the pass get `crm_removed_at`. The row is kept. A later pass that includes the id clears `crm_removed_at`.

`update_deal` records changed CRM fields on `crm_manual_fields`. The next sync does not write those fields. Amount and currency are one pair, and the two close dates are one pair: editing either side keeps both. Notes and a manual stage survive. Fields the person did not edit still take the provider value.

## Shared job kind

`JobKind.crm_sync` (`crm_sync`) is the only CRM sync kind. The payload `provider` is `salesforce` or `hubspot`. This ticket runs Salesforce. HubSpot (TC-20-053) uses the same kind, the same history row, and the same object link. The jobs history page shows progress (`generated` / `total` records), cancel, retry, and `Open synced pipeline` (`/dashboard/deals?connection_id=<id>`). Those come from the stored job and the current connection, so they are still there after a reload. A connection in another workspace is not linked.

## Migration

Revision `tc20050_crm_pipeline_sync` (parent `tc04007b_rate_buckets`).

Upgrade copies `provider` from `crm_source` when the source is `salesforce` or `hubspot`. It then dedupes rows that share workspace, provider, and external id and whose connection ids are not distinct (null matches null, because older rows have no connection). The oldest id keeps the identity. Later rows keep their company, amount, stage, notes, and dates. Their provider, `crm_source`, and `crm_external_id` are cleared and copied to `tc20050_deal_identity_hold`. Those deals are not deleted.

Downgrade drops the unique index, writes `crm_source` and `crm_external_id` back when the live external id is still null, then drops the new deal columns, the hold table, and `crm_connections`.
