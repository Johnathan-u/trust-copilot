# Notification rule and log API implementation plan

Status: regression stage; production behavior unchanged. Assigned in [coordination issue #85](https://github.com/Johnathan-u/trust-copilot/issues/85#issuecomment-6503307759).

**Goal:** Validate rule recipients in the active workspace, enforce current permissions, preserve personal preferences and honest delivery logs, and verify persisted results with PostgreSQL.

**Architecture:** Keep the existing policy, delivery, template, preference, and dedupe models. Add bounded recipient validation before policy mutations and local notification access guards that recheck membership/current role. Read endpoints remain side-effect free. No migration or shared authentication change is planned.

**Constraints:** No live provider calls, paid accounts, new dependencies, migrations, web edits, or E20 work. TC-19-008's shared static template renderer remains authoritative; editable templates have no approved persisted contract and require Coordinator ruling. No ticket identifiers in published API descriptions.

## Review focus

Missing and foreign references must produce the same 404. A failed PATCH must not partially change an existing policy. Removed or demoted members cannot use a stale session to administer notifications. GET never writes and does not disclose a foreign notification reference. Test teardown removes every added row, including audit, notification, session, and idempotency records, and compares the complete snapshots.
