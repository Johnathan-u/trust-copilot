# Notification rules and delivery logs

Status: the API contract below is on master. The rules form now asks for an active workspace member and stores that member's user id. Editable templates remain deferred. Real-provider sandbox evidence remains blocked on owner accounts. Assigned in [coordination issue #85](https://github.com/Johnathan-u/trust-copilot/issues/85#issuecomment-6503307759).

## User recipients

A user recipient is an active workspace member, stored by that member's user id (`users.id`). It is not an email address and it is not the membership row id. `validate_recipient` is unchanged: it accepts that integer, and a foreign, missing, or suspended member returns the same 404. The rules form loads `GET /api/members` for the current administrator and submits the selected user id. The role field is still a role name, limited to 255 characters. When policy creation returns a `detail` that is not a string, such as a validation list, the form shows one fixed message and does not render the raw value.

Operator steps are in [docs/ops/notification-delivery.md](../../ops/notification-delivery.md) under "User recipients".

## Rule and permission contract

Policy creation, recipient edits and re-enabling validate the entire prospective recipient before writing. A disable-only PATCH can turn off a policy whose recipient has since left, been suspended, or had its role deleted; it retains the stale routing value without authorizing delivery. User recipients must be active members of the current workspace. Role recipients must be a built-in role or a custom role in that workspace. Foreign, missing and suspended user recipients return the same 404; foreign and unknown roles also return the same 404. Role names and user ids are canonicalized; switching to `all` or `admins` clears the obsolete recipient value. Request fields have database-aligned bounds and reject control characters and overlong normalized values.

All notification endpoints recheck membership and use the member's current role. Policy mutations and delivery logs require current administrative permission, including workspace custom roles. Personal preferences and unsubscribes remain scoped to the authenticated user. API keys preserve their existing current-key permission behavior; personal writes require a user context.

GETs do not write. Delivery-log pages break timestamp ties by id; attempts suppress a linked in-app reference when its workspace does not match. Existing policy, log, preference and attempt response fields are preserved for `apps/web/app/dashboard/notifications/page.tsx`. The rules form is the consumer that now sends a member user id. Shared auth modules are unchanged.
