# Notification rules and delivery logs

Status: implemented; PostgreSQL CI and independent review pending. Assigned in [coordination issue #85](https://github.com/Johnathan-u/trust-copilot/issues/85#issuecomment-6503307759).

## Rule and permission contract

Policy creation and updates validate the entire prospective recipient before writing. User recipients must be active members of the current workspace. Role recipients must be a built-in role or a custom role in that workspace. Foreign, missing and suspended user recipients return the same 404; foreign and unknown roles also return the same 404. Role names and user ids are canonicalized; switching to `all` or `admins` clears the obsolete recipient value. Request fields have database-aligned bounds and reject control characters and overlong normalized values.

All notification endpoints recheck membership and use the member's current role. Policy mutations and delivery logs require current administrative permission, including workspace custom roles. Personal preferences and unsubscribes remain scoped to the authenticated user. API keys preserve their existing current-key permission behavior; personal writes require a user context.

GETs do not write. Delivery-log pages break timestamp ties by id; attempts suppress a linked in-app reference when its workspace does not match. Existing policy, log, preference and attempt response fields are preserved for `apps/web/app/dashboard/notifications/page.tsx`. No web code or shared auth module changes.

## Templates and delivery

The [Coordinator ruling](https://github.com/Johnathan-u/trust-copilot/issues/85#issuecomment-6503678126) accepts qualification of the existing shared static renderer. Editable template authoring is follow-up TC-19-009a and is outside this PR. The renderer's cross-channel label, template key, HTML escaping and redaction contracts are covered here.

Dispatcher behavior is unchanged. PostgreSQL qualification exercises policy creation through HTTP, injected provider rejection followed by acceptance, exhausted rejection, attempt-state history, matching delivery-log fields, and persisted dedupe across a disposed connection pool. Only an accepted provider result sets `delivered_to_provider`; a synthetic provider is labeled `fixture`. No live provider acceptance is claimed. Existing console-stub and delivery tests remain part of full CI.

## Validation and scope

The initial 26-case PostgreSQL regression suite at `e54d3cf52a27d6842137375ded15d9c90e9f64c9` produced ten intended failures in CI, with 3206 passing tests and one external-data skip. There were no setup or cleanup failures. Eight additional local input-boundary tests failed before their schema fix, then passed. The current module contains 49 cases: 11 pure schema/template checks pass locally; 38 PostgreSQL cases await the updated CI run. Local collection is not a PostgreSQL pass.

Fixtures create isolated workspaces, users and roles and delete all rows they added, including delivery attempts/logs/dedupe claims, preferences, unsubscribes, policies, in-app rows, audit events, idempotency entries and sessions. Teardown asserts every table's key set and count returns to baseline. Read-only tests also compare full row values. Missing and foreign references, every mutating route, stale membership, failed prospective PATCH, and retry/new-connection behavior are covered.

No migration, new dependency, paid account, or provider network call. Browser UI execution and full process restart are not claimed by the domain tests; current UI-consumed fields are preserved and connection-pool replacement verifies persisted state. Required CI and independent review must pass before readiness. Evidence is under `artifacts/acceptance/TC-19-009/`.
