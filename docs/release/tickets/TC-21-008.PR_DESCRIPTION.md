# TC-21-008: Scoped actionable compliance alerts

Built from origin/master `47b5972`. The branch was not behind master, so there is no merge commit.

## AC

AC1: a scan persists one alert per workspace, condition, and source, with the current source revision and, for a control check, the control revision. A second scan updates that row.

AC2: positive, negative, and partial-failure cases run on PostgreSQL. Missing and foreign ids share one 404. Permissions stay as listed below.

AC3: `GET /api/compliance-alerts/active` returns `compliance-alerts/v1`. The notifications page reads that schema. A retry of the same idempotency key returns the stored response. The rows survive a new database session.

## Migration

`tc21008_alert_records` (21 characters) revises `tc02001a_parent_ws_move` on one `down_revision` line. It creates `compliance_alerts` and the partial unique index `uq_compliance_alerts_one_active` on `(workspace_id, condition, source_ref) WHERE status = 'active'`. Downgrade parks the rows in `tc21008_alert_hold` and upgrade copies them back. Parent = `tc02001a_parent_ws_move` for now. Migration slot: last in queue; re-parent on Coordinator's signal.

Scans take `pg_advisory_xact_lock(150017, workspace_id)`.

`alert_acknowledgments`, `evidence_gaps`, and `in_app_notifications` cannot store the condition, lifecycle, and source revision without overloading those tables.

## Ambiguities

A coverage alert stores a fingerprint in `source_revision` because coverage has no revision column. `GET /active` reads stored active rows and does not recompute. An acknowledged or unexpired snoozed row stays on the same id when the condition remains. A cleared condition becomes `resolved`. A later scan of that condition inserts a new active row. Expired snoozes become active on the next scan, not on GET. The scan does not send email or chat.
