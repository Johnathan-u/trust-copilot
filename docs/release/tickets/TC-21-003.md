# TC-21-003 Control library lifecycle and evidence verification

**Status:** implemented. Framework catalogs stay **BLOCKED** pending **TC-01-007**. No framework control text was added.

Routes are mounted at `/api/compliance/controls` (`app.include_router(..., prefix="/api")` and router prefix `/compliance/controls`).

## Evidence gate

Verify, a patch to status `verified`, marking a link verified, and linking with `verified` true all require at least one qualifying evidence item. A count of linked files is not enough.

An item qualifies when all of these hold:

- `approval_status` is `approved`
- it belongs to the control's workspace
- no `evidence_metadata.expires_at` is already due
- if it points at a document, that document is in the same workspace and `deleted_at` is null

A repeat of verify while the control is already verified and the evidence still qualifies does not change the stored status. `sync_workspace_row` still copies a new verification onto the paired legacy control.

The same rule lives in `app.services.evidence_qualification.evidence_qualifies`. The compliance routes and remediation evidence both call it.

## Remediation evidence links

`POST /api/remediation/tickets/{id}/evidence` still cannot set the control status to `verified`. An unknown bump is `invalid_control_status`. `verified` is `verified_status_not_allowed`. A permitted bump is stored and `sync_workspace_row` copies that lifecycle onto the legacy row. Null leaves the status unchanged. The default `implemented` bump does not change a control that is already `verified`. Links and the legacy mirror are written before that sync. The route commits once. Leaving `verified` clears `verified_at` and `verified_by_user_id`.

A link this route creates or updates is `verified` only when that evidence qualifies. Pending, expired, and deleted-document evidence are stored with `verified` false. A link that was already verified is set back to false when the evidence no longer qualifies. Qualifying evidence, including an existing unverified link, is stored with `verified` true. That flag does not move the control to `verified`.

`last_verified_at` follows that flag. A new verified link stores the current time. A link that becomes verified stores the current time. A link that stops being verified stores null. A link whose flag does not change keeps its previous timestamp. The remediation audit payload keeps `evidence_ids` and adds `links`, a list of `{evidence_id, verified}` for the links this request wrote.

The legacy mirror is unchanged. Each evidence item still gets a `control_evidence` row on the paired legacy control. That table has no verified column, and the mirror does not depend on qualification.

After a compliance `DELETE /{id}/evidence/{link_id}` or a legacy `DELETE /api/controls/{id}/evidence/{evidence_id}`, the link is removed. If the control was `verified` and no qualifying evidence remains, the control is stored as `implemented` and `verified_at` and `verified_by_user_id` are cleared. That sync does not check the owner, so a suspended owner does not block the delete. The caller commits once, then emits `control.implemented` with `previous_status` `verified` and `reason` `no_qualifying_evidence`. If another qualifying link remains, the control stays `verified`.

`POST /api/compliance/controls` with `status` `verified` returns 400 `verified_status_not_allowed` and writes nothing. A new control has no links.

`POST /api/control-engine/evaluate/{id}` reports `passing` only when at least one linked item qualifies and is fresh (created less than 180 days ago). Qualifying evidence that is not fresh is `stale`. Linked files that do not qualify are `failing`. No linked files stays `not_assessed`.

## Owners

`POST /api/compliance/controls` and `PATCH /api/compliance/controls/{id}` refuse an `owner_user_id` that is not an active member of the control's workspace. A user from another workspace, a suspended member, and a removed member (the user row remains, the membership row does not) all return 404 `owner_not_in_workspace`. The stored control is unchanged. The check is `_owner_error` in the control contract, used by create and by `sync_workspace_row` on patch.

## Links

`control_evidence_links` has unique index `uq_control_evidence_links_pair` on `(control_id, evidence_id)`. The control row is already workspace-scoped, so that pair is one link per workspace, control, and evidence.

If two rows already share the pair, the oldest stays. Later rows are copied to `tc21003_link_hold` and deleted. Evidence items stay. Downgrade drops the index and inserts the held rows back.

A new `POST /{id}/evidence` returns 201. Repeating it returns 200 with the stored link and does not insert another. It used to answer 400.

Cross-workspace or missing evidence, documents, chunks, and controls return 404. GETs do not write.

## Ambiguities

- Evidence items have no deleted column. A linked document with `deleted_at` set is the deleted case. Manual evidence with no document is not treated as deleted.
- Expiry is `evidence_metadata.expires_at`. A null expiry is not expired. `freshness_date` is not a gate; requiring it would invent a freshness policy.
- The unique key does not add a workspace column. The control's workspace is the scope.
- A new link is 201. A second link of the same evidence is 200 with the stored link. It used to answer 400.
- Verify of an already verified control whose evidence no longer qualifies returns 400 and does not clear `verified`.
- Suggest-evidence does not persist and does not require evidence to already be linked.
- Accept-suggested `Idempotency-Key` is optional. Requiring it would reject callers that already post without the header. The route stays admin. A present key is claimed with an owner token, the same way case-study publish does. A retry with that key returns the first response and does not create another evidence item or link. A failed commit rolls the write back, then releases that claim.
- The web consumer is `apps/web/app/dashboard/controls/*` (TC-15-042). It reads the control and evidence fields these routes already return. Response fields are unchanged.
- Remediation attaches evidence that does not qualify. The link is stored unverified, with `last_verified_at` null. The route does not reject the attach for approval, expiry, or a deleted document.
- Removing the last qualifying link demotes a verified control to `implemented`. It does not refuse the delete.
- Create does not accept `verified`. Verify and a patch to `verified` still require qualifying evidence that is already linked.
