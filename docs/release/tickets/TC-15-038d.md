# TC-15-038d: publisher lock_timeout

Follow-up of TC-15-038. Filed by Claude while accepting #262 ([comment 6935642452](https://github.com/Johnathan-u/trust-copilot/pull/262#issuecomment-6935642452)). Registered on #85 ([comment 6935642903](https://github.com/Johnathan-u/trust-copilot/issues/85#issuecomment-6935642903)).
Epic E15. Points were not assigned. P3. Depends on TC-15-038c. Open. Not accepted. Not counted toward DONE.

## Acceptance criteria

1. In the publisher session that writes running progress, set `SET LOCAL lock_timeout = '250ms'`, or take the row with `FOR UPDATE NOWAIT`.
2. Treat a lock timeout as a skipped publish. `publish_running_progress` returns `False` quickly.
3. A test holds the job row locked and asserts `publish_running_progress` returns `False` quickly. A later change that leaves the job row locked must not hang the worker on itself.

## Scope

Claude's re-review of #262 confirmed the publisher takes `FOR UPDATE` on the job row from the worker's own thread, and that the job transaction holds no lock on that row during the loops. The only foreign-key writer mid-run, `provider_call_started`, commits on its own connection, and `job.result` is not flushed mid-loop. This child is the hardening for a future change that leaves the job row locked.

## Evidence and sign-off

`publish_running_progress` sets `SET LOCAL lock_timeout = '250ms'` on the publisher session. A Postgres lock timeout (`55P03`) is a skipped publish and returns `False`. The named release test is `apps/api/tests/release/test_tc15038d_publisher_lock_timeout.py`. Local evidence is in `artifacts/acceptance/TC-15-038d/`.

This file does not accept TC-15-038 or TC-15-038d. The child is not counted toward DONE.
