## Behaviour

Line numbers were read on this change.

**Rows and built-ins.** `GET /api/dashboard/cards` lists the four built-in cards first (`dashboard_cards.py:57-77`, `:136`). Those dicts have no `id` and no `updated_at`. Custom rows follow, as `_card_dict` plus `is_builtin: false` (`dashboard_cards.py:40-53`, `:138-145`). An admin sees every custom row. Anyone else sees a custom row only when it is enabled, `visibility_scope` is `all`, and `ROUTE_PERMISSION` says the application nav would show that route (`dashboard_card.py:31-53`, `dashboard_cards.py:98-109`, `:154-161`). `requiresAdmin` is `can_admin`. `requiresReview` is `can_review`. Review, exports, and account security have no nav flag, so they stay visible.

**Routes.** A target must be in `ALLOWED_ROUTES` (`apps/api/app/models/dashboard_card.py:12-29`). Create and update both reject anything else with 422 before a write (`dashboard_cards.py:218-237`, called from `:255-260` and `:377-382`). The same check covers icon, visibility, and size. The operator note lists the routes.

**Revision.** `updated_at` is the loaded revision. `CardUpdate.updated_at` carries it (`dashboard_cards.py:326-327`). It is not written as the new value. `_require_loaded_revision` runs after the workspace lookup and before any column change (`dashboard_cards.py:336-345`, `:376`). A blank or missing value is 422. A different value is 409 with `This card changed since it was loaded. Reload it and try again.` The `UPDATE` also requires the loaded timestamp (`dashboard_cards.py:408-425`), so a second request that read the same row before the first commit does not overwrite it. On 409 the handler rolls back and returns. The stored title and `updated_at` stay.

A matching revision writes the sent fields and a new `updated_at`. The response is `_card_dict`. Reorder sets `updated_at` when `sort_order` changes (`dashboard_cards.py:508-510`), so an edit that still holds the previous revision is 409. Delete is still by id inside the workspace (`dashboard_cards.py:443-478`). A card that is already gone is 404.

**Create retry.** `POST /api/dashboard/cards` takes an optional `Idempotency-Key`, scoped to the workspace and `dashboard-cards:create` (`dashboard_cards.py:165-176`, `:241-266`). The same key and the same body return the stored card and do not insert another row (`:184-191`, `:264-266`). The stored response is in `idempotency_keys`, so a new process has it. A different body with that key is 422. An illegal key is 422 and inserts nothing. A rejected body is validated before the key is claimed (`:255-264`), and a failure after the claim releases it (`:303-306`). A request with no key still inserts a new card.

**Form.** The edit request is `PATCH` and the body includes the loaded `updated_at` (`apps/web/lib/dashboard-card-form.ts:69-82`). The dashboard form uses that request (`apps/web/app/dashboard/page.tsx:582-592`). A built-in card has no id, so the form does not patch it (`page.tsx:528`, `dashboard-card-form.ts:75`). Create sends one `Idempotency-Key` for the same body and a new key when the body changes (`dashboard-card-form.ts:56-63`, `page.tsx:575-586`). A 409 is not a save (`dashboard-card-form.ts:102-116`, `page.tsx:593-598`). The notice is the response `detail`, or the same stale sentence when the detail is blank. The list reloads only from `onSaved`.

The named test uses synthetic titles. It checks the built-in list, a stale edit, a reorder that moves the revision, an editor and another workspace, an unknown route, a retried create read back by a new process from `GET /api/dashboard/cards`, and a rejected create whose key can then succeed. `apps/api/tests/test_dashboard_cards.py` still covers create, update, delete, reorder, visibility, and the route allow-list. Its update sends the loaded `updated_at` (`test_dashboard_cards.py:133-136`).
