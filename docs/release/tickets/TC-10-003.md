# TC-10-003: Idempotent parse, index, generate and export side effects

Status: implemented on `tc/core/TC-10-003`. It needs a review from someone other than the implementer.
Evidence: [`artifacts/acceptance/TC-10-003/`](../../../artifacts/acceptance/TC-10-003/README.md).

## Contract

The job contract does not promise exactly-once execution. Instead, every job side effect is
**reconciled**. A re-run of the same job, a second job for the same input, or a re-claim after a crash
finds the side effect already in place and does not apply it again.

### The `job_effects` ledger (new table)

There is one row per `(job_id, effect, attempt)`, enforced by a unique constraint. `state` takes one of these values:

| state | meaning |
|---|---|
| `applied` | The side effect committed. It is written in the **same transaction** as the effect (attempt 0, so any attempt sees it). |
| `started` | A paid provider call is about to happen. It is written on a **separate connection** so the marker survives a crash or rollback. |
| `settled` | The provider call completed and its result was committed. |
| `uncertain` | The provider call may have been charged, but its outcome was lost (the attempt was interrupted or failed). |

### Per job kind

| Job | Side effect | Crash before the commit | Crash after the commit / re-run | Stale input |
|---|---|---|---|---|
| `parse_questionnaire` | questions | rolled back, so the re-run inserts once | `already_applied`. Existing questions are never duplicated or deleted (`reconciled`). | `superseded` if the questionnaire was deleted or its `storage_key` changed (checked again under `FOR UPDATE`) |
| `index_document` | chunks plus embeddings | rolled back. The embeddings marker becomes `uncertain`. | `already_applied`, or `reconciled` if the doc is already indexed. No re-embed. | `superseded` if `job.input_version` is not the doc's current `storage_key`, or the doc was deleted |
| `generate_answers` | answers (one per question, upsert) | partial drafts are protected on the retry | approved answers, and answers changed after the job was requested, are skipped (`skipped_protected`) | `superseded` if the questionnaire was deleted |
| `export` | object plus `ExportRecord` | the re-run overwrites the same deterministic key `exports/{ws}/job-{job_id}.{ext}` | `already_applied`. At most one `ExportRecord` per job (partial unique index). | n/a |

Quota usage (`ai_jobs`, `exports`) is recorded once per job (effect `usage:<type>`).

### Enqueue dedupe

`Job.idempotency_key` combined with the partial unique index
`(workspace_id, kind, idempotency_key) WHERE status='queued'` makes an identical request reuse the
job that is still queued. Once a job is running, a new request gets its own job. All enqueue sites use
`app.services.job_effects.enqueue_job`.

### HTTP Idempotency-Key

On `POST /api/exports/generate/{id}` and `POST /api/exports/export/{id}`, the key is scoped to
`ws:{ws}:{route}:{resource}:{client key}`. The workspace check runs before the key is claimed, so a 403 is
never cached. A 429, or any exception, releases the claim so that the client can retry with the same key.

### API change (additive)

`GET /api/jobs/{id}` adds `charge_uncertain: bool`. `result.outcome` may be `already_applied`,
`reconciled` or `superseded`.

## Runbook

- If a job shows `charge_uncertain: true`, the provider may have billed a call whose result was discarded. Reconcile it against
  the provider's usage dashboard. Do not re-run the job to "fix" it; that is already safe and does not refund anything.
- If an export bucket holds an object without an `ExportRecord`, a crash happened between the upload and the record commit. The
  object is overwritten on retry. Sweeping orphans belongs to TC-10-005.
- Behaviour change: answer generation no longer overwrites **approved** answers, even when the evidence
  fingerprint changed. To regenerate one, un-approve it first.

## TC-10-003b follow-up: enqueue conflicts and claim owner tokens

Evidence: [`artifacts/acceptance/TC-10-003b/`](../../../artifacts/acceptance/TC-10-003b/README.md).

### Enqueue conflict is a retryable 409, not a 500

`enqueue_job` retries the insert once when the race winner has already left `queued` (TC-10-003a). If the
retry loses the same way, it now raises `EnqueueConflictError` (its cause is the `IntegrityError`) instead of
letting the `IntegrityError` escape as a 500. A stress probe hit that path 34 times in 900 requests. The API
maps the error, on every route, to:

```
HTTP/1.1 409 Conflict
Retry-After: 1
X-Request-ID: <id>

{"detail": "<message>", "error": {"code": "idempotency_conflict", "message": "<message>",
 "request_id": "<id>", "retryable": true}}
```

This is the same `{"detail", "error"}` envelope as the `invalid_idempotency_key` 400. On the exports routes the
Idempotency-Key claim is **released, not cached**, so a retry with the same key runs again and either reuses the
queued job or creates one.

Why 409 rather than 503: the condition is a conflict between concurrent identical requests for the same
resource, not server unavailability. Clients already treat the in-progress Idempotency-Key 409 as "retry with
the same key", so this adds no new retry branch. A 503 would count against 5xx alerting and error budgets,
could trip proxy or client circuit breakers for a healthy service, and would be indistinguishable from a real
outage. `Retry-After: 1` is sent as a hint anyway, because the race clears in milliseconds.

### Owner token on Idempotency-Key claims

`idempotency.claim()` writes a random `owner_token` (migration `tc10003b_idempotency_owner_token`) and returns it.
A reclaim of an expired row through `ON CONFLICT DO UPDATE` replaces the token. `set(..., owner=)` and
`release(..., owner=)` only act while the row still carries the caller's token, and they return whether they
did. A request whose 60-second lease expired, and whose key another request then reclaimed, can no longer
free or overwrite the new owner's claim or its stored response. The exports routes pass the token on every
set and release.

`try_claim()` (boolean) and `owner=None` keep the old unconditional behavior for any caller that has not
been migrated. Case-study publish now passes the owner token (TC-25-005a).

Migration: `tc10003b_idempotency_owner_token`, `down_revision = "tc24001_stripe_webhook_events"` (master's single head at the time of writing; chain `… → tc10002_job_retries → tc24001_stripe_webhook_events → tc10003b_idempotency_owner_token`). One nullable
`VARCHAR(64)` column with no default and no backfill. The downgrade drops it.

## TC-10-003c follow-up

Upload routes committed the document or questionnaire, and stored the file, before `enqueue_job`. The retryable 409 from TC-10-003b then left that row behind, and the client's retry created a second one. [TC-10-003c](TC-10-003c.md) commits the row, the job, and the idempotency response once, and deletes the stored object if the enqueue conflicts.
