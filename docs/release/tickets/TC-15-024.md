## Alias

`/dashboard/vendor-requests` is a GET route returning HTTP 307 with a fixed relative
`Location: /dashboard/requests`. It replaces the old client-effect null page.
The existing authentication middleware still applies. The destination consumes no
query parameters, so the approved preservation allowlist is empty. Unknown query
values, tokens and redirect targets are not forwarded or interpreted.

A server-component `redirect()` was insufficient inside the current dashboard
client auth shell: a real HTTP test observed 200 with only a serialized redirect
digest. The coordinator approved replacing the page with a route handler to make
the redirect occur before layout rendering. A relative Location also avoids the
development server's normalization of `127.0.0.1` to `localhost`, preserving the
browser's actual origin. No shared layout, middleware or configuration changed.

## Outbound contract

The page consumes the existing `schema_version: "1"` vendor response and the bare
array returned by `GET /api/vendor-requests`. Review permission allows reading;
only admin permission exposes mutations. Questionnaire labels come from the
authorized list; missing names say “Questionnaire unavailable”, without an ID.

Creation sends a scoped request key and preserves it after an unconfirmed result
while the payload is unchanged, including closing/reopening the form. Changing
the payload starts another key; an acknowledged creation ends that attempt.
Send and resend have per-request/action keys, retained across failed/unknown
responses and list refreshes. They are explicit actions, never automatic retries.
Keys and form state are local to the mounted workspace/permission context; reload
does not promise recovery of an unsaved attempt. Progress and revoke use their
existing API contracts, which do not require a client key.

The page displays the authoritative delivery state. Provider acceptance is labelled
as acceptance, not mailbox delivery. `sending` and `uncertain` block new invitations
and explain that reconciliation is required. `unavailable` and legacy `unknown`
remain explicit. Sending warns that it replaces the prior link. Revocation needs
confirmation and is reflected only after a valid acknowledged response. A failed
mutation retains the current row and exposes a visible error.

Only a recorded `submitted_at` establishes completion. The cosmetic Completed
option is removed; progress remains supported. Revoked/completed rows do not offer
invitation or progress actions. Expired links remain labelled; an explicit send can
use the backend's existing rotation behavior.

First-create/send/resend responses may expose a one-time link. List and replay
responses may return `link_token: null` without `share_url`; this is a saved request,
not a link-recovery promise. Links are shown only when actually returned and valid
for the current origin, path and token. Copy feedback waits for the clipboard and
cannot migrate to a newer result. No token retrieval endpoint was invented.

Workspace/permission changes remount the page-local state. Old list responses are
aborted/ignored, and old mutations cannot expose their result or token in the new
context. Create/send/resend share a synchronous guard across rows: only one may
be pending, and its displayed result retains the guard until Done, Close or Escape.
This prevents a second one-time token from replacing an unacknowledged result.
Rejected/unconfirmed responses release the guard without dropping retry keys;
successful send/resend responses without a link release it after updating the row.
Progress and revoke retain their per-row guards. No success is shown before
response validation.
