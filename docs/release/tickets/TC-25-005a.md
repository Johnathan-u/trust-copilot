# TC-25-005a Owner-scoped idempotency claims for case studies

**Status:** implemented. No migration. The `owner_token` column already exists (`tc10003b_idempotency_owner_token`).

`POST /api/case-studies/{id}/publish` was the remaining route that claimed an Idempotency-Key with `try_claim` and then called `set` without an owner. A request whose 60-second lease expired could still overwrite or, on a 5xx store, release a claim that a later request had taken over.

Publish now uses `claim()`, the same call `POST /api/exports/...` uses. The returned owner token is passed to `set` and to `release`. `set` and `release` update or delete the row only while `owner_token` still matches. A stale token is a no-op. The new owner's claim and any response they store stay in place.

Response codes are unchanged. A stored body is replayed. An in-progress key is still `409` with `Request in progress; retry with same Idempotency-Key`. A `CaseStudyError` is still stored under that status and replayed on retry. A second publish with the same key does not publish again.

## Ambiguities

- The storage key stays `case-study:{workspace}:{case_id}:{client key}`. It is not rewritten onto `scoped_key`, so keys stored before this change still replay.
- An unexpected error after a successful claim now releases only that request's claim, matching the export routes. Previously the in-progress row sat until the lease expired. The client still sees the same error. A stale owner's release does not delete the new owner's row.
- A stale request that already committed `publish` still returns its own success body. The fence stops that request from writing the idempotency row. It does not roll back the publish it already committed.
