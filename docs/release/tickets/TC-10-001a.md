# TC-10-001a Lease recovery follow-ups

**Status:** implemented. No migration. Alembic head stays `tc10001_job_leases`.

Follow-ups after #84 (squash `a2458c9`). The lease columns, heartbeat, and recovery loop from TC-10-001 are unchanged except for the two recovery bugs below.

The earlier TC-10-001a idea, a one-off grace-period recovery for `running` jobs whose `lease_owner` and `lease_expires_at` are still NULL, is not in this change. Those rows are still left alone. An operator fails one with the statements in [TC-10-001](TC-10-001.md). Whether that grace-period work should be filed under a new id is open.

## 1. Abandoned audit commits with the classification

`recover_abandoned_jobs` used to classify the job (and commit, because `persist_audit` commits) and write `job.abandoned` afterwards. A worker that claimed the re-queued job in that gap made the post-commit read fail, and the loop `return`ed. The abandoned audit was never written, and later expired rows in the same batch were skipped.

The `job.abandoned` row is now flushed in the same locked transaction, before that classifying commit. `FOR UPDATE SKIP LOCKED`, the replacement owner token, the abandoned audit, and the retry-or-fail classification commit together. A claim cannot land between the classification and the audit.

The next expired row is a separate transaction. After the commit, a worker may claim the job before this loop reads it again. That is a normal claim of a queued job. If the post-commit read no longer shows `queued` or `failed` at the same attempt, the row is logged and the loop `continue`s. The abandoned audit is already committed. The other rows are still recovered.

## 2. A status-query error during recovery is not swallowed

`_job_already_completed` rolls back and returns false when its status query throws. That is still what the normal failure path does, so a broken transaction can still be classified.

Recovery holds `FOR UPDATE` and has already swapped the owner token in that open transaction. The same rollback drops the lock, and classification then commits without it. On the recovery path (`rollback_first=False`) the query error is re-raised. The worker loop rolls the open transaction back, so the job stays `running` under the previous owner, with the same attempt, and no `job.abandoned`, `job.retry_scheduled`, or `job.failed` row is written.

## 3. Docstring

`recover_abandoned_jobs` states which steps share the row's transaction and which do not: the lock, the token, the abandoned audit, and the classification commit are one transaction; the next row, and any claim after that commit, are not.

## 4. Replay test quota flake

`test_replay_returns_same_error_body_as_live_response` expects 400. Workspace 1's hourly `ai_jobs` limit is 10. Earlier tests in the same module can fill that hour, and the live call then returns 429. The test fixture sets that workspace's current-hour `ai_jobs` count to 0 and restores the saved count at teardown. `quota_service` is unchanged.
