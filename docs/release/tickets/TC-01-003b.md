# TC-01-003b: split same-line table cells in PDF questionnaires

Status: implemented on `tc/core/TC-01-003b`. It is **stacked on TC-01-003a** (PR #11, base
`e57b849`), so merge #11 first. It is the follow-up the Coordinator logged on PR #11 (2 pts, owner
TC Core). Evidence is in `artifacts/acceptance/TC-01-003b/`.

## Problem
pypdf's plain `extract_text()` joins text that shares a baseline into one line with single
spaces. In a table-style questionnaire, the answer cells then trail the question text, for
example `do you encrypt backups at rest? yes no` where PyMuPDF gave
`do you encrypt backups at rest`.

## What changed
- New `app/services/pdf_cells.py`. It reads the geometry of every text-show operation on a page
  through pypdf's layout-mode text-state code: start x, end x after the font's glyph widths,
  baseline and em size, with Tc/Tw/Tz/TJ kerning and `cm` applied. It then maps the characters of
  each plain-text line back onto those operations. A line is cut between two operations only if
  all of these hold:
  - they are on the same baseline (within 0.2 em) and both are upright (no rotated or mirrored
    text);
  - they are at least **1 em** apart horizontally (in either direction, with no overlap);
  - the right-hand cell starts in a column (within 1.5 pt) where a cut also starts on another
    line of the page, **or** the gap is at least **3 em**.
- `pdf_text.extract_page_rows(path)` returns, per page, the unchanged `extract_page_texts` text
  plus its non-empty lines as `TextRow(line, cells)`.
- `pdf_questionnaire_parser` reads a split row cell by cell when at least one cell is question-
  or section-like on its own. Otherwise it uses the joined line exactly as before.
- `synthetic_pdf`: `Page.raw`, `bt_row()` and `tj_row()` write a whole table row in one text
  object (relative `Td` moves) or with `TJ` kerning, as real generators do. These are for test
  fixtures only.

## Not changed
- **Evidence text.** `extract_page_texts` and `parse_evidence` output are byte-identical. Table
  rows stay joined in evidence, as TC-01-003a documented, so the TC-01-003a locator corpus still
  scores 149/149.
- **Reading order.** Rows and cells keep content-stream order, so two-column pages still read
  column by column. When two question columns are written row by row on shared baselines, each
  joined line is split into its two questions, in stream order.
- Output shape, page numbers, `source_location`, confidence and the error types/messages.

## Behaviour changes (questionnaire parser only)
1. On split rows, the answer cells (`Yes`/`No`/`N/A`, checkboxes, a filled-in answer) are no
   longer part of the question text. `answer_type` is now inferred from the question cell, as it
   was with PyMuPDF. The `questionnaire_table_cells` parity test is now exact equality with the
   PyMuPDF baseline.
2. Two question cells on one row become two questions, where before they were one merged
   question.
3. A numbered row (`1.1 | Do you ...? | Yes`) used to be read as a *section header*, because
   `question_detector` treats "digits + space + capital" as a header. It is now read as the
   question, without the number cell (the PyMuPDF behaviour).
4. Answer cells written before the question in the stream (`Yes NoAre audit logs ...`, where
   pypdf adds no space) yield the clean question.

## Fallbacks (never lose text)
- Any failure in the geometry pass, or any page where the plain text and the geometry do not
  match character for character, leaves every line of that page unsplit. That is the
  TC-01-003a behaviour. Causes include form XObjects, decoding differences and a pypdf internals
  change.
- A split row whose cells are not question- or header-like on their own uses the joined line.
- Gaps under 1 em, or lone gaps under 3 em that line up with no other row, are never cut. A
  justified question with wide word spacing therefore stays whole, and so does a single row with
  a narrow trailing cell (its text stays in the question).

## Limits (logged, not fixed here)
- A question that wraps inside its cell over two lines is still read line by line, as before
  (and as with PyMuPDF).
- Answer padding written as literal spaces inside one string is not split. That would need a
  text heuristic.
- A trailing answer cell that itself looks like a question (`Do not ...`, ending in `?`) is
  detected as a question, as with PyMuPDF.
- The geometry uses private pypdf modules (`pypdf._text_extraction._layout_mode`). pypdf is
  pinned `>=6.21.2,<7`; a change there falls back to unsplit lines, and
  `tests/test_pdf_table_cells.py` would show the regression.
