## Behaviour

Line numbers were read at `6769a2c86f8c0d674fa9b6d70c65a03ef506707c`. That commit is the product code.

**Catalog.** `docs/product/tag-vocabulary.json` lists every framework key and every subject key, with the label and the aliases. Subject rows are tag category `topic` (`subject_tag_category`). `apps/api/app/services/tag_vocabulary.py` loads that file in a checkout (`vocabulary_path`, `load_tag_vocabulary`). The API image copies only `apps/api`, so the same JSON is also at `apps/api/app/data/tag_vocabulary.json`. The named test fails if the two files differ or if `SYSTEM_TAGS` framework and topic rows differ from the file. Document-type keys stay in code (`tag_service.py` `_DOCUMENT_TYPE_TAGS`) and are not part of the alias contract. `SYSTEM_TAGS` is the catalog entries plus those document types (`tag_service.py:34`).

A token is the lowercase letters and digits of a key, label, or alias (`normalize_tag_token`). Within frameworks, and within subjects, each token belongs to one key. The loader raises if two keys share one.

**Alias resolution.** `resolve_tag` and `get_or_create_tag` rewrite a framework or subject alias to the canonical key before lookup (`tag_service.py:82-84`, `tag_service.py:107-111`). `SOC II` and `soc-2` return the existing `soc2` system tag. `ISO/IEC 27001` returns `iso27001`. `iam` returns `identity_authentication`. `Access Control` returns `access_control`. The call does not insert a second key. A key that is not in the catalog still creates one workspace tag, and that tag stays hidden from another workspace. Workspace lookup still wins over the global system row when both use the canonical key.

**Suggestions.** `auto_tag_document` stores `source="ai"` and `approved=False` and does not write `frameworks_json` or `subject_areas_json` (`tag_service.py:441-472`). An approved manual add, or `approve_tag` with `approved=True`, appends that tag's label. Unapprove or remove of an approved assignment drops that label when no other approved tag on the document still has it. A label that was already on the document, such as `GDPR`, stays. Document-type and custom tags do not write those two fields (`_label_field`, `tag_service.py:541-546`).

**Invalidation.** Add, approve, remove, and relabel call `invalidate_derived_mappings` for that tag id and that workspace only (`tag_service.py:500-538`). A `question_mapping_preferences` row with `preferred_tag_id` equal to the tag becomes `status="stale"` and `approved=False`. An approved `evidence_tag_mappings` row with that `tag_id` becomes `approved=False`. A mapping for another tag, and the same tag in another workspace, stays approved. Framework-control mappings are keyed by framework name, not by the tag row, and are not changed. `stale` is not in the statuses a client can set on a questionnaire mapping. Regeneration still treats only `approved` and `manual` as protected, so a stale row can be generated again. The row is not deleted.

**Relabel.** `PATCH /api/tags/{tag_id}` uses the same reviewer-or-admin dependency as add, remove, and approve (`tags.py:131-155`, `_require_tag_manager`). An editor is 403. A system tag is 404 and keeps the vocabulary label. A tag owned by another workspace is 404. A workspace-owned tag is renamed. If it is a framework or subject tag, approved documents in that workspace replace the old label in the JSON field.

Existing workspace checks on document add, remove, and approve are unchanged. The tag router remains `/api/tags`.

The named test uses synthetic documents, questions, and evidence. It checks the docs file, alias collapse, an unknown custom key, unapproved JSON, and add, approve, remove, and relabel. The editor and the other workspace are refused.
