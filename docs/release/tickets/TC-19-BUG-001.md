# Provider response size limit

Assigned in [#85](https://github.com/Johnathan-u/trust-copilot/issues/85). Status: bounded decoder approved and merged in #87 as `2e8a59d`. The separately authorized encoding-classification follow-up is implemented; its exact-head CI remains pending.

## Contract

Slack and Gmail HTTP calls accept at most 1,048,576 decoded response bytes. Exact-limit responses succeed. Oversize bodies remain a nonretryable `response_too_large` outcome, including 429 and 503 responses. Rejected content is not included in the result.

The transport reads raw response chunks. A single `identity`, `gzip`, or `deflate` encoding is accepted. Compressed responses must use gzip or zlib wrapping (the Coordinator-prescribed `wbits=47` auto-detection); raw DEFLATE formerly accepted by HTTPX now returns nonretryable `invalid_encoding`. Compressed content goes through stdlib zlib with output capped to the remaining allowance plus one byte on every call; `unconsumed_tail` is processed through the same cap. The stream must reach EOF, and trailing compressed data is rejected. Malformed/incomplete compressed content is a nonretryable `invalid_encoding` outcome. Nested, unsupported or explicitly empty encodings use nonretryable `invalid_encoding` and are rejected before reading a body. A missing Content-Encoding header uses identity.

A declared Content-Length greater than the limit rejects before reading. Missing or understated length cannot bypass byte counting. Redirects return the existing `redirect_blocked` outcome before reading their body. The stream closes on success, rejection, and read/decode errors.

No database migration, dependency, route, credential, or scope changes. All tests use synthetic transports. Real provider sandbox qualification is outside this ticket.

## Review correction

[Coordinator review](https://github.com/Johnathan-u/trust-copilot/issues/85#issuecomment-6503727123) required bounded decompression after demonstrating that HTTPX decoded a complete network chunk before the original size check. That supersedes the first implementation's retained-body-only interpretation. The final code uses raw streaming and capped zlib output, not HTTPX's unbounded decompressor.

The new review regressions failed on `f80aa2e`: 13 failed and 14 passed. The implementation then passed all 97 focused tests (27 response-limit, 41 provider-wiring, 29 safe-collection). Tests include nested and single gzip payloads representing 32 MiB of zeros, with traced allocation constrained below 8 MiB; exact-limit gzip/deflate success; early length/redirect handling; and truncated gzip rejection.
