# TC-04-003 — Invalidate authority after password change or reset

**Status:** implemented, waiting for independent review. The implementer does not accept this result and must not merge it.

**Branch:** `fix/TC-04-003-reset-revocation`

Checked against parent `787976e9d7aee40c3cf0a5d5a94d74155fba32c1`. The batch-4 report at `docs/release/verification/TC-04-003.md` is the gap this change closes. Issue #85 comment 6961380351 requires the strict reading: a successful reset revokes every unused reset token for that user, and `change_password` drops other sessions regardless of the client flag.

## Release notes

- A successful `POST /api/auth/reset-password` deletes every unused password-reset token for that user, including the link that was just used. Any other unused link for that user then returns 400 `Invalid or expired link`.
- The same successful reset deletes every stored session for that user. Reset does not sign the caller in. A cookie from before the reset returns 401. The old password returns 401. The new password can sign in.
- `POST /api/auth/forgot-password` is unchanged. It still deletes unused reset tokens for that user when it issues a new link, so a later request normally leaves only one unused link. Reset is the backstop when more than one unused link is still stored.
- A failed reset does not delete tokens. A short new password is rejected before the token is consumed. An unknown token does not affect another user's links.
- Email-verification tokens and MFA recovery codes are not deleted by a password reset. They are not password-reset credentials. An unverified account that claims an invite still clears them, and that path is unchanged.
- `POST /api/auth/change-password` always deletes every other stored session for that user and keeps the session that sent the request. The current cookie still works. A second browser's cookie returns 401.
- The request field `invalidate_other_sessions` is still accepted, including when it is omitted (default `false`). It does not control revocation. `false` still signs the other sessions out. The audit event `auth.password_changed` records `invalidate_other_sessions: true` as the effective policy, `client_invalidate_other_sessions` as the value the client sent, and `revoked` as the number of session rows deleted.
- A wrong current password does not change the password and does not delete sessions.
- The account security page no longer offers a checkbox to keep other sessions. It says a password change signs out every other session and that this session stays signed in. The page still sends `invalidate_other_sessions: true` so an older server follows the same rule. The separate "Sign out all other devices" action is unchanged.

## Behavior

`reset_password` still looks up one unused token by its hash, rejects an expired link, and replaces `password_hash`. It then deletes every `password_reset_tokens` row for that user with `used_at` unset, and calls `_delete_user_sessions`. Already-used rows are left in place. They cannot be reused because lookup requires `used_at` to be null, and the row that was just presented is included in the delete.

`change_password` still requires the current password and a new password of at least 6 characters. On success it deletes `user_sessions` rows for that user except the current `session_id`. If that id is missing, every stored session for the user is deleted. A request that passed `require_valid_session` has a session id, so the cookie that changed the password stays valid.

Another user's reset tokens and sessions are not touched.

## Rollout and rollback

No migration and no backfill. Unused reset links and session rows already exist. The next successful reset or password change applies the new rule. Rollback is reverting this change. After a rollback, a successful reset again marks only the presented token used, and `change_password` again revokes other sessions only when the client sends `invalidate_other_sessions: true`.

## Limitations

- `forgot_password` still collapses unused links at issue time. Two sequential reset requests do not leave two live links. The new test plants the extra unused rows after the request, which is the state a concurrent issue can leave behind.
- Password reset does not disable MFA, delete recovery codes, or delete email-verification tokens. That is the policy recorded above.
- The security page sends `invalidate_other_sessions: true`. A client that sends `false` or omits the field gets the same revocation. The field remains in the API for compatibility.
