# TC-10-003c: No duplicate upload after a retryable enqueue 409

Status: implemented on `tc/core/TC-10-003c`.
Evidence: [`artifacts/acceptance/TC-10-003c/`](../../../artifacts/acceptance/TC-10-003c/README.md).

Follows [TC-10-003](TC-10-003.md) and TC-10-003b (#43).

## Problem

Since TC-10-003b, `enqueue_job` raises `EnqueueConflictError` when it loses the queued-slot race on every attempt. The API maps that to a retryable 409 `idempotency_conflict` with `Retry-After: 1`.

`POST /api/documents/upload` and `POST /api/questionnaires/upload` committed the `Document` or `Questionnaire` row and stored the file *before* `enqueue_job`. A 409 therefore left a committed row and a stored object behind. The client's retry created a second row.

## Design

`enqueue_job` and `idempotency.set` take a keyword-only `commit: bool = True`.

- `commit=True` is the previous behavior: success commits. `set` with a lost owner token returns `False` and does not raise.
- `commit=False` flushes and leaves the commit to the caller. `enqueue_job` still rolls the transaction back when it raises `EnqueueConflictError`, so the caller's uncommitted rows in that transaction cannot be committed afterwards. `idempotency.set(commit=False)` stays owner-token fenced: if the claim was lost it raises `IdempotencyClaimLost` and does not commit or roll back. The caller rolls back.

Both upload routes, after the workspace check:

1. Reject an invalid `Idempotency-Key` with 400 `invalid_idempotency_key` before anything is stored. A missing header skips idempotency.
2. Replay a completed key. Otherwise `claim()` and keep the owner token (TC-10-003b).
3. Store the object, insert the row, enqueue the job (`commit=False`), and `set` the response (`commit=False`) in one transaction, then commit once.
4. On `EnqueueConflictError` or `IdempotencyClaimLost`, roll back, delete the stored object (best effort), release this request's claim, and re-raise. The client gets the same retryable 409 (`Retry-After: 1`). A failed delete is logged; the 409 is still returned and no row remains.
5. Any other exception after the object is stored follows the same rollback, delete, and release, so a claim is not stuck and a rolled-back row does not leave the only copy of the object without a record. A successful commit is not undone.

Scopes are `documents.upload` and `questionnaires.upload`. The resource slot is the constant `new` (`ws:{workspace}:{scope}:new:{client key}`), because the row does not exist when the key is claimed. A retry or replay with the same key returns the original body (`id`, `job_id`, `display_id`, `storage_key`) and does not create a second row. Same-key concurrent uploads create one row. A 403 or an invalid key stores nothing and is not cached.

`IdempotencyClaimLost` uses the same handler as `EnqueueConflictError`. The questionnaire upload response adds `storage_key` so both routes can replay that field. Document responses already had it.

| Caller | Duplicate risk after a 409? | Change |
|---|---|---|
| `POST /api/documents/upload` | Yes. The document row and the object were committed before enqueue. | This ticket. One transaction, then delete the object on conflict. |

| `worker.enqueue_missing_index_jobs` | No. Documents are already committed (`status=uploaded`). A conflict does not insert a second document. | None. |

## Open questions

- The idempotency resource slot is the constant `new`, not a hash of the file. A reused key returns the first response even when the bytes differ. That is the usual Idempotency-Key contract: the key names the request the client means to retry. A new file needs a new key.
- `enqueue_job(commit=False)` rolls the caller transaction back on `EnqueueConflictError` (same as `commit=True`). `set(commit=False)` does not roll back on a lost claim; the upload route does. Splitting it this way matches the two primitives: a lost race must not stay committable, and a lost claim must let the caller decide.
- On any exception after the object is stored and before the single commit, the route deletes the object and releases the claim, not only on `EnqueueConflictError` and `IdempotencyClaimLost`. Otherwise a later error would leave an orphan object and a stuck in-progress key. A committed upload is not deleted.
- If that delete fails, the object can remain and the client still gets the 409. There is no row. Sweeping that orphan is out of scope (TC-10-005 owns orphan objects).
- `maybe_auto_generate` can still drop an uncommitted parse-job completion if enqueue raises `EnqueueConflictError`, because the worker catches `Exception` and then commits. That is not the duplicate-upload bug. It was left unchanged so this ticket does not move the worker's commit boundary.
- Questionnaire upload responses now include `storage_key`. The field is additive. Documents already returned it. Both replays need it.
- A same-key request that loses `claim()` still gets the existing in-progress 409 (`Request in progress; retry with same Idempotency-Key`), not `idempotency_conflict`. The winner's stored body is what the retry replays.
