## Delivered contract

`/dashboard/trust-requests` consumes only the existing authenticated incoming
Trust API. Navigation identifies this as Incoming Trust requests; outbound
requests are unchanged. The screen checks the current `can_review` permission,
including custom roles, rather than assigning authority from a role name. The
navigation entry remains discoverable with the existing shared navigation
contract; the page and API enforce access. No shared shell or auth edits are made.

The list sends the current workspace id and rejects mismatched response rows.
Detail responses must match both workspace and selected request; notes and mutation
acknowledgments must match the selected request and reply. Workspace/user changes
remount the screen, discard previous workspace state and ignore late responses.
Attachments download only through the protected request endpoint, never a storage
key or public blob URL. Failed downloads have an explicit error.

Saving a draft does not approve or send it. Existing replies show their saved
revision and approval state. A reviewer must explicitly check the saved revision
before saving edits or approving; edits disable approval/send until the new revision
is acknowledged. A refreshed conflicting reply shows its latest saved text beside
the retained local text and requires review again. New drafts and edited text stay
in the page after 403/404/409 or an unconfirmed result. Refreshing a reply that has
become unavailable retains the local text with mutation actions removed. Navigation
and reload warn about unsaved text; no sensitive reply is persisted in browser
storage. Switching workspace intentionally clears the old workspace's state.

Send is a separate action on an approved unchanged revision. The screen says
provider accepted, not recipient delivered. Accepted, uncertain and sending records
cannot be edited or resent. Unavailable means the provider was not called. A failed
or unavailable send requires an explicit saved-state reload before any eligible
retry. No automatic retry or blind resend occurs. One mutation/reload runs at a
time for the selected request. Legacy null-revision replies need a saved revision
before approval. Unknown future outcomes disable reply mutations.

## Acceptance and execution ledger

- Consumer parser/reply-state tests first failed against unimplemented behavior,
  then passed. They cover workspace/request/reply mismatches, no storage-key
  exposure, exact approval provenance and immutable delivery-attempt states.
- Rendered-component tests first failed against the absent screen, then passed.
  They exercise real page code with synthetic HTTP responses: review/approve/send,
  approval invalidation, denied/stale save retention, no blind resend, current
  permission denial and an old-workspace response arriving after switching.
- A refresh-loss regression failed before the fix, then passed: a missing saved
  reply now retains local text as a non-mutable recovery record.
- The backend-derived `internal_note` fixture exposed and reproduced a consumer
  discriminator mismatch. The parser/page now accept the actual contract and keep
  internal notes read-only alongside reply actions; no backend change was made.
- Additional controls cover unconfirmed creation, a lost send response followed by
  authoritative acceptance, and the unsaved-text unload guard.
- `screen-trust-requests.spec.ts` contains 22 browser cases. Synthetic responses
  cover current built-in/custom permissions, partial/error/empty states, download
  denial, revision conflicts, reload, lost acknowledgments and workspace races.
  Three viewport cases (360/768/1440) check keyboard focus, horizontal overflow,
  axe and screenshots. Axe artifacts include integer `violationCount` equal to
  `violations.length`. These cases still require actual Chromium execution.

   custom permission flags. No owner/viewer mapping was invented.
3. **Integrated API/browser qualification:** these synthetic HTTP fixtures prove
   control paths only. A real backend/browser persistence and tenant acceptance
   run is separate and remains pending for the parent.
4. **Live provider delivery:** no provider, account or paid service was contacted.
   Actual provider acceptance/delivery qualification remains separate and pending.
