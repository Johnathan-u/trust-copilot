# TC-10-003d: Keep parse-job completion when auto-generate enqueue conflicts

Status: implemented on `tc/core/TC-10-003d`.
Evidence: [`artifacts/acceptance/TC-10-003d/`](../../../artifacts/acceptance/TC-10-003d/README.md).

Follows [TC-10-003c](TC-10-003c.md).

## Problem

After a `parse_questionnaire` job, the worker calls `automation_service.maybe_auto_generate`. That enqueues a `generate_answers` job through `job_effects.enqueue_job`. Since TC-10-003b, `enqueue_job` raises `EnqueueConflictError` when both insert attempts lose the queued-slot race, and that path calls `session.rollback()` before raising.

The worker sets the parse job to completed, writes `job.completed`, then calls `maybe_auto_generate` inside `except Exception: pass`, and then commits. A rollback inside `enqueue_job` discards whatever was still pending in that session. The exception is swallowed, so the worker does not crash, and the following commit stores only what survived the rollback.

What the probe on unmodified master actually showed: `persist_audit` commits the session while writing `job.completed`, and that commit includes the completion fields (`status`, `completed_at`, `result`) because they were already pending. So the status stayed `completed` in the probe. The rollback still drops anything not yet committed, and nothing wrote the conflict onto the job. The result stayed `{"count": 1}` with no conflict marker. The only log line was `enqueue_job`'s own warning. The completion boundary was an accident of the audit helper, not a commit the worker made before auto-generate.

## Design

Option (a): commit the parse-job completion before calling `maybe_auto_generate`.

Option (b) was a separate transaction or savepoint around the auto-generate enqueue, plus its own retry. `enqueue_job` already retries once, and on the second loss it calls `Session.rollback()`, which ends the whole transaction, not a savepoint. Containing that rollback needs another session, and a further retry is a second enqueue policy. Option (a) is the smaller change: one commit on the parse path, then a typed catch.

On `parse_questionnaire`, when the outcome is not `superseded`:

1. Commit the completion (status, timestamps, result, and the `job.completed` audit) before auto-generate.
2. Call `maybe_auto_generate` as before.
3. On `EnqueueConflictError`, log a warning and set `result.auto_generate` to `enqueue_conflict`, keeping any parse result already stored (for example `count`). The worker's existing commit then stores that annotation. The parse job stays completed. No generate row is inserted by the failed attempts: `enqueue_job` rolls the insert back (savepoint, then the full rollback) and this path does not retry again.
4. Any other exception is still swallowed. The parse job is not failed. Because the completion was committed in step 1, a later rollback cannot return it to `running`.

Other `enqueue_job` callers are unchanged. `enqueue_job` itself is unchanged. No migration.

`auto_generate` sits beside an existing `outcome` (`already_applied`, `reconciled`, `superseded`) instead of replacing it. A superseded parse never calls `maybe_auto_generate`.

## Open questions

- Route-handler docstrings outside `questionnaires.py` still publish ids. That set is 34 handlers, past the cutoff, so they were not edited. They are `answers.bulk_update_status` (`REV-07`), `exports.trigger_generate` (`AI-06`), `exports.trigger_export` (`EXP-07`), `workspaces.get_current_workspace` and `update_current_workspace_policy` (`ENT-202`), seven handlers in `members.py` (`AUTH-208`, `AUTH-212`, `AUTH-215`, `AUTH-216`), and 22 handlers in `auth.py` (`AUTH-nn`, `ENT-nn`, `WEB-nn`). Module, helper, service, test, and migration docstrings are in scope no longer.
- The conflict marker is `result.auto_generate = enqueue_conflict`, not a new `result.outcome` value. Replacing `outcome` would hide `reconciled` or `already_applied` on the same parse.
- There is no second retry after `EnqueueConflictError`. `enqueue_job` already tried twice. Another insert could create a generate job the conflict path is required not to leave behind. A later manual generate still uses the same idempotency key.
- `persist_audit` commits the caller's session. The worker now commits again before auto-generate so the completion does not depend on that side effect. Callers of `persist_audit` other than this path were not changed.
- Backlog TC-10-003g (low): if maybe_auto_generate swallows a non-conflict exception after a partial write, the worker's commit (around worker.py:1165) can still persist that partial write. Master already behaves this way; not changed here.
