# TC-21-008 Scoped actionable compliance alerts

**Status:** implemented locally. Not pushed. Framework catalogs stay **BLOCKED** pending **TC-01-007**. No framework requirement text was added.

Before this change, `GET /api/compliance-alerts/active` computed alerts from coverage and stored nothing. `POST /api/compliance-alerts/scan` did not exist.

## Behavior

`GET /api/compliance-alerts/active` stays read-only and stays on admin. It returns persisted rows whose status is `active`. It does not compute a fresh alert and it does not wake a snooze.

`POST /api/compliance-alerts/scan` is admin. It stores one row per workspace, condition, and source. A second scan updates that row, including `source_revision` and `control_revision`. It does not insert another active row. An acknowledged row, and a snooze that has not expired, stay on that same row. A snooze whose `snoozed_until` has passed becomes `active` on the next scan. When the condition is gone, the open row becomes `resolved`. A later scan of the same condition inserts a new active row.

Coverage conditions are `coverage_drop`, `high_insufficient`, `blind_spot`, `weak_evidence`, and `framework_gap`. Their `source_revision` is a short fingerprint of the coverage numbers, because coverage has no revision column. `control_id` and `control_revision` stay null. An open `control_check` gap adds `control_gap`. Its source is `control:<id>`. `control_revision` is `workspace_controls.content_version`, or `updated_at` when that version is null. A control in another workspace is omitted.

`POST /api/compliance-alerts/{id}/acknowledge`, `/snooze`, and `/resolve` are review. A missing id and an id from another workspace both return 404 `Alert not found`. A resolved row returns 409 `already resolved`. `Idempotency-Key` is required. The same key and body replay. A different body is 422 and writes nothing. Each mutation writes one audit row with the user id. A failed publish after the scan commits leaves the rows and returns `partial: true`.

The response schema is `compliance-alerts/v1`. The notifications page reads it through `parseComplianceAlerts`.

## Permissions

`GET /api/compliance-alerts/active` stays admin. New mutation routes are listed below.

| Route | Permission |
| --- | --- |
| `GET /api/compliance-alerts/active` | admin |
| `POST /api/compliance-alerts/scan` | admin |
| `POST /api/compliance-alerts/{id}/acknowledge` | review |
| `POST /api/compliance-alerts/{id}/snooze` | review |
| `POST /api/compliance-alerts/{id}/resolve` | review |

## Migration

Existing tables cannot store this honestly. `alert_acknowledgments` is an action log: it has no single lifecycle, no source revision, and no one-active identity. `evidence_gaps` is constrained to gap statuses and close reasons, and its identity is a question or a control check, not a coverage condition. `in_app_notifications` is a per-user read flag. A partial unique index is itself a schema change.

`tc21008_alert_records` revises `tc02001a_parent_ws_move` on one `down_revision` line. It creates `compliance_alerts` and the partial unique index `uq_compliance_alerts_one_active` on `(workspace_id, condition, source_ref) WHERE status = 'active'`. `workspace_id` references `workspaces` and cascades on delete. Downgrade copies the rows into `tc21008_alert_hold` and drops the live table. Upgrade copies them back and empties the hold table. The scan takes `pg_advisory_xact_lock(150017, workspace_id)` before it writes. A conflicting insert uses a savepoint and updates the active row.

## Ambiguities

- `GET` is empty until a scan. That is the read-only split from the old computed response.
- Acknowledged and unexpired snoozed rows are not active, so they stay out of `GET /active`.
- Coverage has no stored revision. The fingerprint is derived from the numbers already on the coverage response.
- `alert_acknowledgments` is unchanged.
- The scan does not send email or chat. `_publish_scan` is only the partial-failure hook.
