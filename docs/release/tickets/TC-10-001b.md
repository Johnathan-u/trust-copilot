# TC-10-001b Grace-period recovery for NULL-lease running jobs

**Status:** implemented. No migration. Alembic head is unchanged.

A `running` job whose `lease_owner` and `lease_expires_at` are both NULL was claimed before the lease deploy. `recover_abandoned_jobs` used to skip it, so it stayed `running`. The operator SELECT and fail-by-id statements in [TC-10-001](TC-10-001.md) were the only way to stop one. Those statements stay as the fallback.

## Recovery

`JOB_NULL_LEASE_GRACE_SECONDS` defaults to 3600. It is clamped to at least five times `JOB_LEASE_SECONDS` and at most 86400. An invalid value falls back to 3600, then that clamp. The worker reads it on each recovery pass. `Settings.job_null_lease_grace_seconds` mirrors it at process start.

Each claim loop still locks an expired lease first. If there is none, it locks one `running` row with both lease columns NULL whose `COALESCE(updated_at, started_at)` is at or before database `now()` minus the grace:

```sql
SELECT id, lease_owner
FROM jobs
WHERE status = 'running'
  AND lease_owner IS NULL
  AND lease_expires_at IS NULL
  AND COALESCE(updated_at, started_at) <= now() - make_interval(secs => :grace)
ORDER BY COALESCE(updated_at, started_at), id
FOR UPDATE SKIP LOCKED
LIMIT 1
```

`now()` is the database clock. The worker clock is not used for the comparison. A row with both timestamps NULL is not selected.

The rest of the path is the expired-lease path. The row stays locked. A new owner token and expiry are written. `job.abandoned` is flushed in that transaction, then the retry classifier commits it together with `job.retry_scheduled` or `job.failed`. The attempt was counted at claim time and is not incremented here. Backoff and the attempt cap are the existing ones. `error_code` is `lease_expired`.

After that commit, a normal claim of the re-queued job can land before this loop reads the row again. If the post-commit read no longer shows the classified status, the row is logged and the loop continues. The abandoned audit is already committed. If the token swap is not visible before the classifying commit, the loop logs and returns the count so far. That case should not happen under `FOR UPDATE SKIP LOCKED` on a real database.

No new column and no new index. `updated_at` and `started_at` are already on `jobs`. The pass is `LIMIT 1` against the leftover NULL-lease rows, not a hot path once those rows are gone. An index would be a migration and is not required for the lock to be correct.

## A live old worker

An old-version worker has no lease and no commit fence. The grace is what keeps recovery from taking a job that process is still in.

* The grace is at least five lease periods, and 3600 seconds unless a longer lease raises that floor. That is the same order as `WORKER_JOB_MAX_RUNTIME_SEC`. Operators can also lower `JOB_NULL_LEASE_GRACE_SECONDS`, down to five times the lease (300 seconds when the lease is the default 60). Doing so raises the chance of recovering a job a live old worker is still running.
* If that process still commits the job row, `updated_at` moves and the grace starts over. `started_at` is used only when `updated_at` is NULL.
* Two recoverers cannot both classify the row. `FOR UPDATE SKIP LOCKED` gives it to one session. The token swap and the classification commit happen before the lock is released.
* A later attempt does not repeat a side effect already stored in `job_effects` for that job (`attempt = 0` on applied effects). The approved-answer guard still refuses to overwrite an approved answer, or an answer whose `updated_at` is after the job was requested.

Residual risk. The old worker does not look at a lease, so it can commit after the new attempt has started. Writes that are not in the effect ledger and are not covered by the answer guard can land twice. Work still open in the old process is not rolled back by recovery. `updated_at` and `started_at` were stored from the worker clock when the row was written; the grace absorbs ordinary skew against database `now()` and does not remove it. A long job that never writes the job row can be recovered at the end of the grace while that process is still running. Raise `JOB_NULL_LEASE_GRACE_SECONDS` if pre-deploy jobs are expected to run longer than the default. To stop one job immediately, use the runbook SQL.
