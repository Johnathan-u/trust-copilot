# TC-09-006: Make repeat upload and parsing deterministic

This file records the implementation. It does not accept TC-09-006. AC1 and AC2 stay unverified until an independent reviewer accepts them. No migration was added. No customer workbook is in the fixture or the evidence. The children TC-09-006a and TC-09-006b are implemented here and are not counted toward DONE by this file.

## What the check does

A replay is decided by `content_hash` and `original_file_hash`, not by whether any question row exists. The same bytes are a no-op. A replaced file on the same questionnaire is parsed once. An approved answer stays on its question. A dropped question that still has an approved answer is kept with `source_location` `not_in_current_file`. Export skips that marker, so the old file hash does not make the new workbook stale and the answer is not written into the file. A draft on a dropped question is deleted. The jobs page shows `input_version_changed` with the questionnaire status. The review page labels the retained question as not in the current file.

The runbook is `docs/ops/questionnaire-replay.md`. There is no new setting.

## Contract

`GET /api/jobs` and `GET /api/jobs/{id}` add `input_version_changed` (boolean) and `questionnaire_status` (a known status, or null). The job result reason `input_version_changed` is unchanged. A successful parse of the current bytes does not set that reason. No response field carries file bytes, a storage key, or question text. No migration.

Two deliveries of the same parse take the existing `FOR UPDATE` lock on the questionnaire row and then re-read the questions effect. The second delivery does not insert. The existing unique key on `job_effects` is unchanged. Nothing new is persisted that would need a rollback.
