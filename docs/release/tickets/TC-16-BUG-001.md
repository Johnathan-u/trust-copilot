# TC-16-BUG-001 — Settings page now gates admin-only sections by role

## Behavior

The Settings page gates admin-only sections by role. It uses the session `can_admin` flag, the same flag the navigation uses.

While that session is still loading, the dashboard shell shows “Loading workspace…” and does not mount the page. If the page itself renders during loading, it shows “Loading settings” and mounts neither admin-only sections nor the not-authorized state. That avoids treating the initial `can_admin: false` value as a decision.

After the session resolves, a workspace admin sees the admin introduction (“Workspace and user settings”), the admin-only sections, the workspace switch when they belong to more than one workspace, and Account Security.

Any other signed-in member sees an accessible not-authorized state: heading “Not authorized”, a short explanation that administration sections on this page are limited to workspace admins and that account security stays available, and a “Back to dashboard” link to `/dashboard`. Account Security stays on the page. The workspace switch stays when they belong to more than one workspace, matching the switch already in the sidebar. Admin-only sections are not mounted.

## Section classification

| Section          | When it mounts                                                      |
| ---------------- | ------------------------------------------------------------------- |
| Billing          | Session resolved and `can_admin`                                    |
| Create workspace | Session resolved and `can_admin`                                    |
| Workspace switch | Session resolved, any signed-in member, and more than one workspace |
| Account Security | Session resolved, any signed-in member                              |

Account Security is personal. It is the same destination as the account menu (`/dashboard/security`) and is not an admin navigation item.

## Tests

`apps/web/lib/settings-access.test.ts` covers the three phases: loading mounts no sections, an admin sees every section, and a non-admin sees only the personal sections. Vitest runs in Node, and the web app does not depend on a component-testing library, so these stay pure unit tests.

`apps/web/e2e/release/settings-access.spec.ts` covers the page in the browser: an admin, a non-admin, and a held session. The existing auth setup signs in against a live API, so this spec uses a synthetic session cookie and a mocked session, the same approach as `responsive-shell.spec.ts`. Axe runs on `[data-testid="settings-not-authorized"]` and must report 0 violations. Evidence is `artifacts/acceptance/TC-16-BUG-001/axe-not-authorized.json`.

The spec is local to this ticket. The CI web-release job is unchanged.

## Local gates

Frontend gates use Node 24 (`apps/web/.nvmrc`, `>=24.11.0 <25`). From `apps/web`: `npm run lint`, `npm run format:check`, `npm run test:unit`, `npm run typecheck`, `npm run build`, then `npx playwright test e2e/release/settings-access.spec.ts`. No new dependencies. Synthetic data only.

## What this ticket does not change

Server behavior, middleware, and the CI workflow stay as they are. Rollback is reverting this change.
