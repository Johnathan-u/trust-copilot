## Defect and behavior

The approval service previously looked up golden answers by ID alone. A member
of workspace A could read workspace B's approval history and, with the existing
route permission, change B's answer, assign its owner/reviewer, or approve a
mixed-workspace batch. Mutation responses disclosed the foreign answer text.
Assignment also accepted users without current membership in the answer's
workspace. A stored-auth, FK-enforced SQLite HTTP diagnostic reproduced these
behaviors before implementation.

Every approval service operation now requires an explicit workspace argument.
Parent lookup checks the ID and workspace before status inspection, projection,
assignment or mutation. Foreign, moved, missing and hard-deleted parents return
the same neutral 404, including history. Own history with no events remains a
successful empty list.

Owner/reviewer targets must have a current nonsuspended membership in that
workspace. No recipient-role restriction is added. Bulk approval authorizes
the entire requested set before any writes; an unavailable ID rejects both
input orders without changing any answer or event. For fully authorized sets,
existing status skips, duplicate handling, empty input, timestamps, review
cycles and events remain intact. Queue/overdue scope and all route permission
dependencies are unchanged.

GoldenAnswer has no soft-delete column, and `source_answer_id` is an optional
integer without a foreign key. This child adds no document/archive eligibility,
source-version, schema, migration, provider, dependency, or UI behavior.

## Acceptance evidence

`tests/release/test_authorization_answer_approval.py` contains 106 SQLite
controls and the same 106 migrated-PostgreSQL cases. They exercise the real
HTTP routes, current stored membership and expiring signed session. Only
`get_db` is wired to the fixture store; no auth, route, service or SQL mocks are
used. SQLite foreign-key enforcement is enabled and checked.

The matrix covers all eight object actions, queue and overdue; foreign, moved,
deleted and unknown parents; foreign status disclosure; invalid assignees;
both mixed-batch orders; every existing built-in role and a session-only custom
role; suspended/removed membership and revoked sessions. Positive controls
verify transition/event/expiry behavior, permitted recipient roles, authorized
status skipping, duplicates, empty batches, empty history, and correctly scoped
queue/overdue results.

Denied requests compare full rows and counts across ten relevant tables and
record SQL statements to reject INSERT/UPDATE/DELETE even if later rolled back.
Fixture cleanup resolves exact event IDs belonging to exact owned parent IDs,
deletes only owned rows in FK order, and compares the entire original snapshot.
Collection does not open the fixture store. Existing approval service tests
retain their assertions and receive only the required workspace argument and
owned active-assignee fixture adaptation.
