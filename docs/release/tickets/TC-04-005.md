## Release notes

- Demotion, suspension, and removal apply on the next request that still carries the old browser cookie. The cookie is not deleted, and the `user_sessions` row is not deleted by those three actions.
- The next request reads `workspace_members` for the user and workspace in the cookie. The role signed into the cookie is not the role the API uses.
- Suspension or removal of the workspace the cookie currently points at returns 403. That same cookie cannot switch into another workspace, because the current membership is checked first.
- A cookie that already points at a workspace where the person is still a member keeps only that membership's permissions. Switching back to the suspended or removed workspace returns 403 and does not set a new cookie.
- There is no organization suspension. A workspace row has no suspended flag. Suspension is the `workspace_members.suspended` flag for one user in one workspace.
- API keys are not revoked when a member is demoted, suspended, or removed. They are not revoked when an administrator revokes that user's browser sessions. Revoking a key is a separate delete of that key.
- `POST /api/members/{id}/revoke-sessions` deletes every stored session for that user, in every workspace, and the old cookie then returns 401. That route is separate from demotion, suspension, and removal.

## What the next request does

`require_session` accepts a valid API key before it looks at a cookie (`apps/api/app/core/auth_deps.py:204-209`). For a human cookie it checks the stored session (`:213`) and then calls `resolve_current_membership` (`:215`). `GET /api/auth/me` does the same membership read (`apps/api/app/api/routes/auth.py:1773-1775`).

`resolve_current_membership` loads `WorkspaceMember` for the cookie's user and workspace (`auth_deps.py:188-193`). A missing row returns 403 `Active workspace membership required` (`:194-195`). `suspended` returns 403 `Your account has been suspended in this workspace` (`:196-199`). Otherwise the session role becomes the row's role (`:201`). The signed cookie is left as it was.

## Demotion, removal, and suspension

`PATCH /api/members/{id}` writes `mem.role` and does not delete a session (`apps/api/app/api/routes/members.py:331-332`). `DELETE /api/members/{id}` deletes that one membership row (`:394-396`). `PATCH /api/members/{id}/suspend` sets `mem.suspended` (`:459`). None of those handlers query `UserSession` or `ApiKey`.

If the removed person has no membership left, the user row is deleted (`members.py:412-420`). `user_sessions.user_id` is `ON DELETE CASCADE` (`apps/api/app/models/user_session.py:16`, migration `apps/api/alembic/versions/013_user_sessions.py:21-23`), so those session rows go with the user. A person who still belongs to another workspace keeps the user row and the session row. The release test covers that remaining-membership case.

## The other workspace

`POST /api/auth/switch-workspace` calls `require_session` first (`auth.py:1891`). When the cookie's current membership is missing or suspended, that check returns 403 and the handler does not read the other membership or set a cookie.

When the current membership is still active, the handler loads the target row (`auth.py:1894-1902`). A missing or suspended target returns 403 `Not a member of this workspace` and does not set a cookie (`:1903-1904`). An active target reissues the cookie with that row's workspace and role (`:1914-1918`). The stored session id is unchanged.

A cookie already issued for the remaining workspace keeps working. `/api/auth/me` then returns that row's role and that role's permissions only.

## API keys when a user or workspace is suspended

API keys are not revoked.

`ApiKey` has `workspace_id`, `key_hash`, `label`, `role`, and `expires_at` (`apps/api/app/models/api_key.py:10-25`). It has no `user_id`. Migration `025` creates the same columns and a cascade from `workspaces`, not from `users` (`apps/api/alembic/versions/025_api_keys.py:19-33`). `Workspace` has no suspended column (`apps/api/app/models/workspace.py:8-20`). There is no organization model and no organization-suspension path.

`get_api_key_context` loads the key by hash, rejects an expired key, and returns that key's workspace and role (`auth_deps.py:143-165`). It does not read `WorkspaceMember`. `require_session` returns that context before the human membership check (`:206-209`). Suspending or removing the human who created the key does not change the row. Demotion does not change it. `POST /api/members/{id}/revoke-sessions` deletes `UserSession` rows for that user (`members.py:510-516`) and does not delete `ApiKey` rows.

A key stops working when it is expired (`auth_deps.py:157-158`) or when an administrator deletes it with `DELETE /api/members/api-keys/{key_id}` (`members.py:693-706`). That delete is per key and per workspace. It is not tied to member suspension.

This is a gap relative to a reading of the ticket that expects suspension to cut off machine credentials. This change does not close it. The release test records the current behavior: after the human member is suspended, the workspace API key still authenticates as its own role, and the human cookie is 403.

## Explicit session revocation

`POST /api/members/{id}/revoke-sessions` deletes every `user_sessions` row for that user, not only sessions that were using the caller's workspace (`members.py:510-516`). The old cookie then fails `enforce_session_record` with 401 `Session invalidated` (`auth_deps.py:86-95`). Memberships and API keys stay.

## Help and runbook

No configuration changed. No migration and no backfill. Rollback of this change is reverting the test, this note, and the artifact. Auth behavior stays the behavior on `0fb552fc`.

Operators:

- Demote with `PATCH /api/members/{id}` and `{"role": "..."}`. The member's existing cookie is still presented. The next `/api/auth/me` shows the new role. Do not expect the browser cookie or the `user_sessions` row to disappear.
- Suspend with `PATCH /api/members/{id}/suspend` and `{"suspended": true}`. A cookie for that workspace gets 403 `Your account has been suspended in this workspace` on the next request, including `POST /api/auth/switch-workspace`. The session row remains. Reactivate with `{"suspended": false}`.
- Remove with `DELETE /api/members/{id}`. A cookie for that workspace gets 403 `Active workspace membership required`. Other memberships remain. If it was the person's last membership, the user row is deleted and the session rows cascade with it.
- To drop the browser session itself, `POST /api/members/{id}/revoke-sessions`. That deletes every stored session for the user. API keys are unaffected.
- To drop a machine credential, `DELETE /api/members/api-keys/{key_id}` for that workspace. Suspending the user does not do this.
