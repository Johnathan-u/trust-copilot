# TC-21-013a: Deterministic gap races and legacy create replay

Local only. This branch is not pushed and this file is a draft, not an open pull request.

Built from origin/master `8060788` (#83).

## Races

`test_decision_and_resolve_race_for_one_open_gap` holds the winner inside the open-row update and starts resolve only then. It requires `pg_stat_activity` or `pg_locks` to show an ungranted `advisory`, `transactionid`, or `tuple` lock before the winner commits.

`test_scan_and_manual_create_leave_one_open_control_gap` holds the scan after `pg_advisory_xact_lock(150016, control_id)` and starts the manual create only then. It requires the same lock wait before the scan continues.

Checked by reverting the guards locally, not by guessing:

- Removing the scanner's `_lock_control_gap_writes` call made the scan test fail with `scan never took the control lock`.
- Replacing `_update_open_gap` with `return True` (no row update) made the decision test fail with `resolve did not wait on the open-row lock`.

Both guards were restored. The evidence-gap release file then passed: 17 tests.

## Legacy create keys

A completed create with no `_request_sha256` is replayed only when the stored response and the new request have the same `gap_type`, `control_id`, and `question_id`. If any of those fields is missing or different, the request stays 409 and does not write. `docs/release/tickets/TC-21-013.md` records that rule.
