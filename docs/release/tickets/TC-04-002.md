## Release notes

- `POST /api/auth/forgot-password` still answers 200 with `If that email is registered, you will receive a reset link.` for an unknown address, for an accepted send, and for a send that fails. The body does not say which of those happened.
- A provider result of false, or a send that raises, does not delete a reset link that was already delivered. The new row is rolled back. The failure is logged with the address and the user id, never the reset URL, and stored as audit action `auth.reset_send_failed`.
- An accepted send commits the new row and deletes older unused rows for that user (a lower id only). `TRUST_COPILOT_DEV_RETURN_RESET_URL` adds `reset_url` only after that commit, only outside production. A failed send and an unknown address omit it.
- The reset message is sent on the request, not on a background thread. The request waits until the provider returns.
- `POST /api/auth/reset-password` locks the account row, then the unused token row (`SELECT ... FOR UPDATE`). A second submit of that same token, including one that is already in flight, returns 400 `Invalid or expired link`. One password is stored. A password shorter than 6 characters is still rejected before the token is read.
- No migration and no backfill.

## Behavior

`forgot_password` still rate-limits by IP and still returns before any mail when the address is not a user. It does not write `auth.reset_requested` or `auth.reset_send_failed` for that address, and it does not call the provider. That is the same as before. The HTTP body matches the body used when the address exists.

When the address exists, the route inserts a `password_reset_tokens` row and flushes it in the open transaction. It does not delete older unused rows yet. It then calls `send_password_reset_email` on this request.

- If the provider returns false, the reason is `provider_rejected`. If it raises, the reason is `provider_error`. The log line names the exception class and does not include the exception text, because that text can carry the message. The transaction rolls back, so the new row is never visible. A delete of that id follows, in case a commit had already landed it. Previously delivered unused rows stay. The audit row is `auth.reset_send_failed` with `{"reason": "<reason>"}` and no token.
- If the provider returns true, unused rows for that user with a lower id are deleted and the new row is committed together with `auth.reset_requested`. A concurrent issuance with a higher id is not deleted by this request. Deleting it as well can leave both callers holding a link that no longer exists.
- If the commit after an accepted send fails, the new row and the delete of older rows roll back. The previous link still works. The emailed link does not match a stored row. The audit reason is `store_failed`, and the HTTP body is still the generic sentence, without `reset_url`.
- An audit write that fails does not change the HTTP status. A 500 only for a real account would say that the account exists.

`reset_password` still rejects a missing token or a short password before it reads a row, so a bad password does not consume the link. It then reads the unused row to learn the user id, locks that user with `SELECT ... FOR UPDATE`, and locks the unused token row the same way (`populate_existing`, so a deleted row is not served from the identity map). The account lock is first so two different links cannot each lock a token and then deadlock while deleting every unused row.

Only the request that still sees the unused row after those locks changes `password_hash`, deletes every unused reset row for that user, deletes that user's sessions, and commits. The other request gets 400 `Invalid or expired link`. An expired link is rejected while the locks are held and is not deleted; closing the request rolls the locks back. Email-verification rows and MFA recovery codes are still not password-reset credentials. That rule is unchanged from TC-04-003.

SQLite's compiler drops `FOR UPDATE`. The overlap test skips there with that reason. PostgreSQL, including CI, runs it with two connections. The pause is inside password hashing, which runs only after both locks are held, so the second submit is waiting on the lock rather than hashing.

## Policy

Anti-enumeration wins over a distinct mail-outage status. A 503 only when a real account's send fails would tell the caller the address exists. The recoverable outcome is: the previous link still works, the unsent row is not left behind, the failure is in the log and in `audit_events`, and the caller can submit again. The forgot-password page is unchanged. It already shows "Check your email" for this 200. It does not gain an error state that would differ for a known address.

Verification mail is out of this change. `_issue_verification` still commits the new code and link and does not look at the provider result, and resend still deletes the previous verification rows first. The batch-4 report already treated expired, cross-user, and resend verification as meeting AC1. Claude's implementation notes for this pass (#85 comment 6961380351 and #276 comment 6965103570) are the reset send, a single-use reset test, and the same-token reset race.

## Rollout and rollback

No migration and no backfill. Unused reset rows already exist. The next forgot-password or reset-password request uses the new rule. Rollback is reverting this change. After a rollback, a failed send again deletes unused rows before the background send, and two simultaneous submits of one token can both return 200.

## Limitations

- Verification and invite sends are unchanged. A false result from `send_verification_code_email` is still ignored after the new verification rows are committed.
- Two overlapping forgot-password requests that both get an accepted send can leave two unused links, because each request deletes only lower ids. Redeeming either link still deletes every unused reset row for that user.
- The forgot-password request holds its database transaction until the provider returns. The SMTP provider times out at 10 seconds. A process stop after the provider accepts and before the commit rolls the new row back; the previous link remains, and the emailed link does not match a stored row.
- The concurrency test is skipped when the bind is not PostgreSQL. SQLite cannot make `SELECT ... FOR UPDATE` meaningful. CI's database is PostgreSQL, so the test runs there.
