## Release notes

- `POST /api/auth/forgot-password` answers 200 with `If that email is registered, you will receive a reset link.` before the provider is called. A known address is not slower than an unknown one. The body does not say whether the address exists or whether the provider accepted the message.
- The send runs on a background session. That session inserts the new reset row, sends, and commits the row only when the provider accepts. A false return or a raised send rolls the new row back, so a link that was already delivered still works. The failure is logged without the reset URL and stored as `auth.reset_send_failed`.
- An accepted send deletes older unused rows for that user (a lower id only). Outside production, `TRUST_COPILOT_DEV_RETURN_RESET_URL` puts the candidate `reset_url` on the immediate response. The row is stored only after the provider accepts, so a later rejection does not leave that link usable.
- `POST /api/auth/resend-verification` uses the same background rule for the code and the link. It does not delete the delivered code before the provider accepts the new message. A rejected resend is `auth.verification_send_failed`. Register queues the first message the same way and still returns the generic sentence immediately.
- `POST /api/auth/reset-password` locks the account row, then the unused token row (`SELECT ... FOR UPDATE`). A second submit of that same token, including one that is already in flight, returns 400 `Invalid or expired link`. One password is stored. A password shorter than 6 characters is still rejected before the token is read.
- `POST /api/auth/verify-email` and `POST /api/auth/accept-invite` lock the row the same way. A second submit of that verification link or invite token returns 400. Two in-flight submits leave one success.
- No migration and no backfill.

## Behavior

`forgot_password` still rate-limits by IP. An unknown address returns the generic sentence and does not start a send. A known address starts a daemon thread with its own `SessionLocal` and returns the same sentence without waiting. The request does not hold a database transaction across the provider call.

The background session inserts the `password_reset_tokens` row and flushes it. It does not delete older unused rows yet. It then calls `send_password_reset_email`.

- If the provider returns false, the reason is `provider_rejected`. If it raises, the reason is `provider_error`. The log line names the exception class and does not include the exception text, because that text can carry the message. The transaction rolls back, so the new row is never visible. A delete of that id follows, in case a commit had already landed it. Previously delivered unused rows stay. The audit row is `auth.reset_send_failed` with `{"reason": "<reason>"}` and no token.
- If the provider returns true, unused rows for that user with a lower id are deleted and the new row is committed together with `auth.reset_requested`. A concurrent issuance with a higher id is not deleted by this request. Deleting it as well can leave both callers holding a link that no longer exists.
- If the commit after an accepted send fails, the new row and the delete of older rows roll back. The previous link still works. The emailed link does not match a stored row. The audit reason is `store_failed`, and the HTTP body is still the generic sentence, without `reset_url`.
- An audit write that fails does not change the HTTP status. A 500 only for a real account would say that the account exists.

`reset_password` still rejects a missing token or a short password before it reads a row, so a bad password does not consume the link. It then reads the unused row to learn the user id, locks that user with `SELECT ... FOR UPDATE`, and locks the unused token row the same way (`populate_existing`, so a deleted row is not served from the identity map). The account lock is first so two different links cannot each lock a token and then deadlock while deleting every unused row.

Only the request that still sees the unused row after those locks changes `password_hash`, deletes every unused reset row for that user, deletes that user's sessions, and commits. The other request gets 400 `Invalid or expired link`. An expired link is rejected while the locks are held and is not deleted; closing the request rolls the locks back. Email-verification rows and MFA recovery codes are still not password-reset credentials. That rule is unchanged from TC-04-003.

`verify_email` locks the account row, then the verification-link row, before `_mark_email_verified` deletes every verification row for that user. `accept_invite` locks the invite row before it creates the membership and deletes the invite. A second in-flight submit waits on that lock and then finds no row.

`resend-verification` no longer deletes the delivered code before the send. `_issue_verification` queues the same background session used by register: insert the code and the link, send, and commit only on acceptance. Older verification rows are deleted only when their id is lower than the new ones. A false or raised send rolls the new rows back. The HTTP body stays the generic resend sentence for an unknown address and for a real unverified account.

SQLite's compiler drops `FOR UPDATE`. The overlap tests skip there with that reason. PostgreSQL, including CI, runs them with two connections. The reset pause is inside password hashing, which runs only after both locks are held. The verification-link and invite pauses are `_after_row_locked`, which runs only after the row lock is held, so the second submit is waiting on the lock rather than inside the hook.

## Policy

Anti-enumeration wins over a distinct mail-outage status, and it also wins over waiting for the provider on the request. A 503 only when a real account's send fails would tell the caller the address exists. Waiting for SMTP only when the address exists would tell the caller the same thing by latency. The request returns the generic sentence immediately. The recoverable outcome is on the server: the previous link still works, the unsent row is not left behind, and the failure is in the log and in `audit_events`. The caller can submit again. The forgot-password page is unchanged. It already shows "Check your email" for this 200.

Review follow-up on PR #280 (comment 6967410479) asked for this background send and for verification and invite coverage in this PR rather than a TC-04-002a split. Verification issuance and resend use the background rule. Invite redemption is locked.

Invite creation is unchanged. `POST /api/members/invites` still commits the invite, returns its id, and sends on the existing background thread. A false provider result leaves that row, which is what `test_create_invite_succeeds_when_email_send_returns_false` requires, and `test_failed_invite_send_leaves_the_code_usable` redeems that code afterwards. A second invite for the same address is still rejected while the row exists, so a failed send does not destroy a previous invite. The admin revokes and creates again to retry delivery. The create request returns before `send_invite_email` finishes. That route is authenticated, so it is not the anonymous account-existence timing oracle on forgot-password and resend-verification.

## Rollout and rollback

No migration and no backfill. Unused reset rows already exist. The next forgot-password or reset-password request uses the new rule. Rollback is reverting this change. After a rollback, a failed send again deletes unused rows before the background send, and two simultaneous submits of one token can both return 200.

## Limitations

- Invite creation still commits the invite before the provider returns. A failed send leaves that row. Retry is revoke, then create. See the policy section.
- Two overlapping forgot-password requests that both get an accepted send can leave two unused links, because each background task deletes only lower ids. Redeeming either link still deletes every unused reset row for that user.
- A process stop after the provider accepts and before the background commit rolls the new row back. The previous link remains, and the emailed link does not match a stored row. The HTTP response has already been sent.
- When `TRUST_COPILOT_DEV_RETURN_RESET_URL` is set, the response contains the candidate link before the provider answers. That link works only after the background task commits it.
- The concurrency tests are skipped when the bind is not PostgreSQL. SQLite cannot make `SELECT ... FOR UPDATE` meaningful. CI's database is PostgreSQL, so the tests run there.
