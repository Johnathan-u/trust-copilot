## Behaviour

Line numbers are the ones read at `39af3c2ff7058e0676c1ae6b0d11c4e0b6e3ccf2`.

**Enrollment.** `encrypt_totp_secret` seals the secret with purpose `mfa` before it is stored (`apps/api/app/core/mfa.py:16-19`). Setup writes `totp_secret_encrypted` with `enabled=False` and returns the plaintext secret and provisioning URI only from that response (`apps/api/app/api/routes/auth.py:2660-2675`). Status returns `enabled` and no secret (`auth.py:2634-2635`). Confirm decrypts, rejects a bad code with `auth.mfa_confirm_failed`, and sets `enabled=True` only after `verify_totp` (`auth.py:2738-2750`). The response is the recovery codes (`auth.py:2788`).

**Challenge.** Password login with an enabled factor returns `requires_mfa` and the MFA token and does not set a cookie (`auth.py:1098-1099`, `:202-219`). Google, GitHub, Microsoft, OIDC SSO, and ID.me all call `_provider_login_response` (`auth.py:1780-1782`, `:1898`, `:1978`, `:2067`, `:2148`). An enabled factor redirects to `/login?mfa_token=` and sets no session cookie (`auth.py:1578-1595`). `Workspace.mfa_required` with no enabled factor, on password and on every provider, issues role `mfa_enrol` only (`auth.py:1101-1106`, `:1141-1144`, `:1597-1628`). `mfa_enrol` is not a built-in role (`apps/api/app/core/roles.py:12`), so `can_edit`, `can_review`, `can_export`, and `can_admin` are false (`apps/api/app/core/auth_deps.py:340-349`). `get_session` drops an enrolment cookie off the allow-list (`auth_deps.py:52-57`). `enforce_mfa_enrol_session` denies every other route (`auth_deps.py:203-210`). `switch-workspace` grants the target role only when the session is `mfa_satisfied`; otherwise it issues the enrol cookie or the login challenge and no role cookie (`auth.py:2374-2423`).

The named tests passed, including the provider and `mfa_required` cases (`apps/api/tests/release/test_mfa_enroll.py:372-457`). That file withholds the privileged session until TOTP on password and each provider, completes the same challenge with a recovery code, keeps `mfa_required` with no enabled factor on the enrol-only cookie, replaces that cookie only after confirm, and issues no session for the undecryptable reset marker. The fixtures are synthetic.

**Operator note.** `docs/release/config-contract.md:53-58` records the same rule: an enabled factor withholds the session until `POST /api/auth/mfa/verify-login`, and `mfa_required` with no factor grants only the five-minute setup session, including on provider sign-in.

`user_mfa` is already on master (`apps/api/alembic/versions/012_user_mfa.py`). `tc05001c_mfa_satisfied` records whether the session completed a challenge. This note adds no migration.
