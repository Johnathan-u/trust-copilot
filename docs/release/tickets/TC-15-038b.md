## Bounded behavior

`/dashboard/jobs` reads the existing history endpoint with the current workspace and a fixed page size of 25. It shows only the five current job types: questionnaire parsing, evidence parsing, document indexing, answer generation and export. A descending ID cursor is saved in the URL alongside its workspace. Reload requests that same page from the server, Back restores the previous page, and switching workspace discards any other workspace's cursor. Invalid saved cursors offer a reset without sending a business request. There is no browser-persisted copy of the job records and no automatic polling; explicit reload checks current state.

The screen uses current `can_review` for reads and current `can_admin` for cancel/retry. Changing workspace or those capabilities unmounts the previous consumer, aborts its owned work, clears dialogs and notices, and ignores late responses. History 401/403/404, detail 401/403 and mutation 401 invalidate all private workspace state: rows, object links, detail, dialogs, confirmations and notices. The consumer aborts every owned pending read/mutation before clearing state, so a late successful response cannot restore old data. An individual detail 404 stays scoped to that job. Transient refresh failures retain the last confirmed results with an explicit partial-state message and disable mutations until a successful refresh. An action 403 does not prove loss of review access: it clears cached state, blocks further administrative actions for that consumer, then performs an authoritative history read. Only a successful new history response restores read-only rows and links. Denied, missing or failed revalidation keeps the private cache empty.

The consumer projects both history and legacy detail/action responses into a safe display model. It never retains raw payload, result text, provider error text, arbitrary error messages, storage keys, stored request IDs or arbitrary URLs. Known lifecycle and job-kind labels are static. Unknown values show an unavailable state and do not offer an action. Detail progress is limited to valid integer answer-generation counters; missing progress stays “not reported,” and zero totals never create a false percentage. Retry scheduling, retry exhaustion, attempts, lifecycle timestamps, known outcomes and charge uncertainty have explicit text. Timestamps without an offset follow the API's UTC convention.

Object links come only from the history API's current, checked object reference with a matching job/object type and valid ID. Questionnaire references use the existing questionnaire route. Document references use the existing document library, clearly labeled “Open document library”: the product has no individual document detail route. Legacy detail or action responses cannot grant a link. Missing, unavailable or malformed references render no link. An export job does not grant a download.

Cancel and retry require a confirmation dialog. Busy controls and a synchronous in-flight guard prevent repeat submission. The response must contain the expected job identity, a valid charge-uncertain flag and the action's acknowledged status (`cancelled` or `queued`) before any success message or lifecycle change. Failure or malformed 200 responses preserve the prior lifecycle and show a safe error. Retry confirmation repeats the charge-uncertain warning when applicable. A successful acknowledgment followed by a failed refresh remains an explicitly acknowledged partial result. This page has no editable draft requiring an unsaved-change prompt.

Loading, empty, denied, invalid-cursor, unknown, not-found-detail, failure, partial and success states are distinct. The existing shared dialogs, buttons, cards and state components remain unchanged. The read effects defer their first request so StrictMode's discarded setup does not send a duplicate business GET; owned aborts are handled locally.
