## Behavior

### Password signup

`POST /auth/register` creates an unverified user and mails one message with a 6-digit code (15 minutes) and a separate high-entropy link (24 hours). The link carries the user id. A second registration for the same address returns the same generic message, sends nothing further, and does not change the password, verification state, or memberships.

`POST /auth/verify-code` accepts only that 6-digit code for that email's user. The code is stored as an HMAC under the existing session purpose key (`purpose_macs` in `app/core/keys.py`), not as unsalted SHA-256. `POST /auth/verify-email` requires the link and the user id. A 6-digit code is rejected there. The link is not looked up by token hash alone. Each attempt is recorded before the decision. Five attempts are allowed; the sixth returns 429 for 15 minutes. The cap is checked on the address, the account, and the submitted code. In production a rate-limit store error fails closed (503), the same way workspace creation does. An expired or already used code or link is rejected.

`POST /auth/login` for an unverified account returns 403 `email_not_verified` and does not set a session cookie. `POST /auth/resend-verification` sends a fresh code and link for an unverified account, at most three times per 15 minutes per address and per IP, and answers with the same message when the address is unknown or already verified.

After verification, login with no membership returns `needs_onboarding` with `workspace_id` 0 and `role` pending. Marking the email verified deletes that user's sessions, so a session from before verification does not continue. `POST /auth/reset-password` also deletes that user's sessions. Under `self_signup`, `POST /workspaces` creates a new workspace administered by that user. The user has no membership in workspace 1 and cannot read its documents. Under the default `invitation_only` policy, the same verified user cannot create a workspace.

### Invites

An existing user whose email is not yet verified must choose a new password to accept an invite. The user row is locked, then the password hash is replaced and sessions, unused password-reset tokens, verification tokens, MFA, recovery codes, MFA login challenges, and provider links are deleted. The email is then marked verified and only the invited membership is added. The previous password no longer works. A user whose email is already verified keeps their password, sessions, and MFA. A brand-new invitee still sets a password while the account is created. The accept-invite page says an unverified existing account must set a new password.

### Provider sign-in

Google, GitHub, Microsoft, OIDC, and ID.me share one rule:

- An unverified provider email is rejected. No account is created, and an existing account is not linked.
- Microsoft does not treat Graph `mail`, a user principal name, or `preferred_username` as a verified address. An email is accepted only from the `email` claim when the id_token signature, audience, issuer, and expiry check out and `xms_edov` is true. The Microsoft identity key is always `tid` + `oid`. A link still stored under the old Graph object id is rewritten to `tid` + `oid` and stays on the same account. In the Entra app registration, Token configuration must add the optional claim `xms_edov` to the ID token. Personal Microsoft accounts may not send it. Without it, an unlinked Microsoft sign-in returns 400.
- A verified provider email is not linked to an unverified local account, so a password chosen before verification cannot ride along.
- A new verified provider identity is stored with `email_verified` set, no workspace membership, and the same pending onboarding session password login uses (`workspace_id` 0, `role` pending). The browser is sent to `/onboarding`.
- A verified member who links a provider stays in their existing workspace. They are not given workspace 1.
- `OIDC_DEFAULT_WORKSPACE_ID` is not applied to membership. Unset, empty, and the word `default` select no workspace. An explicit integer is still stored and still does not grant a membership.

Workspace creation then follows the existing signup policy, cap, and throttle. Those controls are unchanged.

## Rollout and rollback

No migration and no backfill. Existing unverified rows stay unverified. An unverified person who tries to sign in sees:

> Verify your email before signing in.

The response code is `email_not_verified` (HTTP 403) and no session cookie is set. Recovery is in the web app. The sign-in page shows "Send a new verification email", which posts the typed address to `POST /auth/resend-verification` and shows: "If that email is waiting for verification, a new message is on the way." A 429 says "Too many verification emails. Try again later." The same action is on the register success page. `/verify-email` accepts the 6-digit code from the message through `POST /auth/verify-code`. That resend route is limited to three requests per 15 minutes per address and per IP. Operator seed scripts mark the accounts they create. `scripts/seed_demo_workspace.py` marks the demo and admin users. `scripts/seed_qa_test_data.py` marks the demo, admin, editor, reviewer, and suspended users. Re-running either script marks that same operator row verified if it already exists. No other account is verified, and there is no migration that sets `email_verified` on existing rows.

Rollback is reverting this change. A 6-digit code stored as unsalted SHA-256 before the HMAC change no longer matches `POST /auth/verify-code`. Resend issues a new code for an account that is still unverified.

## Limitations

- Registering an address that already exists does not send a replacement code. An unverified account can request one with `POST /auth/resend-verification`.
- The verification lockout uses the existing rate-limit store (Redis when `REDIS_URL` is set, otherwise this process). In production a store error on that check returns 503.
- An unverified owner or admin can no longer sign in with a password. Workspace creation still allows an active owner or admin who already has a session, without a separate email check. That path is covered by a signed session in the workspace-creation tests.
- The verify-email page sends the user id from the mailed link and also accepts the 6-digit code. The accept-invite page tells an unverified account to set a new password.
- OAuth state comparison, the ID.me verified-claim meaning, duplicate-registration timing, and retiring `OIDC_DEFAULT_WORKSPACE_ID` are outside this change.
