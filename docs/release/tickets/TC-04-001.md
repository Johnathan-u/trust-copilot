## Behavior

### Password signup

`POST /auth/register` creates an unverified user and mails one message with a 6-digit code (15 minutes) and a separate high-entropy link (24 hours). The link carries the user id. A second registration for the same address returns the same generic message, sends nothing further, and does not change the password, verification state, or memberships.

`POST /auth/verify-code` accepts only that 6-digit code for that email's user. `POST /auth/verify-email` requires the link and the user id. A 6-digit code is rejected there. The link is not looked up by token hash alone. Five failed attempts on the address, the account, or the submitted secret lock that check for 15 minutes and return 429. An expired or already used code or link is rejected.

After verification, login with no membership returns `needs_onboarding` with `workspace_id` 0 and `role` pending. Under `self_signup`, `POST /workspaces` creates a new workspace administered by that user. The user has no membership in workspace 1 and cannot read its documents. Under the default `invitation_only` policy, the same verified user cannot create a workspace.

### Invites

An existing user whose email is not yet verified must choose a new password to accept an invite. That replaces the password hash, deletes sessions, unused password-reset tokens, and outstanding verification tokens, then marks the email verified and adds only the invited membership. The previous password and any session issued before acceptance no longer work. A user whose email is already verified keeps their password and sessions. A brand-new invitee still sets a password while the account is created.

### Provider sign-in

Google, GitHub, Microsoft, OIDC, and ID.me share one rule:

- An unverified provider email is rejected. No account is created, and an existing account is not linked.
- A verified provider email is not linked to an unverified local account, so a password chosen before verification cannot ride along.
- A new verified provider identity is stored with `email_verified` set, no workspace membership, and the same pending onboarding session password login uses (`workspace_id` 0, `role` pending). The browser is sent to `/onboarding`.
- A verified member who links a provider stays in their existing workspace. They are not given workspace 1.
- `OIDC_DEFAULT_WORKSPACE_ID` is not applied to membership. Unset, empty, and the word `default` select no workspace. An explicit integer is still stored and still does not grant a membership.

Workspace creation then follows the existing signup policy, cap, and throttle. Those controls are unchanged.

## Migration and rollback

No schema change and no backfill. Rollback is reverting this change. A 6-digit code already stored before the change can still be used on `POST /auth/verify-code` until it expires. It is no longer accepted by `POST /auth/verify-email`.

## Limitations

- Registering an address that already exists does not send a replacement code. The link remains valid for 24 hours after the code's 15 minutes. After both expire, this change does not add a resend.
- The verification lockout uses the existing rate-limit store (Redis when `REDIS_URL` is set, otherwise this process).
- `invitation_only` still lets an active owner or admin create another workspace without a verified email. That path was already covered and is unchanged.
- The verify-email page now sends the user id from the mailed link. This run did not boot the web app, so that page was not clicked in a browser. The API test posts the same query.
