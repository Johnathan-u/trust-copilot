`/dashboard/questionnaires` reads `GET /api/questionnaires` and does not change backend authorization. Search waits 300 ms, then sends `search`. With none of those four parameters, `GET /api/questionnaires` still returns the unpaged JSON array, newest `created_at` first, then `id` descending. With any of them, the body is one page: `items`, `page`, `page_size`, `total`, `sort`, and `order`. `page` is 1-based and defaults to 1. `page_size` defaults to 25 and must be 1–100. `sort` is `created_at`, `filename`, `status`, or `id`. `order` is `desc` or `asc`. An unknown sort or order, a `page` outside 1..1000000, or a `page_size` outside 1..100 is HTTP 400. The page does not reorder rows in the browser. It offers sort controls and a page navigation labelled Previous page and Next page. Those controls stay on the page. Previous page is disabled on page 1, and Next page is disabled on the last page.

Changing the workspace, a filter, the sort, or the page clears the selection. Every row reports `question_count`, `review_reviewed`, `review_total`, `job_id`, `job_status`, `job_progress`, `mapping_ambiguous`, `mapping_confirmation_url`, and `needs_review`. `question_count` and `review_total` are the number of stored questions. `review_reviewed` is how many of those questions have an answer whose status is `approved`. `job_id` and `job_status` are the newest `parse_questionnaire` job in the same workspace whose payload names that questionnaire. `needs_review` is true when the questionnaire status is `needs_review`, and the page labels that status "Needs review".

`mapping_ambiguous` is true when this workspace has a `suggested` mapping for the questionnaire. The confirmation URL is `/dashboard/questionnaires/{id}/confirm-mapping`. Otherwise the flag is false and the URL is null. The page links "Confirm mapping" when the flag is true and the path is same-origin. `false` does not link. A true flag without a same-origin path leaves the control disabled. The confirmation page is `apps/web/app/dashboard/questionnaires/[id]/confirm-mapping/page.tsx`. `GET /api/questionnaires/{id}/mapping-confirmation` requires a reviewer in the same workspace. `POST` the same path requires an editor, approves every named suggested mapping, and changes nothing when any id is missing, duplicated, or not suggested.

The questionnaire list does not return `max_upload_bytes`. The size line still shows the documented 50 MB default. `GET /api/jobs/{id}` still has no `progress` key. The page uses a row job id when the newest jobs page does not include that job.

## Behavior

`/dashboard/questionnaires` is a workspace questionnaire list. It reads `GET /api/questionnaires` and does not change backend authorization.

Search waits 300ms, then sends the existing `search` parameter. A newer search aborts the previous request with `AbortController`, and a late response is ignored. The page sends `page`, `page_size=25`, `sort`, and `order`, as the current contract describes. The page does not slice or reorder the payload on the client.

Selection applies to every questionnaire in the current page for the current workspace. Changing the workspace, a committed filter, the sort, or the page clears it. Previous page and Next page stay on the page. Previous page is disabled on page 1, and Next page is disabled on the last page.

A successful empty library, a successful search or filter with no rows, and a failed read are three states. The empty library says "No questionnaires yet" and, for an editor, offers "Upload your first questionnaire". A narrowed empty result says "No matching questionnaires" and does not offer that first-upload action. A failed read uses `ErrorState` and does not look like an empty library.

Editors see the upload allow-list before choosing a file: PDF, DOCX, DOC, XLSX, XLS, and TXT, matching `FileService.ALLOWED_RAW_EXTENSIONS`. The size line says 50 MB, the documented default of `MAX_UPLOAD_BYTES`. The questionnaire API does not return the configured limit. The workbook contract on the page is the merged cell-mapping rule: an XLSX or XLS answer cell comes from a header named Answer, Response, Reply, Vendor response, Vendor answer, or Answer text. The parser does not use the next column. A sheet with no answer header stores no answer cell. DOCX and PDF imports do not store a workbook answer cell. A new CSV upload is rejected. CSV parsing applies only to a file that is already stored with a `.csv` name.

The upload button stays on "Uploading" until the upload response. "Uploaded" / "The file is stored." appears only after that response succeeds. The follow-up list read uses the same search, framework, subject, status, created-from, created-to, and archive parameters that were active when the upload was sent. If the response includes `job_id`, the page polls `GET /api/jobs/{id}` and shows Queued while the job is queued or running. Parsed appears only after the job is completed and a following questionnaire read has `status` `parsed`. Failed appears when the job is failed or cancelled, or that read says `failed`. Parsing progress stays "Not reported" unless the job object includes integer `progress.generated` and `progress.total`.

Retry is `POST /api/jobs/{id}/retry`. That route requires an administrator. The page uses the row's `job_id` when the newest `GET /api/jobs` page does not include that job. Otherwise it reads that page (`limit=25`, which is what the job-history reader accepts) and offers "Retry parsing" only when that page has a failed or cancelled `parse_questionnaire` for the row. "Parsing queued" appears only after the retry response has `status` `queued`. There is no questionnaire reparse route, and the page says so. A matched parse job links to `/dashboard/jobs?workspace_id=…`.

Questions show `question_count` when the row carries that integer, and otherwise `parse_metadata.count` when that value is a non-negative integer. Otherwise the line says "Not reported". The stored question texts inside `parse_metadata` are not rendered. Review progress says "Review: N of M" only when the row carries both integers and N is not greater than M. Otherwise it says "Not reported". Job progress on a row says "N of M" from the row's `job_progress` or from the newest jobs page. A `needs_review` status is labelled "Needs review".

`mapping_ambiguous` false does not link. `true` links to "Confirm mapping" at `/dashboard/questionnaires/{id}/confirm-mapping` when `mapping_confirmation_url` is a same-origin path. Without that path the control is disabled and the row says mapping confirmation is not available. The confirmation page lets an editor confirm the suggested mappings and lets a reviewer read them.

Metadata and restore dialogs stay open until the response is acknowledged. The row updates, and "Metadata saved." or "Restored." appears, only when the body has `ok: true`. A failed response stays in the dialog as an alert and does not change the row.

Archive and delete are different. Archive calls the existing soft-delete `DELETE /api/questionnaires/{id}` (and bulk archive calls `POST /api/questionnaires/bulk-delete`). The dialog says the questionnaire can be restored, and "Archived." appears only after `ok: true` (or, for the bulk call, a numeric `deleted`). Delete opens a separate dialog titled "Delete record?" that explains permanent deletion is not available. Its confirm control stays disabled and does not call the API.

Mutation controls use `permissions.can_edit` and `permissions.can_admin` from the session. A reviewer (`can_edit` false) does not get the upload control, the file input, row checkboxes, or the row menu. Parse retry additionally requires `can_admin`, matching the job retry route. Reviewers can still open the questionnaire and the review page. This is display only. The server checks are unchanged.

Search, framework, subject area, created from, created to, questionnaire status, and the archive filter have labels. Selected values appear as removable chips.

At 360, 768, and 1440 CSS pixels the filters are reachable from the keyboard, long filenames wrap, and the empty and error states stay on screen without horizontal scrolling. axe-core reports no violations for the ready, empty, and error states at those widths.

## API gaps (not faked on the client)

- `GET /api/questionnaires` pages when `page`, `page_size`, `sort`, or `order` is sent, and each row carries question counts, review counts, the newest parse job, job progress, `needs_review`, and the mapping-confirmation path. Callers that omit those four parameters still receive the unpaged array.
- `GET /api/jobs/{id}` does not include `progress`. The list row's `job_progress` uses the same integer rules as job history.
- Mapping confirmation is `GET` and `POST /api/questionnaires/{id}/mapping-confirmation` and the page `/dashboard/questionnaires/{id}/confirm-mapping`. A confirmation link is rendered only from a same-origin `mapping_confirmation_url` on a row whose `mapping_ambiguous` is true.
- `MAX_UPLOAD_BYTES` is not returned by the questionnaire list. The page shows the documented 50 MB default.
- A new `.csv` upload is rejected by the shared allow-list even though a stored `.csv` can be parsed. `.txt` is accepted by upload and is not a workbook round trip.
- Permanent deletion of one questionnaire is not available. Archive is the existing soft-delete.
- Job retry requires an administrator. The page uses the row job id when the newest jobs page does not include that job.
- `confirm_mapping` writes no audit event. That is open child TC-15-017c. Claude's #290 ruling says it does not block this parent.
