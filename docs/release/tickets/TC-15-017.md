# TC-15-017 — Finish and polish /dashboard/questionnaires

## Behavior

`/dashboard/questionnaires` is a workspace questionnaire list. It reads `GET /api/questionnaires` and does not change backend authorization.

Search waits 300ms, then sends the existing `search` parameter. A newer search aborts the previous request with `AbortController`, and a late response is ignored. The list states its contract: every match comes back in one response, newest first. `GET /api/questionnaires` does not accept `page`, `page_size`, `limit`, `offset`, `sort`, or `order`. The page does not slice or reorder the payload on the client. The server order remains `created_at` descending, then `id` descending.

Selection applies to every questionnaire in the current result for the current workspace. Changing the workspace or a committed filter, including the debounced search, clears it. There is no page control, and the page says so.

A successful empty library, a successful search or filter with no rows, and a failed read are three states. The empty library says "No questionnaires yet" and, for an editor, offers "Upload your first questionnaire". A narrowed empty result says "No matching questionnaires" and does not offer that first-upload action. A failed read uses `ErrorState` and does not look like an empty library.

Editors see the upload allow-list before choosing a file: PDF, DOCX, DOC, XLSX, XLS, and TXT, matching `FileService.ALLOWED_RAW_EXTENSIONS`. The size line says 50 MB, the documented default of `MAX_UPLOAD_BYTES`. The questionnaire API does not return the configured limit. The workbook contract on the page is the merged cell-mapping rule: an XLSX or XLS answer cell comes from a header named Answer, Response, Reply, Vendor response, Vendor answer, or Answer text. The parser does not use the next column. A sheet with no answer header stores no answer cell. DOCX and PDF imports do not store a workbook answer cell. A new CSV upload is rejected. CSV parsing applies only to a file that is already stored with a `.csv` name.

The upload button stays on "Uploading" until the upload response. "Uploaded" / "The file is stored." appears only after that response succeeds. The follow-up list read uses the same search, framework, subject, status, created-from, created-to, and archive parameters that were active when the upload was sent. If the response includes `job_id`, the page polls `GET /api/jobs/{id}` and shows Queued while the job is queued or running. Parsed appears only after the job is completed and a following questionnaire read has `status` `parsed`. Failed appears when the job is failed or cancelled, or that read says `failed`. Parsing progress stays "Not reported" unless the job object includes integer `progress.generated` and `progress.total`.

Retry is `POST /api/jobs/{id}/retry`. That route requires an administrator. The questionnaire list does not include a job id, so the page reads the newest `GET /api/jobs` page (`limit=25`, which is what the job-history reader accepts) and offers "Retry parsing" only when that page has a failed or cancelled `parse_questionnaire` for the row. "Parsing queued" appears only after the retry response has `status` `queued`. There is no questionnaire reparse route, and the page says so. A matched parse job links to `/dashboard/jobs?workspace_id=…`.

Questions show `parse_metadata.count` when that value is a non-negative integer, or `question_count` when the row carries that integer. Otherwise the line says "Not reported". The stored question texts inside `parse_metadata` are not rendered. Review progress says "Review: N of M" only when the row carries both integers and N is not greater than M. Otherwise it says "Not reported". Job progress on a row says "N of M" only when the newest jobs page includes `progress` for that questionnaire. Today that field is filled for `generate_answers` only.

Mapping says "Not reported" unless the row has a boolean `mapping_ambiguous`. `false` says "Not ambiguous" and does not link anywhere. `true` links to "Confirm mapping" only when `mapping_confirmation_url` is a same-origin path. Without that path the control is disabled and the row says mapping confirmation is not available. This app has no mapping-confirmation page for a questionnaire.

Metadata and restore dialogs stay open until the response is acknowledged. The row updates, and "Metadata saved." or "Restored." appears, only when the body has `ok: true`. A failed response stays in the dialog as an alert and does not change the row.

Archive and delete are different. Archive calls the existing soft-delete `DELETE /api/questionnaires/{id}` (and bulk archive calls `POST /api/questionnaires/bulk-delete`). The dialog says the questionnaire can be restored, and "Archived." appears only after `ok: true` (or, for the bulk call, a numeric `deleted`). Delete opens a separate dialog titled "Delete record?" that explains permanent deletion is not available. Its confirm control stays disabled and does not call the API.

Mutation controls use `permissions.can_edit` and `permissions.can_admin` from the session. A reviewer (`can_edit` false) does not get the upload control, the file input, row checkboxes, or the row menu. Parse retry additionally requires `can_admin`, matching the job retry route. Reviewers can still open the questionnaire and the review page. This is display only. The server checks are unchanged.

Search, framework, subject area, created from, created to, questionnaire status, and the archive filter have labels. Selected values appear as removable chips.

At 360, 768, and 1440 CSS pixels the filters are reachable from the keyboard, long filenames wrap, and the empty and error states stay on screen without horizontal scrolling. axe-core reports no violations for the ready, empty, and error states at those widths.

## API gaps (not faked on the client)

- `GET /api/questionnaires` has no page or sort parameters, and the list payload has no question total, review counts, job id, or ambiguity flag.
- `GET /api/jobs/{id}` does not include `progress`. History `progress` is present only for `generate_answers`.
- There is no mapping-confirmation route. A confirmation link is rendered only from a same-origin `mapping_confirmation_url` on a row whose `mapping_ambiguous` is true.
- `MAX_UPLOAD_BYTES` is not returned. The page shows the documented 50 MB default.
- A new `.csv` upload is rejected by the shared allow-list even though a stored `.csv` can be parsed. `.txt` is accepted by upload and is not a workbook round trip.
- Permanent deletion of one questionnaire is not available. Archive is the existing soft-delete.
- Job retry requires an administrator and is offered only when the failed or cancelled `parse_questionnaire` job is on the newest jobs page.
- TC-09-001 is not merged, so numbered and uppercase question detection is not reported here.
