## AC1: required variables and owner prerequisites are typed, documented and validated at startup

- `apps/api/app/core/config_contract.py` is the single source of truth. Every environment variable the API, worker, migrations and seed scripts read (plus compose-only variables) has a `ConfigVar` entry. Each entry gives the name, type, production rule (`required`, `forbidden`, `optional` or `conditional`), whether it is a secret, the non-production default, a description and any owner prerequisite.
- `docs/release/config-contract.md` holds the generated reference table (`python -m app.core.config_contract markdown`) and an owner-prerequisites table. A test fails if the table drifts from the code.
- **Startup validation:** `enforce_startup_contract(role)` runs first in each of these places:
  - the API lifespan in `app/main.py`, before settings are loaded and before the DB connectivity check;
  - the worker in `app/worker.py` `main()`, before polling;
  - Alembic in `alembic/env.py`, skipped only when `TRUST_COPILOT_TESTING=1`;
  - the container entrypoint in `docker-entrypoint.sh`, via `python -m app.core.config_contract check entrypoint` before migrations.
- **Behaviour outside production:** problems are logged as warnings. Two kinds are always fatal: a malformed integer that would crash later (`MAX_UPLOAD_BYTES`, `EXPORT_ANSWER_COL_OFFSET`, `OIDC_DEFAULT_WORKSPACE_ID`), and an unknown `APP_ENV`.
- **No values in output:** errors and CLI output name variables only and never print values. The tests check this.
- `.env.example` now has a header explaining the contract and an explicit `APP_ENV=development` line.

## AC2: production refuses default credentials and demo auto-seeding

When `APP_ENV=production` (case- and whitespace-insensitive), startup fails closed if any of the following holds.

**Credentials (the Integrations list is fully covered):**
- `SESSION_SECRET` is unset, empty or weak (TC-07-001 `is_weak_secret`).
- `DATABASE_URL` is unset, empty, not postgres, has no user or password, or uses a known vendor or tutorial default, a placeholder, a short or low-variety password, or a password equal to the user name.
- `S3_ACCESS_KEY` or `S3_SECRET_KEY` is unset, empty, a known default (including MinIO's `minioadmin` family) or a placeholder. The secret key must also be at least 16 characters. `S3_ENDPOINT` is required.
- `POSTGRES_PASSWORD` or `MINIO_ROOT_PASSWORD` is set to a default or weak value. These are checked whenever present. `MINIO_ROOT_USER` must not be a default.
- Any dev-compose default (`${VAR:-dev…}` fallbacks) or `.env.example` value is supplied. The tests read these values from the repo files at test time, so they are never copied into the test source.
- The credential store has no hard-coded fallback key in production. That was handled in TC-07-001 and is now also enforced through the `SESSION_SECRET` check.

**Public surface:**
- `APP_BASE_URL` and `FRONTEND_URL` must be https and must not be localhost or loopback.
- `TRUSTED_ORIGINS` and `CORS_ORIGINS` must be https only.

**Providers and owner prerequisites:**
- `OPENAI_API_KEY` is required.
- `SMTP_HOST` and `SMTP_FROM` are required **only when email delivery is enabled** (see the Coordinator rulings below).
- OAuth, OIDC and ID.me client id/secret pairs must be complete, and OIDC needs an issuer.
- Stripe needs its webhook secret when it is enabled.

**Forbidden switches:**
- `TRUST_COPILOT_DEV_RETURN_RESET_URL`, `TRUST_COPILOT_TESTING`, `TRUST_COPILOT_DEBUG_NDJSON` and `TRUST_COPILOT_E2E_RUNNER`.
- `TC_ALLOW_PRODUCTION_SEED`, `TC_SEED_*` passwords, `TC_SEED_RESET_PASSWORDS` and `TC_SESSION_SECRET`.
- `NEXT_PUBLIC_DEMO_LOGIN_EMAIL` and `NEXT_PUBLIC_DEMO_LOGIN_PASSWORD`.

**Demo seeding:** every `scripts/seed_*.py` calls `refuse_demo_seed_in_production()`, either directly or through `_seed_credentials.refuse_production_seed`. This exits non-zero in production. The old `TC_ALLOW_PRODUCTION_SEED` override was **removed**, and setting it is now itself a production error. `main.py` does not seed accounts at startup, and a test enforces this.

**Deployment hardening:**
- The `docker-compose.prod.yml` worker now sets `APP_ENV: production` like the API, so the worker is validated as well.
- The `apps/web/Dockerfile` builder blanks the `NEXT_PUBLIC_DEMO_LOGIN_*` build args, so the demo login cannot be baked into a production bundle.
- `.dockerignore` excludes `.env*` (except `.env.example`), seed credential files, cookie jars, HAR files and traces.

## Behaviour changes that may affect existing deployments (owner action)

1. Production now **requires** `OPENAI_API_KEY`, `S3_ENDPOINT`, https public URLs and https origins. It also requires `SMTP_HOST` and `SMTP_FROM`, but only when email delivery is enabled. A deployment that relied on the old defaults will refuse to start until these are set.
5. In production with email delivery disabled, all email is suppressed: verification codes, invites, password resets and notifications are not sent and are **not** printed to logs. As a result, email-based sign-up verification and self-service password reset do not work in that mode. Owners who need them must enable email. Also, in production, an SMTP send failure no longer prints the message body (which may contain reset links) to stdout.
2. An unknown `APP_ENV` (for example `prod`) is now fatal in every environment. Use `development`, `test`, `staging` or `production`.
3. `APP_ENV` is now stripped and lower-cased consistently in `config.py`, `session.py` and `rate_limit.py`, so `" Production "` really means production everywhere.
4. Production demo seeding can no longer be overridden.

### Email enablement signal (logged choice)

**Existing signal:** the code had no explicit email or notification provider setting. The only signal was implicit: `email_service.get_email_provider()` used SMTP when `SMTP_HOST` was set and otherwise fell back to a console stub that prints messages, including reset links, to stdout.

**New flag:** I added an explicit, conservative flag, `EMAIL_DELIVERY_ENABLED` (bool), documented in the config contract. Its single source of truth is `config_contract.email_delivery_enabled()`, which both the startup validation and `email_service` use.

| `EMAIL_DELIVERY_ENABLED` value | Email delivery |
|---|---|
| `true`, `1`, `yes`, `on` | Enabled |
| `false`, `0`, `no`, `off` | Disabled |
| Unset or empty | Enabled only if `SMTP_HOST` is set. This keeps the pre-existing behaviour, so existing SMTP deployments are unaffected |
| Any other value | Treated as **enabled** (fails closed) and also reported as a type error, which is fatal in production |

**Production behaviour:**
- With email enabled, startup fails if `SMTP_HOST` or `SMTP_FROM` is missing or empty.
- With email disabled, startup succeeds. The email provider is then `DisabledEmailProvider`, which drops every message and logs only a fixed "suppressed" line, never the recipient or body.
- Production never uses the console stub, even if startup validation were bypassed.

**Tests:**
- Production boots with email disabled and no SMTP, both with the flag unset and with every false spelling.
- Production with email enabled and `SMTP_HOST`, `SMTP_FROM` or both missing or empty fails.
- Email enabled with valid SMTP passes.
- An invalid flag fails closed.
- The provider selection is checked.
- In production, no message body is printed when email is disabled or when an SMTP send fails.

## Ambiguities resolved conservatively

- **Exposed project secrets:** the denylist (`KNOWN_DEFAULT_CREDENTIALS`) holds only public vendor and tutorial defaults. The project's own exposed values (see the TC-07-001 exposure list) are **not** listed, because that would commit them again. Rotation (owner action) plus the strength rules is the remedy.
- **Strength thresholds:** passwords must be at least 16 characters with at least 6 distinct characters. The session secret uses the TC-07-001 rule (at least 32 characters).
- `POSTGRES_USER=postgres` is allowed, and only emptiness is checked. Only the MinIO root user is checked against vendor defaults.
- Alembic revision 003 creates the structural default workspace (id 1), which is not a demo account. It is unchanged, and no migration was added because no persisted state changes.
- Outside Docker, `app/main.py` loads `apps/api/.env` with `override=True` unless `TRUST_COPILOT_E2E_RUNNER=1`. This pre-existing precedence is unchanged. The contract validates the effective environment after that load.
- `infra/caddy/Caddyfile.production`, `apps/api/Dockerfile` and `.github/workflows/deploy.yml` were reviewed and needed no change. The deploy target is still TBD, so there is no deploy-time hook to add. The entrypoint check covers containers.
