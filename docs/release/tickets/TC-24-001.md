## Ordering rule

Subscription state for one Stripe subscription id moves forward only.

- Compare `event.created` (unix seconds) with the watermark on the `subscriptions` row (`stripe_event_created`), not with the signature timestamp. The signature tolerance applies only to the `t` value in `Stripe-Signature`.
- Apply the event when `created` is strictly newer than the watermark.
- When `created` is equal, the higher-ranked type wins. Low to high: `checkout.session.completed`, `invoice.payment_failed`, `customer.subscription.updated`, `customer.subscription.deleted`.
- `customer.subscription.deleted` is terminal for that subscription id. After it has been applied, a later update, payment failure, or checkout event does not change status, plan, or period. An example is `customer.subscription.updated` arriving after `customer.subscription.deleted`.
- An older event does not regress a newer one. An example is an update with an earlier `created` arriving after a newer update, or a delete whose `created` is older than an update already applied.
- The watermark stays on the subscription row. Pruning the replay store does not make an old event applicable again.
- A replay of the same Stripe event id is not an ordering decision. The unique row short-circuits the handler.

The same rule is the module docstring of `apps/api/app/services/billing_provider.py`.

## Replay store

Table `stripe_webhook_events` (Alembic revision **tc24001_stripe_webhook_events**, parent **tc11001_model_outcome_codes**). `stripe_event_id` has unique constraint `uq_stripe_webhook_events_event_id`.

Rows are deleted on `processed_at` once they are older than `max(STRIPE_EVENT_RETENTION_SECONDS, STRIPE_WEBHOOK_TOLERANCE_SECONDS + 1)`. The default retention is 604800 seconds (7 days), which is past the 300 second tolerance and past Stripe's roughly 3 day retry window. A mis-set retention smaller than the tolerance cannot delete rows that are still inside the signature window.

Pruning runs at the start of a verified webhook. It does not delete subscription watermarks.

## Configuration

All of these are environment variables. Unset means unset. `.env.example` lists them as comments with the value `placeholder` only.

| Variable | Role |
|---|---|
| `STRIPE_SECRET_KEY` | Buyer secret key. `sk_test_` / `rk_test_` are test. `sk_live_` / `rk_live_` are live. No other prefix is accepted. |
| `STRIPE_WEBHOOK_SECRET` | Webhook signing secret. |
| `STRIPE_WEBHOOK_SECRETS` | Extra secrets, comma-separated, accepted during rotation. A match on any secret is enough. |
| `STRIPE_WEBHOOK_TOLERANCE_SECONDS` | Default 300. Past and future. |
| `STRIPE_MODE` | `test` or `live`. When unset, the key prefix is used. |
| `STRIPE_PLAN_PRICE_IDS` | `plan_key:price_id` pairs, comma-separated. Ids only. |
| `STRIPE_PRICE_ID` | Legacy monthly price id, used only when that plan key is not already in the map. |
| `STRIPE_ANNUAL_PRICE_ID` | Legacy annual price id, same rule. |
| `STRIPE_MONTHLY_PLAN` | Plan key for monthly checkout. Default key name `pro` (not a price). |
| `STRIPE_ANNUAL_PLAN` | Plan key for annual checkout. Default key name `pro_annual`. |
| `STRIPE_EVENT_RETENTION_SECONDS` | Default 604800. |

Production (`APP_ENV=production`) startup calls `raise_for_stripe_preflight`. A missing webhook secret, an unresolved mode, or a test/live mismatch raises `RuntimeError` and the process does not serve. Outside production a live key also fails startup. A missing webhook secret outside production does not fail startup; the webhook route still returns 503 and does not apply the event.

Checkout reads the price id from the plan map and stores the plan key and price id in Checkout metadata. It does not send an amount. Renewal, downgrade, cancel, and Customer Portal behavior beyond the existing portal session call are left to TC-24-002.

`FREE_TRIAL_END` (2026-04-05) is unchanged except for a comment that TC-24-002 owns it. The date check is the same.

Public pricing pages still show the legacy $25 / $250 copy. That copy is OD-8 and was not edited here. The ROI default of 399 was not edited here.

## Buyer runbook

The buyer uses their own Stripe account. No seller personal Stripe account is required, shared, or referenced.

1. Create a Stripe account at `https://dashboard.stripe.com/register` and stay in **Test mode**. Do not use a key from anyone else's account.
2. Developers → API keys. Copy the test secret key (`sk_test_...`) into `STRIPE_SECRET_KEY`. Leave `STRIPE_MODE=test`.
3. Product catalog → add the product the buyer wants to sell. Add a recurring monthly price and a recurring annual price. Copy each **Price id** (`price_...`). Do not copy the amount into this application.
4. Set `STRIPE_PLAN_PRICE_IDS=pro:<monthly price id>,pro_annual:<annual price id>`. Change the plan keys only if `STRIPE_MONTHLY_PLAN` and `STRIPE_ANNUAL_PLAN` are set to the same keys.
5. Developers → Webhooks → Add endpoint. URL: `https://<buyer-host>/api/billing/webhook`. Events: `checkout.session.completed`, `customer.subscription.updated`, `customer.subscription.deleted`, `invoice.payment_failed`. Copy the signing secret into `STRIPE_WEBHOOK_SECRET`.
6. Deploy. `GET /api/billing/subscription` stays the read API. Checkout is `POST /api/billing/create-checkout-session`. The webhook has no session cookie; trust is the signature.
7. **Rotation.** Roll the signing secret in Stripe. Put the new secret in `STRIPE_WEBHOOK_SECRETS` (or comma-separate it with the old one in `STRIPE_WEBHOOK_SECRET`) and deploy before removing the old secret. Keep the old secret until in-flight retries finish. Stripe retries for about 3 days; the default replay retention is 7 days. After that, remove the old secret and deploy again.
8. **Live cutover.** In the live Stripe dashboard, create live prices, a live webhook endpoint, and a live secret key. Set `APP_ENV=production`, `STRIPE_MODE=live`, `STRIPE_SECRET_KEY=sk_live_...`, and the live webhook secret together. The process will not boot if the live key is paired with test mode, if a test key is paired with live mode, or if the webhook secret is missing. An event whose `livemode` flag does not match `STRIPE_MODE` is rejected and is not stored, so a config fix can still accept Stripe's retry.

## Assumptions

TC-06-001, TC-10-003, and TC-11-002 are not on this branch and are not implemented here.

- **TC-06-001.** Checkout and portal require `can_admin`. Subscription reads use `require_session()`. `principal_for_billing_session` adapts that session dict and does not build the versioned RequestPrincipal. Webhooks trust the verified Stripe event via `principal_for_stripe_event`. Missing checkout metadata does not fall back to workspace 0; the event is rejected and logged.
- **TC-10-003.** Webhook dedupe is the `stripe_webhook_events` unique constraint plus one transaction around claim and apply. `billing_idempotency_key` only names that key. The job idempotency table and parse/index/generate/export side effects are untouched. A crash after the commit is a stored event; a crash before the commit is retried by Stripe. The credit-ledger ensure after checkout remains best-effort and is not an outbox.
- **TC-11-002.** `spend_bounds_enforced_for_billing` is false. Webhooks do not call a model. No token ceiling or per-workspace spend check was added. OD-6 is still pending.
