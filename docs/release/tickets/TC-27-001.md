# TC-27-001 — Make failed backup stages fail loudly and atomically

Status: implemented, reviewer sign-off still open. No migration. No change to
auth, admin controls, CI gates, or `docs/planning/backlog-state.json`.

Evidence: `artifacts/acceptance/TC-27-001/`.

## What was wrong

`scripts/backup_db.sh` used `set -e` and `pg_dump | gzip > trustcopilot_<time>.sql.gz`
without `pipefail`. gzip's exit status was the pipeline status. A `pg_dump` that
exited 42, or gzip that wrote a bad stream and exited 0, still printed
`Backup written:` and left a file whose name looks like a good backup. A gzip
failure (full disk) exited nonzero but left that same final name in place. There
was no checksum, no temp-file publish, and no failure line.

## What it does now

The script enables `pipefail` and reads `PIPESTATUS` for `pg_dump` and `gzip`.
Tool stderr goes to a temporary directory, not to the script's stderr.

Publish order:

1. Write `.trustcopilot_<UTC timestamp>.sql.gz.partial`.
2. Require `pg_dump` and `gzip` to both exit 0.
3. Require gzip magic `1f8b` and `gzip -t`.
4. Require a sha256 digest, write it to a partial sidecar named for the final
   archive, and compute the digest again.
5. Rename the archive, then the sidecar.
6. Recompute the digest of the published archive. On mismatch, delete the new
   archive and sidecar.

A failure in `dump`, `compress`, `checksum`, or `publish` exits with that stage's
code, deletes the partial files, and does not leave a new `trustcopilot_*.sql.gz`
or `.sha256`. An older published file in the directory is not rewritten.

Stderr on failure is one line:

```text
BACKUP_FAILURE stage=<stage> exit_code=<code> message=<message>
```

`message` is the stage plus a short diagnostic (for example `pg_dump failed` or
gzip's `No space left on device`). Before it is printed, the script replaces
`DATABASE_URL`, URL userinfo, password assignments, and any `scheme://...` text.
The captured stderr file is removed before exit.

An S3 upload runs only after that local publish. If `aws s3 cp` fails, the script
exits nonzero with `stage=upload` and leaves the local archive in place. If the
bucket is set and the `aws` CLI is absent, the local success still exits 0. That
skip was already the behavior.

## Tests

From `apps/api`:

```bash
python -m pytest tests/release/test_backup_failure.py -q
```

Seven tests. No database and no network. On the unchanged script: 6 failed, 1
passed (the missing `DATABASE_URL` guard already exited nonzero). After this
change: 7 passed.

The fakes record the path gzip wrote. Failure and success both require that path
to be a temporary name, not `trustcopilot_<timestamp>.sql.gz`. The fake `pg_dump`
writes the URL and the password to its own stderr. The test fails if either
appears in the script's stdout or stderr. The assertion does not print those
values.

Covered cases: `pg_dump` exit 42, gzip writing a non-gzip stream and exiting 0,
gzip exiting 1 with `No space left on device`, `sha256sum` exiting 3, a
pre-existing archive left untouched, a successful archive plus matching sidecar,
and a missing `DATABASE_URL`.

## Limits

- The tests use stand-in binaries. They do not open a real database, fill a real
  filesystem, or call S3.
- Restore is not implemented here.
- A bucket set without the `aws` CLI still exits 0 after the local publish.
- There is no product metric or API log line for this script. The alert is the
  stderr line above.

## Rollback

Revert the change. No schema, rows, or credentials are involved. Backups already
published under the old script stay as they are; they have no `.sha256` sidecar.
