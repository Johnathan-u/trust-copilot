## Behaviour

**Write.** `POST /api/shareable-spaces` stays on `require_can_admin`. Before the row is inserted, every article, answer, and document id must be a live row in the caller's workspace (`shareable_space_service.py` `create_space`, `_require_ids`). A missing id, a deleted document, and an id from another workspace are the same 404. Nothing is written. An editor is 403. `PATCH /api/shareable-spaces/{space_id}` replaces only the lists the body sends, with the same checks, and does not return a raw token.

**Read.** `GET /api/shareable-spaces/access` still checks the hash, then active, then expiry, and still audits the space id only. The returned lists keep stored order and omit an id that is missing, deleted, or outside the workspace. An article is omitted unless `published` is 1 and a published version exists. An answer is omitted unless `status` is `approved`. The response keys are `valid`, `space`, `article_ids`, `answer_ids`, and `document_ids`. `space.access_token` is null.

Token reads stay on the routes added in TC-17-005b:

| Route | Who |
| --- | --- |
| `GET /api/shareable-spaces/access/documents/{id}/content?token=` | live token, document listed and still in the workspace |
| `GET /api/shareable-spaces/access/articles/{id}?token=` | live token, listed article, published version title and content |
| `GET /api/shareable-spaces/access/answers/{id}?token=` | live token, listed answer, `status` is `approved` |
| `GET /api/documents/{id}/content` | `require_can_review`. A share token is not read. |

Deactivating the space or letting it expire makes the previous download fail. The access response is then `valid` false, with reason `Space deactivated` or `Space expired`.

**Public page.** `/share?token=` is the buyer link (`apps/web/lib/shareable-space-link.ts` `buyerAccessLink`). The page loads `GET /api/shareable-spaces/access` and renders that payload (`apps/web/app/share/page.tsx` `parseAccess`). It shows the space name, then each listed article's published title and content and each listed answer's text from the token read routes above. A document is a download link to the token content route, using only an id from `document_ids`. An id that is not in the payload is not requested. A token read that is not ok is omitted. Buyer email, workspace id, citations, and draft fields are not rendered. An invalid, inactive, or expired token shows the access `reason` and no lists. The page does not call the reviewer document route or the admin article and answer routes. The runbook `docs/ops/shareable-space-token-rotation.md` sends buyers to `/share`. Checking that an old token is dead still uses `GET /api/shareable-spaces/access`.

**Retry.** Create follows the trust-article Idempotency-Key pattern (`shareable_spaces.py` `create_space`, `_claim_or_replay`). The header is optional. When it is present, the stored key is scoped to the workspace and `shareable-spaces:create`. The same key and the same body return the same space and do not insert a second row. The first response still includes the raw token once. The dict passed to `idempotency_set` has that field null and does not contain the raw token or a URL built from it. A replay is 200 with `access_token` null and `token_available` false. The dashboard create form then says "This link was already created. Rotate it to get a new link." A different body with that key is 422 and does not insert. An invalid header is 422. A create that fails the asset check writes no row and releases the key, so the corrected body can use it. A new Python process, which is what an API restart is, reads the stored row and returns the same space without the raw token. `shareable_spaces.access_token` stays null. There is no new column and no new unique constraint.

A create without the header still inserts a new space. Two intentional spaces are not the same request.
