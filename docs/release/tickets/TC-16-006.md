# TC-16-006 — Make runtime feature flags safe and auditable

Status: gap 1 and gap 2 are implemented. This note does not accept the ticket.
Independent review is still open. No migration and no tracker edit.

Evidence: [artifacts/acceptance/TC-16-006/README.md](../../../artifacts/acceptance/TC-16-006/README.md).

Ruling: issue #85, 2026-11-18 17:16Z. Audit flag changes. Environment flags must not override rows in production.

## Gap 1

`PATCH /api/feature-flags` is still `require_can_admin`. A non-admin receives 403
and no audit row. An empty or over-long name receives 400 and no audit row.

Every call that reaches `set_flag` writes one `audit_events` row in the same
transaction as the flag change. `persist_audit` commits the session. The flag
update is still pending on that session, so there is one commit, not the
separate commit used in `members.py`.

| Field | Value |
|---|---|
| `action` | `feature_flag.updated` |
| `user_id` | Session user id. The route passes it only when it is an `int`. |
| `email` | Session email when it is a string. |
| `workspace_id` | Current workspace. |
| `resource_type` | `feature_flag` |
| `resource_id` | Flag key. |
| `details` | `flag_name`, `old_enabled`, `new_enabled`, `changed`. |

`old_enabled` is JSON null when the workspace had no row. A no-op (the row
already stores the requested value) still writes the event, with
`old_enabled == new_enabled` and `changed: false`, and does not update the row.
`feature_flags` has no actor column. The audit row is the record.

`POST /api/feature-flags/seed` inserts missing built-in defaults and does not
write `feature_flag.updated`. An existing row keeps its value.

## Environment variables

Production is `app.core.session.is_production_env()` (`APP_ENV` on the settings
object or the process, whitespace and case ignored).

In production, `FEATURE_*` does not override a stored workspace row. When the
workspace has no row, the variable is the default, ahead of `KNOWN_FLAGS`, and
then the value is false. That default is not an admin write, so it is not audited.

Outside production (`development`, `test`, `staging`) a set variable still
overrides the stored row. `tests/test_feature_flags.py::test_env_override_takes_precedence`
now sets `APP_ENV=development` for the override and `APP_ENV=production` for the
row win. The old assertion was the override with no environment selected.

`1`, `true`, and `yes` enable. Any other set value disables. An unset variable
is not a value.

Documented in `.env.example`, `docs/release/config-contract.md`, and
`docs/ops/feature-flags.md`. The names are dynamic, so they are not rows in the
generated contract table.

## Tests

From `apps/api`:

```sh
python -m pytest tests/release/test_feature_flags.py -q
python -m pytest tests/test_feature_flags.py -q
```

The release file covers an audited change (actor, old value, new value), a
no-op audit, a non-admin 403 with no audit row, a rejected name with no audit
row, one commit for the row and the event, production spellings of `APP_ENV`
that do not let `FEATURE_CONNECTORS_AWS=1` override a stored false row, the
production default when no row exists, and the override in development, test,
and staging.

## Rollback

Revert this change. There is no schema change and no backfill. After a revert
of gap 1, `set_flag` commits the row with no audit event, and `FEATURE_*`
overrides a stored row in production as well as outside it. After a revert of
gap 2, a security-control name can be stored again and the release scan is
gone. Gap 2 does not change the audit write or the production env rule.

## Gap 2

Ruling: issue #85, 2026-11-18 17:52Z. No flag may gate permissions, CSRF,
sessions or audit, and the release check must fail the build.

No registered flag is read outside the flag service, the admin route and the
tests. The web app does not read them. None of them gates a security control,
so no call site was removed. `trust_center.nda_gating` and `credits.enforce`
are product names and are not consulted. They are not the permission, CSRF,
session, audit, rate-limit or tenant-isolation controls.

A security-control name cannot be stored or resolved to false:

| Entry | Behavior |
|---|---|
| `GET /api/feature-flags/{name}` | 400, `Security controls are not feature flags` |
| `PATCH /api/feature-flags` | 400, no row, no `feature_flag.updated` event |
| `is_enabled` / `set_flag` | `SecurityFlagError` before any read or write |
| `seed_defaults` | skips the name and does not insert it |

The match is `is_security_sensitive_flag` (`feature_flags.py`). After strip,
lower-case and hyphen-to-underscore, a dot-segment equals a token or starts
with `<token>_`. Tokens cover permission, CSRF, session, auth, MFA, audit,
rate limit and tenant isolation. `connectors.aws` does not match.
`audit.write` and `auth_bypass` do.

The gap 1 release tests now use the flag key `release.tc16006.row`. The
previous key ended in `.audit`, which this rule rejects. The audit action is
still `feature_flag.updated`.

Release check, both parts, in `tests/release/test_feature_flags.py`. The build
job already runs `pytest -rs` (`.github/workflows/ci.yml`), which collects this
file. No workflow change.

1. `SECURITY_MODULES` is the denylist of permission, CSRF, session, auth, MFA,
   audit, rate-limit and tenant-isolation modules, including `main.py` because
   `CSRFMiddleware` and `GlobalRateLimitMiddleware` live there, and the web
   session middleware. `flag_lookups` fails the test on `is_enabled(`,
   `get_all_flags(`, `set_flag(`, `KNOWN_FLAGS`, `ff_service`, the feature-flag
   service import, `/feature-flags`, `FEATURE_<NAME>`, or a quoted registered
   flag name. The admin router mount in `main.py` is not a lookup. A synthetic
   injected lookup must be reported, so the scan cannot pass vacuously.
2. There is no pricing JSON. The public home and pricing pages are the
   manifest. Both contain `Gmail and Slack evidence ingestion`, and
   `connectors.gmail` and `connectors.slack` must default on. Every other
   `KNOWN_FLAGS` key is listed in `NOT_ADVERTISED_FLAGS`. A new flag, or an
   advertised flag set default-off, fails the test. The home page sentence
   "No tiers, no feature gates" is a withheld pricing claim. It is not a
   reason to turn the unadvertised flags on. The pricing page also advertises
   role-based access and audit logging; those are not flags, and the registry
   is asserted to contain no security-control name.
