## Problem

Generate skips an approved question. It does not insert a second draft or show the approved text beside a new draft. `Answer` has no revision column (`apps/api/app/models/answer.py`). The review page posts the whole questionnaire (`apps/web/app/dashboard/review/[id]/page.tsx`). Priority is P0 because the parent is P0.

## Acceptance criteria

1. On an explicit regenerate, keep the approved row and insert a new draft revision with its own text and citations.
2. The review page shows the approved text beside that draft and requires reapproval before the draft becomes the current approved answer.
3. Document the behaviour in this file.

## Behaviour

`POST /api/answers/{answer_id}/regenerate` requires review permission (`require_can_review`). Another workspace is 403. A missing answer or question is 404. A row that is not approved is 409. Those denials do not change the row. The call inserts an `answer_revisions` row with status `draft` and that draft's own text and citations. The `answers` row stays unchanged, including status `approved`. A second regenerate marks the open draft `superseded` and inserts a new `draft`. The write takes the existing per-question answer lock.

`POST /api/answers/{answer_id}/revisions/{revision_id}/approve` uses the same review and workspace guards. The revision must belong to that answer and still be an open `draft`. Approve stores the previous approved text as a `superseded` revision, copies the draft onto the answer, leaves the answer status `approved`, and marks the draft `applied`.

Until that approval, questionnaire read returns the approved row's text, status, and citations, and returns the open draft beside them. Export uses the approved row, not the draft. The review page shows the approved text beside the draft and asks for reapproval. Editing the draft is not the autosave that writes the approved row.

Bulk generation still skips an approved answer. It does not insert this draft.
