## Release notes

- Password sign-in, MFA verify, and the enrolment recovery-code continuation navigate only to the value returned by `safePostLoginPath`.
- A `next` value that is not a same-origin relative path is replaced with `/dashboard`. That includes absolute URLs, protocol-relative URLs, backslashes, ASCII controls and whitespace, `javascript:` and `data:` schemes, and nested percent-encoding of those forms.
- A path that starts with `/` and stays on the parser origin is kept, including its query and hash. An encoded slash inside a query is kept.
- Middleware and the dashboard shell put only a pathname into `next`. They do not copy a query or a hash from the page that sent the browser to sign-in.
- Demo sign-in, when the build enables it, always goes to `/dashboard`. It does not read `next`.
- No API route reads `next`. There is no server-side redirect for this parameter.

## What the sign-in page does

The sign-in page is the only reader of the `next` query (`apps/web/app/login/page.tsx:30`). It assigns `window.location.href` to `safePostLoginPath` of that value after a successful password sign-in (`:171`), after MFA verify (`:214`), and after the enrolment recovery-code confirmation (`:322`). A failed password sign-in returns without navigating (`:157-159`).

`safePostLoginPath` returns `/dashboard` unless every percent-decoding of the value is a same-origin relative path (`apps/web/lib/post-login-path.ts:10`, `:27-36`, `:44-60`, `:68-76`). The parser base is `https://post-login.invalid`. It is not an allow-list of hosts. An absolute URL never starts with `/`, so it fails closed. Five decode rounds are the limit. A value that still changes when decoded again fails closed. A malformed escape fails closed.

## Middleware and the shell

Middleware, when `tc_session` is absent, redirects to `/login` and sets `next` to `request.nextUrl.pathname` (`apps/web/middleware.ts:6-9`). The dashboard shell does the same with `pathname` (`apps/web/components/layout/DashboardShell.tsx:57-60`). A request for `/dashboard/review/12?tab=open` therefore comes back from middleware as `next=/dashboard/review/12`. The query is not in `next`. A `next` value that already contains a query and a hash, such as `/dashboard/review/12?tab=open#section`, is preserved by the sign-in page.

## Demo sign-in

Demo sign-in is compiled in only when both `NEXT_PUBLIC_DEMO_LOGIN_EMAIL` and `NEXT_PUBLIC_DEMO_LOGIN_PASSWORD` are set at build time (`apps/web/app/login/page.tsx:16-18`). The click handler always assigns `window.location.href = '/dashboard'` (`:241`). It does not call `safePostLoginPath` and it does not read `next`. When the build leaves the demo disabled, the handler sets an error and does not navigate (`:219-221`).

## API

No route in `apps/api` reads a `next` parameter. The backlog file `apps/api/tests/release/test_login_redirect.py` exists because the ticket names it and the file was absent. It runs the three vitest files above. It does not add a server redirect. A server test of `next` belongs here only if a route starts honoring that parameter.

## Help and runbook

No configuration changed. No migration and no backfill. There is no separate runbook for this check. Rollback of this change is reverting the test, this note, and the artifact. The sign-in behavior stays the behavior on `37ac10b8`.

Operators:

- A browser that is sent to `/login?next=...` lands on the path `safePostLoginPath` returns. A dangerous value becomes `/dashboard`. The API does not see `next`.
- An anonymous request for a protected page is sent to `/login` with `next` set to the pathname only. The query and hash of that page are not stored.
- Demo sign-in, on a build that enables it, ignores `next` and opens `/dashboard`.
