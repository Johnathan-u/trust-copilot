## Problem

Cookies, bearer tokens, and URL passwords are masked, and request and job ids remain. Upload warnings still include filenames. Classification logs model text. Sentry drops cookies and Authorization only. Priority is P0 because the parent is P0.

## Behaviour

`FileService.upload_raw` and `FileService.upload_trust_request_attachment` still return the stored key and the sanitized filename to the caller. An oversized body is still 413. A missing or disallowed extension is still 400. The detail of those errors does not include the filename. The object key is still `prefix/workspace/<uuid><suffix>` (or `trust-requests/workspace/request/<uuid><suffix>`). This change does not edit authentication, authorization, or migrations.

The four rejection warnings no longer include the user-supplied filename. `filename` is read only to choose a suffix. Each warning logs `workspace_id`, `size_bytes`, `ext`, and `reason`. `ext` is the lower-case suffix when it is one to eight letters or digits, such as `.pdf` or `.docx`. A missing suffix is `none`. Any other suffix is `other`, so a name placed in the suffix is not written out. A size rejection also logs `max_bytes`. An `upload_raw` extension rejection also logs the fixed allow-list. A trust-request rejection logs `request_id` as that trust request's id on both the size and the extension rejection. When the request context has an HTTP request id made of letters, digits, `.`, `_`, or `-`, the warning includes it as `http_request_id`. Otherwise that field is `-`. These rejections happen before a job exists, so the warning does not invent a `job_id`.

`JsonFormatter` still adds `request_id` and `workspace_id` from the request context when those values are set, and it does not remove `job_id`. The redaction patterns still do not match `request_id` or `job_id`.

`parse_classification_response` logs `JSON parse failed` and the UTF-8 byte length of the model text. It does not log the text. A failed classification call, including a bulk classification failure, logs the exception class name and not the exception message.

Password-reset warnings in `apps/api/app/api/routes/auth.py` already omit the reset URL. They log the user id and, on a send error, the exception class. This change does not edit that path or email delivery. Production email failure still does not print the message body.

Sentry `before_send` still runs only when `SENTRY_DSN` is set. It drops request cookies, the Authorization header, and the request body (`data` or `body`). A value whose key is a filename field becomes `[REDACTED]`. A `/reset-password?token=` value in any remaining string is masked, as are `filename=` pairs and the same secret patterns `redact` already masks. Keys named `request_id` and `job_id` are left in place. A short operator message that is not one of those values is left in place.

The non-production Slack stub still logs the first 100 characters of a message. Production refuses that stub and does not log the text. This change does not edit the stub. A successful upload's audit event still records the stored filename in the audit details. That is the audit record, not the rejection warning. TC-07-011b is unchanged: `apps/api/tests/release/test_log_redaction.py` and `docs/release/tickets/TC-07-011.md` are not added here.

## Acceptance criteria

- **AC1:** User filenames, reset-link tokens, and classification source text do not appear in the upload rejection logs, the classification failure logs, or the Sentry event `scrub_sentry_event` returns.
- **AC2:** Those records keep `request_id` when the request context has one, and they do not remove `job_id`. An upload rejection also keeps the workspace id, the byte size, a short extension, and the reason. A trust-request rejection keeps that request's id.
- **AC3:** This file documents the behaviour.
