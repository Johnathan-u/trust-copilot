# TC-08-005 — Remove shared SQLAlchemy Sessions across worker threads

Status: implemented on branch `tc/core/TC-08-005`, **held unmerged** until depends_on
TC-03-004, TC-06-002, TC-07-007 are DONE (Coordinator ruling). Baseline `c20f949`.

## Finding at baseline

`RetrievalService.batch_search` (`apps/api/app/services/retrieval.py`) ran up to 8
`ThreadPoolExecutor` workers that all queried through the caller's single `Session`
(`self._db`). SQLAlchemy Sessions are not thread-safe. Under concurrency this raises
`InvalidRequestError: This session is provisioning a new connection; concurrent operations are
not permitted` and can interleave statements on one DBAPI connection. The bug is reproduced by
`tests/test_session_concurrency.py` against baseline: 6 of 9 tests fail, see
`artifacts/acceptance/TC-08-005/`. `batch_search` is called by answer generation
(`services/answer_generation.py`).

The background evidence-gap thread in `answer_generation.py` already used its own Session.
However, it bound that Session to `db.get_bind()`, which is a *shared Connection* when the
caller's Session is connection-bound.

Audited and **not** sharing a Session across threads (no change):
- `worker.py`: one `SessionFactory()` per job and per loop iteration; the dispatch loop is serial.
- Thread pools in `answer_generation._generate_batched_answers`,
  `routes/questionnaires.py` (`_classify_one_thread_safe`) and `mapping_llm_classify.py`: these
  do LLM work only, and DB writes happen on the calling thread.
- `routes/members.py` background invite: opens its own `SessionLocal()`.
- `routes/auth.py` reset email thread: no DB.
- Ticket-listed modules (evidence_parser/processor, chunking, index_service, retrieval_cache,
  answer_cache, corpus_version, registry_lifecycle, retention, credential_store_service): no
  threads.

## Behavior after this change

- New helpers in `app/core/database.py`:
  - `supports_thread_isolation(bind)`: true only for a pooled `Engine` (QueuePool/NullPool).
  - `pool_thread_budget(bind, n)`: caps threads at `pool_size + max_overflow - 1`.
  - `task_slots(bind, name, size)`: a process-wide semaphore per engine.
  - `isolated_session(bind)`: a new Session on its own connection, always closed.
- `batch_search` handles each query in its own short-lived Session, used by exactly one thread
  and closed in `finally`.
  - Per-call threads are bounded by `min(RETRIEVAL_MAX_THREADS, len(queries), pool budget)`.
  - Concurrent `batch_search` calls share a process-wide slot limit, so the total task
    connections stay within the pool.
  - The caller's Session is never used from a worker thread.
  - Results are plain dicts, so no ORM instances escape a task Session.
- If the bind cannot be isolated (Session bound to a Connection, or StaticPool/SQLite),
  `batch_search` runs **serially on the calling thread** with the caller's Session. That
  preserves visibility of the caller's uncommitted rows.
- The gap-generation thread uses `isolated_session`. When the bind is a shared Connection, the
  work runs inline on the calling thread instead.
- A failing task propagates its exception. Its Session is still closed, its connection returns
  to the pool, and the caller's transaction is unaffected.

## Configuration

`RETRIEVAL_MAX_THREADS` (default 8, clamped 1–32; documented in `.env.example`). Set it to 1 to
force serial retrieval. The effective value is also capped by the engine pool.

## Behavior change to note

In the threaded path, task Sessions see **committed** data only. Before, they shared the
caller's transaction. All current callers retrieve already-committed, indexed chunks. Callers
holding uncommitted chunk writes on a pooled engine would no longer see them in
`batch_search`. `search()` (single query) is unchanged and still uses the caller's Session.
