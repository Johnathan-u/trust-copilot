# TC-21-003a Settle the accept-suggested idempotency claim after commit

**Status:** implemented. Framework catalogs stay **BLOCKED** pending **TC-01-007**. No framework control text was added. No migration.

`POST /api/compliance/controls/{id}/evidence/accept-suggested` stays admin. `Idempotency-Key` stays optional.

After the evidence item and the link commit, the claim is completed even if `list_tags_for_document` or `idempotency_set` raises. The successful commit is not rolled back. A later `db.rollback()` only clears the failed post-commit transaction.

## Ambiguities

- A post-commit failure completes the claim with the stored result. It does not release the claim. The evidence item and the link are already committed, and releasing the claim would let a retry insert another pair.
- Tag lookup is not part of that write. If `list_tags_for_document` raises, the stored result uses an empty tag list.
- If `idempotency_set` raises, the same result is stored again through the idempotency core. The route still returns the committed result when that second store succeeds. A tag-lookup failure still surfaces as an error on the first response; the stored result is what the same key replays.
