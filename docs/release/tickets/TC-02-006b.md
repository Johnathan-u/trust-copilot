## How each finding was fixed

Synchronous `setState` was removed from effect bodies.

- Values that can be computed from props or other state are derived during render (`lib/render-state.ts`).
- Resets that used to run when an input changed store the previous key during render and update state on that render. `useKeyedGeneration` is that pattern.
- A fetch effect only writes state from the promise callback. The event-handler path still sets loading before it starts the request.
- Subscriptions that already set state from a listener, timer, or promise callback were left on that path.

After this work, `origin/master` (`a53dc7c`) was merged with a pure merge commit. Lint on that tree still exits 0. Unit tests are 24 files and 164 tests. The release Playwright suite, including `workspace-create-denied`, is 43 passed.

`lib/render-state.test.ts` covers the decisions those effects used to make: gated and list loading, page reset, palette index, nav close on navigation, citation-tag clear, slow-loading reset, search activity, trust redirect, missing verification and vendor tokens, proof-chain ids, card and case-study drafts, elapsed seconds, and the toast server snapshot.

## Decisions

1. The initial session read does not increment `requestId`. Loading already starts true. `refresh()` from a later action still increments it and restarts the slow-loading timer.
2. A filter change resets the page during render, so the fetch runs for page 1. The previous effect could also start a request for the old page index.
3. The generation elapsed clock's first update is a zero-delay timer, the same callback style as the one-second interval. Stopping generation sets the clock back to 0 during render.
4. The toast region is read with `useSyncExternalStore`. The server snapshot is null, which keeps the server and client first render aligned.
5. Two `react-hooks/exhaustive-deps` disables on the members and questionnaires effects no longer matched a finding after those effects stopped calling a loader recreated every render. An unused disable fails `--max-warnings=0`, so those two comments were removed. Every other existing disable is unchanged. No new disable was added.
