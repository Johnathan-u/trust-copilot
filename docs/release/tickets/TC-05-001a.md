## Behavior

Password login already withheld the session cookie and returned `requires_mfa`
plus a five-minute `mfa_token` when `UserMfa.enabled` was true. Google, GitHub,
Microsoft, OIDC SSO and ID.me all went through `_provider_login_response` and
issued the member's role without reading `UserMfa`. A workspace with
`mfa_required` and no enabled factor still received that full role; `/api/auth/me`
only reported the flag.

All five provider callbacks still share `_provider_login_response`. That function
now uses the same gate as password login:

- An enabled factor, and not an administrator re-enrolment, stores an
  `MfaLoginToken` and sets no session cookie. Password login still returns
  `{"requires_mfa": true, "mfa_token": ...}`. A provider callback redirects to
  `{FRONTEND_URL}/login?mfa_token=...`. The sign-in page opens the existing
  two-factor form, then removes `mfa_token` from the address bar. Completion is
  the existing `POST /api/auth/mfa/verify-login` (TOTP or a recovery code).
- `Workspace.mfa_required` with no enabled factor, on password and on every
  provider, issues only the five-minute `mfa_enrol` session (`mfa_enrol_only`,
  zero permissions), the same shape as administrator re-enrolment. Password
  login returns `requires_mfa_enrol`. A provider callback redirects to
  `/login?mfa_enrol=1` and the sign-in page starts the existing authenticator
  setup. Confirming the code replaces that cookie with the member's current role.
- An administrator re-enrolment marker still takes that enrolment path, including
  on a provider. An undecryptable `reenrol.` secret still returns
  `mfa_reset_required` and no session. A provider callback redirects to
  `/login?error=mfa_reset_required`.
- No enabled factor and no workspace requirement is unchanged: password login
  returns the member role, and a provider callback still redirects to
  `/dashboard` (or `/onboarding` when there is no membership).

The enrolment session may call `/api/auth/me`, MFA status, setup, confirm and
logout. Other routes stay denied. An enabled factor cannot be skipped by
presenting an enrolment cookie. Login still chooses the membership with the
lowest workspace id. `mfa_required` is read from that workspace.

The one-time MFA token is in the provider redirect query, the same class of
secret as the password-login JSON field and the password-reset link. It expires
in five minutes and is single-use. The page strips it from the address bar after
reading it. It can still appear in that redirect's browser history entry and in
access logs for the login request.

## Limits

No migration. Rollback is reverting this change. A browser that already holds a
privileged cookie from a provider login made before the fix keeps that cookie
until it expires or the user signs out.

Sign-in does not inspect every membership. A later workspace with `mfa_required`
does not gate the session chosen from the lowest workspace id. A user with no
membership still receives the pending onboarding session even if an old factor
row exists, which is the same as password login.

An administrator of a workspace that requires MFA must finish enrolment before
`POST /api/members/clear-mfa-reenrol/{user_id}` will succeed.
