# TC-10-002: Classify job errors and apply bounded retries

Status: implemented on `tc/core/TC-10-002`, based on `master` `d527863` (TC-10-003, #28, merged). It needs a review
from someone other than the implementer.
Evidence: [`artifacts/acceptance/TC-10-002/`](../../../artifacts/acceptance/TC-10-002/README.md).

## Contract

Every job failure is classified into a stable, typed `jobs.error_code` (`app/core/job_errors.py`). The column itself
comes from TC-11-001 (#16, migration `tc11001_model_outcome_codes`); TC-10-002 writes it for every failure.

**Model-provider failures keep TC-11-001's codes.** A `ModelCallError` or an `openai` client exception is classified
with `app.services.model_outcomes.failure_from_exception`, so the job gets the `model_*` code, the catalog's
`retryable` flag and the catalog's safe message (also what `error_detail`/`job_error_payload` return):
`model_rate_limited`, `model_timeout`, `model_server_error`, `model_malformed_output` are retried;
`model_credentials_missing`, `model_credentials_invalid`, `model_unavailable`, `model_quota_exhausted` (fatal) and
`model_refusal`, `model_request_rejected`, `model_error` are terminal. The table below covers everything else
(storage, database, input, provider-like exceptions that are not `openai` types).

| class | codes | worker behaviour |
|---|---|---|
| retryable (transient) | `rate_limited` (429), `timeout` (408/504, client/socket timeouts), `upstream_unavailable` (other 5xx), `connection_error`, `database_unavailable` (SQLAlchemy/DBAPI `OperationalError` etc.) | re-queued with a bounded, jittered backoff while attempts remain |
| terminal | `bad_input` (other 4xx, `ValueError`/`KeyError`/`TypeError`, bad zip, decode errors), `not_found`, `auth_failed` (401, bad keys), `permission_denied` (403), `config_error` (missing `OPENAI_API_KEY`, missing storage credentials or bucket), `internal_error` (anything unrecognised) | `failed` immediately with the code; never retried |

Classification is duck-typed (status codes on the exception or its `response`, botocore `Error.Code`, exception class
names along the MRO) so the module imports neither openai, httpx nor botocore and never touches the network. For
model failures it calls TC-11-001's classifier first (imported lazily).
Handlers can also raise `RetryableJobError` / `TerminalJobError` / `JobConfigError` explicitly.

### Retry schedule

* Attempts per job: `jobs.max_attempts` (default 3), clamped to `[1, 10]` (hard ceiling `MAX_ATTEMPTS_CEILING`).
  `claim_job` increments `attempt` on every claim, as before.
* Delay after failed attempt *n*: `d = min(JOB_RETRY_MAX_SECONDS, JOB_RETRY_BASE_SECONDS * 2^(n-1))`, then
  "equal jitter" uniform in `[d/2, d]`. A provider `Retry-After` raises the floor but is itself capped, so the delay
  is always in `[0, JOB_RETRY_MAX_SECONDS]`. Defaults: base 15 s, cap 600 s (env-configurable, clamped).
* A scheduled retry is a `queued` job with `next_attempt_at` set; `claim_job` skips it until that time
  (`claimable_filter`). No new job status was introduced.
* The in-process completion retry in `answer_generation` (per question) now uses the same classifier and
  `backoff_delay` (base 1 s, cap 10 s) instead of string matching and an un-jittered `1.5^n`.

### Visibility (AC2)

`GET /api/jobs/{id}` keeps TC-11-001's `error_code` and `error_detail` and adds (additive, existing fields unchanged):

| field | meaning |
|---|---|
| `max_attempts` | effective attempt budget |
| `error_code` | typed class of the last failure (TC-11-001 field, now set for every failure), or `null` |
| `retryable` | whether that class is retried (`null` when there is no error) |
| `next_attempt_at` | ISO time of the scheduled retry, or `null` |
| `retry_scheduled` | `status == "queued"` and a retry time is set |
| `retries_exhausted` | `status == "failed"`, retryable code, and `attempt >= max_attempts` |

While a retry is pending, `error` reads `Attempt n of m failed (<code>): <safe message>. Next attempt scheduled at <time>Z.`
After the last attempt it reads `Retries exhausted after n attempt(s) (<code>): ...` and the status is `failed`;
it is never `completed`. On a later success, only the error left by an earlier failed attempt is cleared (history
stays in the audit log).

**Completed jobs keep their `error_code`.** A completed job can carry a non-fatal code (TC-02-BUG-015 will set
`evidence_gaps_failed`). TC-10-002 never overwrites it:
* On success the worker clears `error`/`error_code` only when they are unchanged since the job was claimed. A value the
  handler set during this run is kept.
* `_handle_job_failure` first checks the committed status. If the job is already `completed` (for example, a step after
  the completion commit raised), it leaves the status, `error_code` and `error` alone: no retry, no `job.failed`.
Audit events: `job.retry_scheduled` and `job.failed`, both with `error_code`, `attempt`, `max_attempts` (and
`next_attempt_at`/`delay_seconds` or `retries_exhausted`). The admin alert and in-app notification fire only on the
final failure. Metric `JOB_COMPLETED_TOTAL{status="retry_scheduled"}` counts scheduled retries.

`generate_answers` never reports success while provider errors left placeholders: a missing key or a fatal provider
failure raises TC-11-001's `ModelCallError` (`model_credentials_missing`, `model_credentials_invalid`, ...) and the job
fails as terminal with that code; any other auth/permission/config failure fails it as terminal too; transient failures (after the inner retries) fail the attempt as retryable, and the
job-level retry regenerates only the `llm_error` placeholders (they are exempt from the TC-10-003 answer guard;
approved and human-edited answers stay protected). `index_document` raises a classified error built from the
embedding provider's last exception (`embedding_service.last_embed_error`); while a retry is pending the document
shows `uploaded` with the attempt's error in `index_error`, and `failed` only after the final attempt.
`parse_questionnaire` failures from an unreadable, encrypted or text-less PDF (`PdfTextError`, master #11) are
`bad_input`, so they stop on the first attempt and still mark the questionnaire `failed` with the readable message in
`parse_metadata`, as on master; that handling now lives in the shared failure path (`_handle_job_failure`).

Upstream (provider/storage) messages are reduced to the exception class and HTTP status, and model failures use
TC-11-001's catalog message, so raw response bodies are not stored in `jobs.error`.

## Configuration

| variable | default | notes |
|---|---|---|
| `JOB_RETRY_BASE_SECONDS` | `15` | first backoff step; clamped to `[0, 3600]` |
| `JOB_RETRY_MAX_SECONDS` | `600` | backoff cap (also caps `Retry-After`); clamped to `[0, 86400]` |

Both are passed to the worker in `docker-compose.prod.yml` and documented (commented out) in `.env.example`.
The per-job budget is `jobs.max_attempts` (existing column, default 3).

## Runbook

* **A job shows `retry_scheduled: true`.** Nothing to do; the worker picks it up after `next_attempt_at`. Repeated
  `rate_limited` means provider quota pressure: lower concurrency or raise `JOB_RETRY_BASE_SECONDS`.
* **`retries_exhausted: true`.** The transient condition outlived the budget. Check provider / storage / DB health,
  then re-submit the action (re-upload, re-run generation). A manual "retry now" endpoint is TC-10-004.
* **`model_credentials_missing` / `model_credentials_invalid` / `model_quota_exhausted` / `model_unavailable`,
  `auth_failed` / `permission_denied` / `config_error`.** Fix credentials, billing or configuration (`OPENAI_API_KEY`,
  model name, S3 keys, bucket); these are never retried automatically. `error_detail.message` says what to do.
* **`bad_input` / `not_found`.** The input itself is unusable (corrupt file, deleted object); fix and re-upload.
* **`internal_error`.** An unrecognised exception; not retried on purpose. Inspect worker logs for the job id.
* **Jobs stuck `running` after a worker crash.** A job with an expired lease is recovered by TC-10-001. A `running` job whose `lease_owner` and `lease_expires_at` are still NULL was claimed before that deploy. TC-10-001b recovers it after the NULL-lease grace. The operator SELECT and the fail-by-id statement in the TC-10-001 runbook are the fallback.
* **Rollback.** `alembic downgrade tc25005_case_study_consent` drops `jobs.next_attempt_at` (TC-11-001's
  `error_code` stays; TC-25-011's table and TC-25-005's columns stay). Deploy the previous worker image first,
  since this worker reads the column.
