## Behaviour

`/share?token=` is the public share page. It reads `GET /api/shareable-spaces/access` and shows the space name plus the listed articles, answers, and documents from that payload (`apps/web/app/share/page.tsx`). Article title and content come from the token article read, which returns the published version. Answer text comes from the token answer read, which returns an approved answer. A document is a download link for an id in `document_ids`, on the token content route. The page does not request an id the payload did not list, and it does not render buyer email, workspace id, citations, or draft fields. A token the access route rejects shows that route's `reason` and no lists.

The buyer link copied after rotation uses this page (`apps/web/lib/shareable-space-link.ts`). `docs/ops/shareable-space-token-rotation.md` says the same. The access route itself is unchanged and is still how an operator checks that an old token is dead.

`POST /api/shareable-spaces` takes an optional `Idempotency-Key`, the same header trust-article create uses (`shareable_spaces.py` `create_space`). The same key and the same body return the same space and do not insert a second row. The first response includes the raw token once. The value stored in `idempotency_keys.response_body` does not. `idempotency_set` receives the space with `access_token` null, and any URL built from the raw token is removed before that write. A replay is 200 with `access_token` null and `token_available` false. The dashboard create form says "This link was already created. Rotate it to get a new link." A different body is 422. A failed asset check writes nothing and releases the key. No migration. `shareable_spaces.access_token` stays null.

## Acceptance criteria
